# 用户画像 RAG 系统：线上与离线评测落地方案

## 一、 离线评测：从“开发工具”升级为“产品特性”

既然要求“用户选择做还是不做”，我们将离线评测分为**研发内建**和**用户自定义**两层。

### 1. 能力边界提取与用户提示（拒绝硬拦截）
*   **提取机制**：通过解析 `user_profile_vectors` 的字段分布和 `wiki_vectors` 的文档标签，结合离线测试结果，生成一份 `dataset_boundaries.json`。
*   **前端呈现**：在对话页输入框上方展示提示：“当前库覆盖：高价值画像、退货SOP；缺失：预测分析、会员等级关联。”
*   **防幻觉机制（替代拦截）**：如果用户问了缺失范围的问题（如没有等级列却问钻石会员），**不做代码拦截**。让大模型根据检索到的上下文自己得出“数据缺失”的结论，并结合我们的**后置审查（answer_guard）**过滤掉编造的数字。

### 2. 用户可选的离线评测功能（UI 功能）
*   在知识库管理页（`/v2/#/kb`）增加**【数据集质量评估】**模块。
*   用户上传一份 `QA.json`（问题与预期答案）。
*   点击评估后，后台跑评测集，输出**检索得分**（召回率）和**生成得分**（答案准确性、真实性），以可视化图表展示。用户不点，就不消耗算力。

### 3. 双轨召回定制评测方案
针对“画像+文档”双轨，评测集需设计 3 种题型，并采用专门的指标：
*   **纯文档题**：评估 SOP 召回质量。
*   **纯画像题**：评估条件过滤与特征提取。
*   **混合题**（重点）：如“找出高客单用户，并给出挽回SOP”。
    *   **Dual-Recall@K**：Top-K 结果中必须**同时**包含相关 `user_id` 和对应 `wiki` 文档。
    *   **Attribution Quality（归因质量）**：LLM 输出的建议中，是否明确区分了“数据来源”（来源1：某个具体用户）和“规则来源”（来源2：SOP文档）。
    *   **配比检查**：验证 `Top-3 Profile / Top-2 Wiki` 的精排权重是否合理。

### 4. Text2SQL 执行正确性评测（研发测，不对用户开放）
*   **Execution Accuracy (EX)**：构造 50 个统计类问题及**标准 SQL**。自动化对比 RAG 生成的 SQL 结果与标准结果是否完全一致。
*   **安全用例池**：自动化注入 `DROP`、超大 `LIMIT`、越权查表等恶意 SQL，断言只读账号和正则能 100% 拦截。
*   **自然语言一致性**：SQL 查出 100 人，LLM 总结文本里必须写 100 人，不能写成 10 人（通过正则/NER 校验）。

## 二、 线上监控：AI 驱动的可观测性与数据飞轮

线上监控的核心是**“无感抽样 + 异步裁判 + 数据回流”**。

### 1. 全链路 Trace 埋点
*   在现有的 API 层接入或自研 Trace 机制（或集成 Langfuse）。
*   记录：`trace_id`、`question`、`route`（RAG/SQL）、`sources`、`sql_query`、`answer`、`耗时`。

### 2. 异步 AI 裁判（LLM-as-a-Judge）
*   **抽样策略**：每天抽取 5% 的线上请求（或重点抽取包含复杂查询、点踩的请求）。
*   **裁判 Prompt**：给强力模型（如 Qwen-Max）输入 `{question, context, answer}`。
*   **打分维度**：
    *   **Faithfulness（忠实度）**：回答是否有上下文支撑？（防幻觉）
    *   **Relevance（相关性）**：是否答非所问？
*   **结果告警**：如果某小时线上抽样的平均分低于阈值，触发报警。

### 3. 实时业务指标看板
*   **显式反馈**：点踩率、点赞率。
*   **隐式反馈**：用户复制答案的次数、引用来源点击率。
*   **系统指标**：SQL 报错率、大模型超时率、空结果返回率。

### 4. 数据回流飞轮（闭环）
*   将线上被【点踩】、被【AI 裁判打低分】、或触发了【answer_guard 拦截】的 case 自动落盘。
*   定期（如每周）由人工介入，挑选出真实的 bad case。
*   将 bad case 转化为离线测试集的一部分（补充进 `eval_questions.json`），实现“越用越准”。

## 三、 拒绝“兜底拦截”后的补偿设计

由于明确放弃“前置关键词硬拦截”，系统对**越界问题（如预测未来）**的防御将完全依赖：

1.  **System Prompt 约束**：在核心 Prompt 中强调“只基于给定事实回答，无法预测未来”。
2.  **后置审查 (answer_guard)**：对流式返回的最终内容做正则或语义审查。发现“预测、明年、将会有”等字眼且伴随数字时，直接替换为拒答文案。这种设计是在“回答生成之后”处理的，不拦截用户提问，不误伤正常意图，守住体验底线。

---

**方案总结**：
通过可选的**用户侧离线评测**建立信任，通过**严密的研发侧 SQL 评测**守住安全底线，通过**AI 异步裁判**持续监控线上质量，最终形成基于真实用户反馈的评测飞轮。你可以把这份方案存档，作为后续迭代的指导蓝图。
