# C 端砍价模块 v2 设计

> 状态：设计方案，待确认后实施  
> 日期：2026-11-17  
> 范围：CShop 商品详情 / 购物车 / CApp 对话入口 + 后端报价引擎

## 1. 结论

把现在的「砍价」升级成 **受控的优惠测算 + 报价**：

```text
选商品/SKU/数量 + 可选目标价
→ 确定性规则计算
→ 展示原价 / 满减 / 到手价 / 省多少
→ 可成交才生成 PENDING 报价
→ 用户确认订单
```

不把定价权交给大模型，不做自由砍价，不把“原价成交”包装成“砍价成功”。

## 2. 现状与问题

当前链路：

```text
CShop「让小鱼去砍价」/ 商品详情 / CApp 底部弹层
→ POST /api/c/negotiations
→ negotiation.py 固定规则
→ 创建 PENDING 报价
```

### 2.1 真实存在的问题

| 问题 | 现状 | 影响 |
|---|---|---|
| 默认预算 500 | CShop / CApp 都写死 `negotiationBudget = 500` | 与商品价格无关；低价商品无意义，高客单商品直接失败 |
| 没有目标价 | 只有“预算”字段 | 用户不知道能谈到多少，也不知道差多少 |
| 原价也能“砍价成功” | 当前价 198、预算 500 → `ACCEPTED`，优惠 0 | 用户以为砍价成功，实际上没有省一分钱，信任受损 |
| 满减规则写死 | 满 299 减 30、满 599 减 80 | 商家无法配置；与其他活动口径不一致 |
| 失败不可行动 | `BUDGET_TOO_LOW` 只返回“等平台活动” | 没有“差多少 / 换规格 / 凑单”的下一步 |
| “轮次”不是谈判 | `MAX_ROUNDS=3` 实际是遍历候选商品 | 产品文案“大模型谈判”与实际能力不一致 |
| 两个入口重复 | CShop 和 CApp 各有一套 budget/need/quantity 状态 | 默认值、错误文案、报价行为容易分叉 |
| 报价无过期 | 报价不显示有效期 | 价格/库存变化后可能拿旧报价下单 |
| 无转化埋点 | 只在订单审计里看到结果 | 无法判断砍价对成交有没有帮助 |

### 2.2 可以保留的部分

- 价格、库存来自商家 SKU，不让 LLM 生成价格。
- 报价只落 `PENDING`，用户仍需确认订单。
- C 伙伴不做定价、不自动下单。
- 平台满减作为当前唯一优惠来源，逻辑可控。

## 3. 目标 / 非目标

### 目标

1. 用户 3 秒内知道“能省多少、怎么买最划算”。
2. 可成交时一键生成报价；不可成交时给出下一步动作。
3. 优惠计算 100% 确定性、可审计、可测试。
4. CShop 和 CApp 共用一套砍价 UI/状态。
5. 兼容现有报价、草稿、订单确认链路。

### 非目标

- 不做 LLM 自由议价。
- 不做商家实时改价。
- 不做真实支付。
- 不在 P0 引入复杂促销引擎（优惠券、阶梯价、会员价先不混入）。

## 4. P0 推荐方案

### 4.1 产品定位

入口名称从「砍价」调整为：

```text
算优惠 / 谈优惠
```

对外文案：

> 小鱼帮你算平台满减后的到手价；价格和库存来自商家，优惠以平台规则为准。

“砍价”可以作为运营口语保留在标题，但成交卡必须显示真实优惠和到手价。

### 4.2 用户流程

```text
商品详情点「算优惠」
  → 带出商品 / SKU / 数量
  → 目标价选填（不填=只看当前可享优惠）
  → 计算
  → 方案卡
      ├─ 有优惠：原价 / 满减 / 到手价 / 省多少 → 使用此报价
      ├─ 无优惠：当前按原价，明确“暂无额外优惠”
      ├─ 目标价过低：差 ¥X；给减数量 / 换规格 / 凑满减
      └─ 缺货/规格不可用：明确原因
  → 使用报价 → 准备订单草稿 → 用户确认
```

购物车：

```text
购物车 → 合并算优惠
  → 展示每个 SKU 的报价明细
  → 满减门槛提示
  → 使用此报价
```

CApp：

```text
对话里说「帮我看看怎么买最划算」/「能便宜点吗」
  → 自动带出当前商品
  → 打开同一个「算优惠」底部弹层
  → 不再让用户先理解“预算 500”
```

### 4.3 方案卡

```text
原价            ¥198.00
平台满减        -¥0.00
────────────────────
到手价          ¥198.00
较原价省        ¥0.00

当前没有额外优惠
[按原价加入购物车]  [换规格]

若目标价 ¥150：
还差 ¥48.00
可选：
  减到 1 件（已是 1 件）
  换更便宜规格
  凑到 ¥299 可减 ¥30
```

有优惠时：

```text
原价            ¥328.00
平台满减        -¥30.00
到手价          ¥298.00
比原价省        ¥30.00

报价有效期 15 分钟
[使用此报价]
```

### 4.4 交互原则

- **不预填 500 元预算**；目标价为空，用户不填也能算。
- “预算”改叫“目标价（可选）”，减少用户心理负担。
- 有优惠才显示“砍价成功”；无优惠不能生成 `ACCEPTED` 报价，只能给原价购买或调整建议。
- 谈判过程放折叠区，不把四段 transcript 铺满详情页。
- 数量、规格、目标价变化后重新计算；不能让旧报价混用。

## 5. 后端设计

### 5.1 分层

```text
c_end/bargain.py           纯确定性报价引擎（无 DB 写）
  pricing.py / rules.py    平台满减、凑单、预算差
  negotiation.py           旧接口兼容层（逐步收口）

api/c_end.py
  POST /api/c/bargains/evaluate   只计算，不落库
  POST /api/c/bargains/accept     校验快照 + 创建 PENDING 报价
  POST /api/c/negotiations        保留兼容，内部转新引擎
```

### 5.2 evaluate 返回

```json
{
  "status": "OFFER_AVAILABLE",
  "items": [
    {
      "product_id": "SIM-TEA-01",
      "title": "明前龙井",
      "sku": "SIM-TEA-01-S1",
      "spec": "100g/罐",
      "price": 198,
      "quantity": 1,
      "subtotal": 198
    }
  ],
  "pricing": {
    "list_total": 198,
    "platform_discount": 0,
    "payable": 198,
    "savings": 0
  },
  "target_price": 150,
  "gap": 48,
  "options": [
    {"type": "CHANGE_SKU", "label": "换更便宜规格", "action": "CHANGE_SKU"},
    {"type": "BUNDLE", "label": "凑到 ¥299 可减 ¥30", "action": "BUNDLE"}
  ],
  "quote": null,
  "expires_at": null,
  "transcript": []
}
```

状态枚举：

```text
OFFER_AVAILABLE     有可成交方案（无优惠但原价可买 / 有满减）
NO_DISCOUNT        原价可买，但无优惠
TARGET_TOO_LOW     目标价低于可成交价
REJECTED           缺货 / SKU 不可用 / 商家不匹配
```

### 5.3 优惠规则

P0 只接平台满减：

```text
subtotal >= 599 → -80
subtotal >= 299 → -30
否则 0
```

规则集中在 `bargain/rules.py`，不再散落在 CShop/CApp。

### 5.4 报价快照与一致性

`accept` 必须重新读取：

```text
SKU 价格
可售库存
商品状态
```

如果和 evaluate 快照不一致：

```text
QUOTE_STALE
```

返回变化项，让用户重新计算；不静默用旧价。

### 5.5 幂等与过期

- `accept` 带 `request_id`，同一请求最多生成一个报价。
- 报价建议 15 分钟有效；P0 可在 `prepare`/`confirm` 时用 `c_quote.created_at` 判定过期，不新增表字段。
- 同一购物车只允许一个活跃报价；重新计算前先释放旧报价。

## 6. 前端改造

### 6.1 统一组件

新增一个共享组件：

```text
web/src/components/BargainSheet.vue
```

输入：

```text
product / items / friend_id / merchant_id / target_price
```

输出事件：

```text
quote-created
cart-add
close
```

CShop 商品详情、购物车、CApp 弹层全部复用，避免两套状态。

### 6.2 入口改造

| 位置 | 改造 |
|---|---|
| CShop 商品详情 | 「让小鱼去砍价」→「算优惠」；打开共享弹层，不再读全局 500 |
| CShop 购物车 | 「合并报价」→「合并算优惠」；保留预算字段但可选 |
| CApp 对话 | 砍价意图打开共享弹层；默认目标价为空 |
| 商品卡 | 可选展示“满 299 减 30”提示，不误导为单品直降 |

### 6.3 视觉状态

```text
计算中
有优惠
无优惠
目标价过低
缺货 / 规格不可用
报价过期
报价已使用
```

每种状态必须有明确下一步，不允许只有一行红字。

## 7. 指标与观测

P0 打结构化日志：

```text
bargain_open
bargain_evaluate { status, list_total, payable, savings, has_target }
bargain_no_discount
bargain_target_too_low { gap }
bargain_quote_created
bargain_quote_used
bargain_order_confirmed
```

关键转化：

```text
打开 → 计算 → 有报价 → 使用报价 → 订单确认
```

P0 不建新表，用日志和现有 `c_quote` / 订单审计统计。

## 8. 测试计划

### 单元测试

```text
无优惠：198 元，不生成“砍价成功”
满 299 减 30
满 599 减 80
目标价低于可成交价：返回 gap 和 options
SKU 缺货 / 数量超过库存
购物车多 SKU 合并
价格变化：QUOTE_STALE
重复 request_id：只生成一个报价
报价过期：不可 prepare
```

### API 测试

- evaluate 不落库。
- accept 只生成 PENDING。
- 跨商家/跨用户校验。
- 旧 `/api/c/negotiations` 兼容。

### 浏览器 E2E

```text
CShop 商品详情 → 算优惠 → 有优惠 → 使用报价 → 订单草稿
CShop 无优惠商品 → 明确“暂无额外优惠”
购物车 → 合并算优惠 → 满减
CApp 对话 → 砍价意图 → 弹层 → 报价
移动端 390px 无横向溢出
```

## 9. 分期

### P0（建议先做，1.5–2 天）

- 后端纯计算引擎 + evaluate/accept
- CShop/CApp 共享弹层
- 去掉默认 500
- 有优惠/无优惠/目标价过低三种状态
- 报价快照 + 幂等 + 过期基础校验
- 单测 + 浏览器验收

### P1（2–3 天）

- 商家配置优惠（上限、活动期）
- 多方案排序：满减 / 凑单 / 规格
- 报价 TTL 持久化、后台可观测
- 转化漏斗与 A/B

### P2（不做进本轮）

- 真正多轮 Agent 谈判
- 动态定价/个性化折扣
- 自动下单

## 10. 风险

| 风险 | 处理 |
|---|---|
| 现有 CShop/CApp 逻辑重复 | 先抽共享组件，避免继续分叉 |
| 旧接口/测试依赖 | `/api/c/negotiations` 保留兼容层 |
| 报价与库存变化 | accept/prepare 双次校验，失败给结构化原因 |
| 无优惠时用户失望 | 明确“暂无额外优惠”，给凑单/换规格，不伪造优惠 |
| 范围膨胀 | P0 只做平台满减，不做商家自定义 |
