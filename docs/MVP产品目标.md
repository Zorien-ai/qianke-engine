# MVP 目标文档

**项目名称**：轻量级电商用户画像查询助手
**版本**：MVP v0.1
**文档日期**：2026-10-16

---

## 一、一句话定位

**让中小电商商家上传自己的交易数据和规则文档，3 分钟内获得一个能用自然语言查询的用户画像系统。**

---

## 二、目标用户

**有基础技术能力的中小电商运营/技术负责人。**

具体特征：
- 手里有订单数据（CSV 导出），但不会写 SQL
- 有业务规则（标签定义、SOP），但散落在 Word/飞书文档里
- 想用 AI 提效，但不想把数据传到第三方 SaaS
- 能跑 `docker compose up`，但不会读源码改配置

**不是目标用户**：
- 完全不懂技术的纯运营（推到 v2）
- 大型企业（有数据团队，不需要这个）
- 开发者（他们会自己搭，不需要产品）

---

## 三、解决什么问题

| 现状 | MVP 后 |
|---|---|
| 商家想问"我最近流失了哪些高价值客户"，只能找技术提需求 | 直接在界面里问，几秒出答案 |
| 标签定义散在文档里，新人问老人，老人口口相传 | 上传文档，系统检索并引用来源 |
| 想用 ChatGPT 分析，但不敢把客户数据传上去 | 本地部署，数据不出内网 |

---

## 四、核心流程

```
上传 CSV + .md 规则文档
        ↓
系统识别字段 → 用户确认
        ↓
一键构建（画像 + 向量索引）
        ↓
自然语言查询 → 返回带来源的答案
```

**全程在浏览器里完成，不需要打开命令行。**

---

## 五、做什么（范围）

### 5.1 上传

- 支持拖拽或点击上传
- CSV：多文件，UTF-8 / GBK 自动识别
- 文档：只支持 `.md`，多文件
- 提供规则文档模板下载
- 上传后显示：文件名、大小、行数

### 5.2 字段识别与确认

- 同义词字典匹配（不做 LLM 智能识别）
- 常见字段：user_id、amount、purchase_time、city、gender、age、category、product_name
- 识别到的自动勾选
- 未识别的让用户从下拉框手动选
- 允许跳过不重要字段

### 5.3 文档结构校验

- 统计每篇 `.md` 的标题层级数量
- 预估分块数
- 无标题的文档给出警告（"检索质量可能下降"）
- 不阻塞构建，只提示

### 5.4 一键构建

- 一个按钮触发全流程：数据清洗 → 画像聚合 → 向量化 → 文档分块 → 建索引
- 进度条显示百分比 + 已处理数量
- 不显示预计剩余时间（会不准）
- 构建完成后自动跳转到查询页

### 5.5 查询

- 一个输入框
- 首次进入显示 3-5 个示例问题（根据上传字段动态生成）
- 答案包含：自然语言回答 + 引用来源
- 历史问答列表

## 六、不做什么（明确边界）

| 不做 | 原因 |
|---|---|
| 用户账号体系 | MVP 单用户本地部署，不需要 |
| 多租户隔离 | 同上 |
| 增量导入 | 每次全量重建，简单可靠 |
| 一键部署脚本 | 目标用户能跑 `docker compose up`，暂不封装 |
| 内置标签模板 | 用户上传自己的定义文档 |
| PDF / Word / Excel 解析 | 只支持 .md，降低复杂度 |
| 字段自动转换（生日→年龄） | 用户自己保证数据质量 |
| LLM 智能字段识别 | 同义词字典够用 |
| 前端美化 | 功能优先 |
| 多轮对话 | MVP 只做单轮查询 |
| 聚合统计（Text2SQL） | MVP 只做检索类查询，统计类推到 v0.2 |

**最后一条要注意**：如果 MVP 阶段用户问"有多少用户"，系统会答不上来——因为 MVP 不做 Text2SQL。

**应对**：在示例问题里只放检索类问题（"谁是高价值客户"），不放统计类（"有多少高价值客户"）。

## 七、验收标准

### 7.1 功能验收

| 项 | 标准 |
|---|---|
| 上传 CSV | 支持 UTF-8 和 GBK，10 万行内不崩 |
| 上传 .md | 支持多文件，正确统计标题结构 |
| 字段识别 | Top 8 常见字段识别率 ≥ 70% |
| 用户确认 | 未识别字段能手动选，允许跳过 |
| 一键构建 | 点击后自动完成全部步骤，不需命令行 |
| 进度显示 | 构建期间每 2 秒更新一次进度 |
| 查询 | 输入问题，5-20 秒内返回带来源的答案 |

### 7.2 体验验收

| 项 | 标准 |
|---|---|
| 全流程 | 从上传到第一次查询，不需要打开终端 |
| 首次使用 | 不需要看文档就能完成流程 |
| 错误提示 | 任何失败都有可读的中文提示，不是 Python 报错 |
| 构建失败 | 明确说明哪一步失败，可重试 |

### 7.3 不做验收的部分

- 准确率不要求达到生产级别
- 不要求支持并发
- 不要求性能优化

## 八、技术约束

| 项 | 约束 |
|---|---|
| 部署 | 单机 Docker Compose，一台 8GB 内存的机器 |
| 数据量 | 单次上传 ≤ 10 万行 |
| 模型 | 复用现有 bge-m3 + bge-reranker |
| 数据库 | 复用现有 PostgreSQL + pgvector |
| 查询链路 | 复用现有 hybrid_retriever + reranker |
| 文档处理 | 复用现有 ingest_docs.py |

**核心原则：MVP 是现有 Demo 的"产品化包装"，不是重写。**

## 九、里程碑

| 阶段 | 内容 | 预计 |
|---|---|---|
| **M1：交互原型** | 用假数据跑通"上传→确认→构建→查询"的界面 | 2 天 |
| **M2：真实后端接入** | 上传接口 + 字段识别 + 构建任务 | 3 天 |
| **M3：端到端联调** | 用户能真正上传自己的数据并查询 | 2 天 |
| **M4：内部测试** | 拿 5 份不同来源的真实电商 CSV 测试 | 1 天 |
| **M5：交付** | 打包 + 文档 + 示例数据 | 1 天 |

**总计 9 天。**

## 十、成功标准

**MVP 是否成功的唯一标准**：

> **找 3 个真实的中小电商运营，让他们用自己的数据跑一遍，不需要你在旁边指导。**

如果做到：
- 他们能自己完成上传
- 遇到字段识别不准能自己修正
- 构建完成后能自己提问

**MVP 成功。**

如果做不到，看卡在哪一步，针对性优化——而不是加新功能。

---

## 十一、风险与应对

| 风险 | 应对 |
|---|---|
| 字段识别准确率太低 | 降到 70% 就够，剩下让用户手动选 |
| 用户不知道能问什么 | 示例问题 + 引导文案 |
| 构建时间太长 | 不承诺时间，只显示进度 |
| 用户上传数据格式太乱 | 在确认页面明确提示问题 |
| 用户上传无关文档 | 在上传页明确说明适用范围 |
