# 三端 Agent 平台架构决策文档

**文件名：** `three_agent_platform_architecture_decisions_v0.1.md`  
**版本：** v0.1  
**状态：** 架构决策基线（待技术验证与正式评审）  
**用途：** 为 C 端用户、B 端商户、管理端三套 Agent 的架构设计、开发、测试和验收提供统一依据。

> 本文整理已确认的架构决策。涉及性能、容量、隐私期限及合规要求的参数，在经过真实业务验证之前，均应视为初始设计值，而非生产承诺。

---

## 1. 执行摘要

平台采用“三端独立、底座共享、权限隔离”的总体架构。

- **C 端用户 Agent：** 理解用户需求、调用商品推荐服务、呈现推荐结果，并支持模拟下单。每次创建订单前，必须取得用户对当前订单内容的明确确认。
- **B 端商户 Agent：** 在商户自己的数据权限范围内，完成订单统计、经营分析、用户分群和业务洞察。SQL、统计代码负责事实计算，LLM 负责解释和总结。
- **管理端 Agent：** 查看运行监控与脱敏业务统计，通过专门的纠纷证据服务获取必要证据。第一版只辅助分析和提出处理方案，正式裁决由人工完成。

三端使用独立的 Agent Graph、独立的对外 API 和独立的业务策略；共享 Agent Runtime、基础 Tool 框架、身份认证基础设施、Memory 基础机制和可复用的基础服务。

共享底座不代表共享业务权限或用户数据。

### 核心架构原则

1. 权限必须在后端执行，不能依赖 Prompt 约束。
2. Tool 调用采用“暴露前过滤 + 执行时复核”双层权限控制。
3. 每个商户拥有独立数据库和独立数据库账号。
4. 用户上下文、Memory、商户数据、平台统计和纠纷证据分域管理。
5. 订单创建必须取得用户明确确认；第一版 Agent 自动执行资金操作的金额上限为 0。
6. 记忆和证据的删除必须考虑在线数据、缓存、索引、备份及恢复流程。
7. 先确保安全边界和可观测性，再逐步提高自动化程度。

## 2. 决策状态与解释

本文中的决策分为三类：

- **已确认：** 当前设计和实现必须遵守。
- **第一版约束：** 第一版主动关闭部分自动化能力，但底层设计允许未来扩展。
- **待验证：** 需要通过原型、安全测试、压测、业务试点或合规评审确定最终参数。

后续任何重大变更，都应记录变更原因、备选方案、影响模块、数据安全影响、迁移方式、测试方法和回滚方案。

涉及权限、隐私、资金操作和纠纷裁决的变更，应进行专项评审。

## 3. 总体架构

### 3.1 逻辑架构

```text
C 端客户端
    │
    ▼
C 端 API ── C 端 Agent Graph ─────────┐
                                     │
B 端客户端                            │
    │                                │
    ▼                                ├── Shared Agent Runtime
B 端 API ── B 端 Agent Graph ────────┤      ├── Tool 调用框架
                                     │      ├── State / Event 基础设施
管理端客户端                          │      ├── 模型适配
    │                                │      ├── 权限检查接口
    ▼                                │      └── 可观测性
管理端 API ── 管理端 Agent Graph ────┘

C 端 Graph
    └── 推荐服务
          └── Recommendation Engine

B 端 Graph
    └── 商户授权数据访问层
          ├── 商户 A 独立数据库
          ├── 商户 B 独立数据库
          └── 其他商户独立数据库

管理端 Graph
    ├── 监控服务
    ├── 脱敏统计服务
    └── 纠纷证据服务
          └── 按案件授权的必要证据
```

### 3.2 三端独立与基础能力共享

| 模块 | 决策 |
|---|---|
| Agent Graph | 三端独立，各自维护业务流程和策略 |
| Agent Runtime | 共享核心运行机制，通过端级配置和策略隔离 |
| State | 共享基础 State 类型，各端扩展字段独立 |
| Tool | 共享 Tool 框架，业务 Tool 按端划分 |
| API | 三端具有独立的 API 服务边界 |
| 身份认证 | 共享认证基础设施，三端授权规则独立 |
| Memory | 共享底层机制，不共享用户级记忆空间 |
| 数据库 | 按端、商户和数据用途隔离 |
| 代码仓库 | Monorepo，严格模块边界 |
| 开发顺序 | 最小公共底座 → B 端 → C 端 → 管理端 |

### 3.3 Monorepo 约束

采用 Monorepo 便于共享基础设施、统一依赖版本和开展跨模块测试，但不能因此允许模块任意依赖。

需要通过以下机制保持边界：

- 规定模块依赖方向。
- 对共享模块和端专属模块进行区分。
- 使用 CI 检查禁止不合规的跨端依赖。
- 为三端维护独立测试与验收基线。
- 将安全策略和业务规则放在明确的领域模块中。

共享模块只放稳定、通用的能力。端专属策略不得无条件下沉到共享 Runtime。

## 4. 身份、权限与 Tool 安全

### 4.1 统一认证、独立授权

- 使用统一身份认证中心管理登录身份和会话。
- C 端、B 端和管理端分别定义角色、权限范围和授权规则。
- 共享的是认证机制和权限检查基础设施，不是三端的业务权限集合。
- 后端根据可信登录身份确定用户、商户和资源范围。
- Agent 不能通过修改参数切换商户、用户身份或数据库。

### 4.2 Tool 权限控制

每个 Tool 应声明：

- 所属端及允许调用的角色。
- 所需能力和资源范围。
- 读操作、写操作及外部副作用。
- 是否涉及资金、隐私数据或高风险操作。
- 输入与输出 Schema。
- 超时、重试与幂等策略。
- 审计要求。

权限控制分为两层：

**第一层：暴露前过滤。** 只向当前 Agent 暴露已授权的 Tool。

**第二层：执行时复核。** 每次调用时，后端重新验证身份、租户、资源范围、操作权限及适用策略。

第一层减少误用机会，第二层才是真正的安全边界。Prompt 中的“禁止越权”不能替代服务端权限校验。

### 4.3 商户数据库隔离

- 每个商户使用独立数据库。
- 第一版允许多个商户数据库部署在同一数据库服务器，但必须保持数据库和凭证隔离。
- 每个商户使用独立数据库账号，该账号只能访问对应商户数据库。
- 数据库路由由后端根据可信身份决定。
- Agent 不得传入任意连接字符串或通过用户输入切换数据库。
- 数据访问层执行租户范围检查，并记录必要的审计信息。
- 未来可以根据规模、安全要求和合规要求，将商户数据库迁移到独立实例。

## 5. C 端商品推荐与订单流程

### 5.1 推荐系统职责

推荐服务作为独立基础服务，同时在 Agent 侧封装为 Tool。

工作流程：

1. C 端 Agent 理解用户需求并整理约束。
2. Agent 调用推荐服务。
3. Recommendation Engine 执行召回、排序、过滤和业务规则校验。
4. 推荐服务返回候选商品及必要的展示信息。
5. Agent 组织结果并以推荐卡片呈现给用户。

第一版以规则和统计推荐为主，预留 ML（机器学习）推荐模型接口。

商品价格、库存、可售状态及排序事实应来自可信业务服务，不得由 LLM 自行编造。

### 5.2 推荐隐私

- 用户原始上下文默认仅供 C 端推荐 Agent 在授权范围内使用。
- 商户可以购买平台提供的黑盒推荐服务或配置获准的推荐权重。
- 商户不能查看平台级用户画像、用户原始上下文或完整推荐权重。
- 推荐服务只接收完成任务所必需的字段。
- 推荐服务应记录必要的算法版本、规则版本和结果信息，支持后续评测与排查。

### 5.3 模拟下单

第一版支持模拟下单，但订单模型和状态流转按照真实订单架构设计，减少未来迁移成本。

强制约束：

- 创建订单前必须展示订单关键信息，并取得用户明确确认。
- 用户曾表达购买意向，不等于确认本次订单。
- Agent 不得根据模型推断自动完成订单确认。
- 确认必须绑定当前订单内容或订单版本。
- 如果价格、商品、数量等关键字段发生变化，应重新取得确认。
- 后端负责订单状态、价格校验、并发处理和幂等控制。
- 重复请求不得产生重复订单。
- 模拟交易与真实支付必须在接口、配置和权限上明确区分。

## 6. B 端商户经营分析与用户画像

### 6.1 数据权限边界

商户只能访问自身业务范围内的数据。

- 商户 A 不得访问商户 B 的订单。
- 商户不得查看平台级用户画像或 C 端用户原始上下文。
- 商户专属画像只能基于该商户有权使用的数据生成。
- 管理端统计权限不等于可以查看商户原始订单明细。

### 6.2 事实计算与 LLM 分工

采用“确定性计算提供事实，LLM 提供解释”的设计。

| 任务 | 主要责任方 |
|---|---|
| 订单数量、销售额、转化率 | SQL / 统计代码 |
| 时间趋势和分组统计 | SQL / 统计代码 |
| 用户分群与统计特征 | 数据处理流程 |
| 指标解释与趋势总结 | LLM |
| 经营建议与后续分析问题 | Agent / LLM |
| 高影响业务操作 | 独立授权流程，必要时人工审批 |

重要结论应说明时间范围、样本量、数据更新时间和计算口径。

数据不足时应明确说明不确定性；不得将相关性直接描述为因果关系。

### 6.3 Agent 工作流

B 端以 ReAct（推理—行动—观察）为主，必要时进入专门的分析流程。

- Tool 调用必须经过权限检查。
- 查询应限制时间范围、返回行数和计算成本。
- 大规模分析优先使用受控 SQL 或统计任务。
- 不应将大量订单明细无必要地传入 LLM。
- 分析结果应尽可能追溯到原始指标、查询口径和数据版本。

## 7. 用户 Memory 与隐私生命周期

### 7.1 Memory 写入机制

Memory 采用初始化模板和受控字段，例如：

- 称呼。
- 回答风格。
- 长期偏好。
- 对后续服务有帮助的非敏感信息。

用户可以修改受控字段，但不能通过 Memory 直接注入任意 System Prompt。

安全机制：

- 使用占位符变量。
- 使用 Schema 校验。
- 执行规则过滤。
- 将用户内容与系统指令分离。
- Memory 不能改变系统安全策略或绕过 Tool 授权。

Agent 可以提取候选记忆，但正式长期记忆必须经用户确认后保存。

可以根据固定数量阈值或重要偏好规则，定期提示用户批量确认候选记忆。LLM 只负责提取候选，不得自行决定将其保存为正式长期记忆。

默认排除密码、支付凭证等高敏感信息，只持久化必要且有服务价值的信息。

### 7.2 冲突处理与检索

- Memory 版本化，支持查看和恢复历史版本。
- 新旧偏好冲突时保留历史，并总结偏好变化。
- Agent 可以自动更新内部偏好演变摘要，但新增正式长期记忆仍需用户确认。
- 当前对话与历史记忆冲突时，以当前对话为优先依据。
- 如果当前对话可能代表长期偏好变化，可以生成候选记忆等待确认。
- 检索采用混合检索：关键词、向量语义和时间等元数据过滤。
- 每条记忆记录来源、创建时间、更新时间和置信度。
- Agent 必须结合当前上下文判断历史记忆是否仍然适用。

### 7.3 删除、恢复与导出

- 用户可以选择性删除 Memory，也可以一键清空。
- 删除后，记忆立即从 Agent 可用记忆中移除。
- 删除的记忆进入 30 天回收站，但在回收站期间不得被 Agent 使用。
- 30 天后永久删除。
- 恢复时以新版本重新生效。
- 用户可以导出当前画像和有效记忆，不包含已删除数据或内部系统信息。
- 删除聊天记录默认只删除聊天记录，并提供“同时删除相关记忆”的选项。
- 原始聊天记录默认保存 30 天，用户可提前删除。
- 不同数据类型可以配置不同保存期限。
- Memory 基础设施可以共享，但用户级权限校验、访问隔离和敏感数据加密必须独立执行。
- 审计记录读取、修改、删除和恢复等操作，但不保存记忆正文。

## 8. 管理端与纠纷处理

### 8.1 管理端数据范围

管理端可以查看：

- 服务运行监控。
- 告警与执行状态。
- 脱敏业务统计。
- 经过案件授权的纠纷证据。

管理端默认不能直接查看用户原始对话或商户订单明细。

纠纷证据必须通过专门的证据服务获取，管理端 Agent 不直接连接商户数据库。

### 8.2 纠纷证据服务

证据可包括：

- 订单记录。
- 支付记录。
- 物流记录。
- 与当前纠纷直接相关的沟通证据。

只允许获取解决当前案件所必需的数据。

每次证据访问都记录：

- 操作人员或服务身份。
- 案件 ID。
- 数据类型和访问范围。
- 操作时间、类型与结果。
- 适用的授权或策略版本（如适用）。

审计日志不保存证据正文。

证据服务应支持授权撤销、异常访问告警和定期审查。

### 8.3 风险规则与裁决边界

- 纠纷风险由固定规则引擎判定。
- 规则由管理端配置、版本化，并经过人工审核后生效。
- Agent 不得自行修改规则或覆盖风险等级。
- 第一版采用“按未来可扩展的架构设计，按当前风险约束实施”的方式。
- 第一版 Agent 只负责收集证据、分析事实和提出处理方案。
- 所有正式裁决由人工完成。
- 可提前设计 `RiskPolicy`、`DisputeDecision` 和人工审核流程，但第一版关闭自动裁决。
- 涉及资金的 Agent 自动执行金额上限为 **0**。
- 退款、赔付等资金操作必须由人工处理。
- 第一版可以按预先批准的规则执行低风险非金钱操作，例如更新纠纷状态或发送处理结果通知。

### 8.4 人工复核

用户或商户可以申请一次人工复核。

复核应由独立于涉事商家的平台专职纠纷处理人员负责，复核结果为最终结果。

### 8.5 补证与超时

- 证据不足时，Agent 通知双方补充证据。
- 仍然不足时转人工。
- 补充证据期限按纠纷类型配置，第一版默认 72 小时。
- 一方超时未提交证据时，不得仅因未提交就直接判定该方败诉。
- 低风险案件可依据现有证据和固定规则继续处理。
- 高风险案件转人工。
- 支持多种证据类型，并记录来源与可信度。
- 关键事实必须核验；无法核验时转人工。

### 8.6 证据保留与删除

- 纠纷证据和裁决记录默认保存 180 天。
- 可按纠纷类型配置期限，法律或合规要求优先。
- 到期后删除证据正文，只保留必要的脱敏统计和删除审计信息。
- 定期检查数据库、缓存、对象存储和索引中的残留数据。
- 备份应有保存期限。
- 删除后保留删除标记，备份过期后执行清理。
- 恢复备份时必须重放删除标记，避免已删除数据重新生效。

## 9. 独立统计仓库与隐私

### 9.1 数据处理架构

商户数据库通过受控处理流程生成脱敏统计，并写入独立统计仓库。

管理端 Agent 不得直接遍历商户数据库生成平台统计。

第一版采用定时批处理，预留增量更新能力。处理流程应支持：

- 失败重试。
- 任务重跑。
- 任务状态记录。
- 输入范围和输出版本记录。
- 数据质量校验。
- 处理代码和口径版本追踪。
- 幂等执行。

### 9.2 仓库数据范围

仓库存储：

- 平台整体指标。
- 经权限控制的商户级聚合指标。

原则上不保存：

- 原始用户对话。
- 完整订单明细。
- 可还原个人行为的统计明细。

### 9.3 最小样本量与推断风险

- 按指标类型设置最小统计样本量阈值。
- 样本不足时不展示。
- 防止通过反复筛选、交叉对比或细粒度时间切片推断个人行为。
- 需要评估查询频率、筛选组合和输出精度限制。
- 阈值应由隐私评审确定，而不只是 UI 层隐藏规则。

### 9.4 隐私规则版本化

- 隐私规则由管理端配置、版本化，并经人工审核后生效。
- Agent 不能自行修改或绕过规则。
- 隐私规则升级后，历史统计结果也必须按当前规则重新校验。
- 不符合要求的结果停止展示，必要时重新计算。

### 9.5 数据新鲜度

- 数据处理失败时，可以暂时展示上一次成功生成的统计结果。
- 必须明确显示更新时间和数据新鲜度。
- 超过按指标配置的有效期限后停止展示并触发告警。

初始示例：

| 指标类型 | 示例有效期 |
|---|---|
| 订单统计 | 24 小时 |
| 月度经营分析 | 7 天 |

以上只是初始设计示例，需要根据业务刷新频率校准。

## 10. 监控、告警与故障恢复

### 10.1 第一版能力

第一版提供：

- 基础健康检查。
- 错误日志。
- 异常告警。
- 管理端监控面板。
- 即时通知。
- 人工排查和恢复流程。

第一版暂不承诺硬性 RTO（恢复时间目标）。

### 10.2 告警级别

| 级别 | 含义 | 未确认升级时间 |
|---|---|---|
| P0 | 紧急：核心服务中断、严重安全或数据风险 | 5 分钟 |
| P1 | 严重：重要功能受损或影响范围较大 | 15 分钟 |
| P2 | 一般：局部问题或存在可行绕过方式 | 60 分钟 |

告警级别由规则引擎判定。Agent 可以分析原因并提出建议，但不能自行修改告警等级。

### 10.3 告警生命周期

- 告警恢复后进入“待确认”状态。
- 管理员确认后关闭。
- 重复告警应合并并累计次数。
- 持续未解决时按规则升级。
- 通知按服务和责任人定向发送。
- P0 额外通知平台负责人。

### 10.4 通知失败处理

- 通知失败最多自动重试 3 次，间隔递增。
- 重试仍失败时切换备用通知渠道并记录状态。
- 所有渠道失败时，保留失败记录、在管理端显示异常并等待人工处理。
- 通知系统自身故障时，管理端显示异常，并通过独立备用告警通道通知负责人。

### 10.5 恢复目标

第一版由人工排查和恢复，不设硬性恢复时间。待系统稳定并积累运行数据后，再制定 RTO 和服务等级目标。

## 11. 备份、恢复与数据删除

### 11.1 备份安全

- 备份整体加密。
- 备份密钥与备份数据分开管理。
- 严格限制备份读取和恢复权限。
- 恢复操作应有审批与审计。
- 每季度在隔离环境进行恢复演练。
- 重大架构变更后额外执行恢复演练。

### 11.2 RPO 目标

| 数据类别 | 目标 RPO |
|---|---|
| 核心业务数据 | 最多丢失 5 分钟 |
| 普通日志 | 最多丢失 24 小时 |

这些是目标值，必须通过备份频率、日志复制策略和恢复演练验证。

RPO 不等于 RTO。第一版暂不设置硬性 RTO。

### 11.3 删除与备份恢复

删除流程必须考虑：

- 主数据库。
- 缓存。
- 对象存储。
- 向量索引。
- 统计仓库。
- 备份副本及过期清理。

删除后保留必要的删除标记。恢复备份时重放删除标记，确保已删除数据不会重新进入在线系统、搜索索引或 Agent 上下文。

## 12. 第一版与后续版本边界

| 能力 | 第一版 | 后续方向 |
|---|---|---|
| Agent Graph | C/B/管理端独立 | 按业务复杂度优化流程 |
| Runtime | 共享核心运行机制 | 扩展运行时能力与性能 |
| API | 三端独立 API 边界 | 按规模独立部署和扩容 |
| 推荐 | 规则和统计为主 | ML 召回、排序和在线评估 |
| 下单 | 模拟下单，必须明确确认 | 经安全和合规评审后接入真实交易 |
| B 端分析 | SQL/统计提供事实，LLM 负责解释 | 增量分析和指标语义层 |
| Memory | 用户确认后保存、版本化、可删除 | 更精细的偏好演变与检索评估 |
| 纠纷 | Agent 辅助分析，人工正式裁决 | 充分验证后探索低风险自动裁决 |
| 资金操作 | Agent 自动执行金额上限为 0 | 需独立安全与合规审批 |
| 统计仓库 | 定时批处理和聚合数据 | 增量更新与数据质量监控 |
| 告警 | P0/P1/P2，人工恢复 | 根据运行数据制定 SLO/RTO |
| 商户隔离 | 独立数据库和独立账号 | 按风险或规模迁移到独立实例 |
| 备份恢复 | 加密备份、季度演练 | 自动化恢复验证和灾备体系 |

## 13. 风险与待技术验证项

1. **租户隔离：** 验证 API、Tool、SQL、缓存、向量检索和后台任务不存在跨商户访问路径。
2. **Tool 授权：** 验证暴露前过滤与执行时复核均有效，权限撤销能够及时生效。
3. **幂等与重试：** 验证网络超时和重复请求不会造成重复订单、重复通知或重复副作用。
4. **订单确认：** 验证订单内容变化、确认过期、并发修改和重复提交的处理。
5. **推荐质量：** 建立离线评测集，验证召回、排序、过滤和推荐解释。
6. **事实可靠性：** 验证经营分析结论可追溯到 SQL 或统计结果。
7. **Memory 隐私：** 验证跨用户检索隔离、敏感信息过滤、删除后不可用和恢复行为。
8. **纠纷证据：** 验证案件授权、证据最小化、访问审计和到期删除。
9. **统计隐私：** 使用小样本、组合筛选和重复查询测试推断风险。
10. **批处理可靠性：** 验证失败重试、任务重跑、版本回滚和过期数据停止展示。
11. **告警链路：** 验证通知重试、备用渠道、重复告警合并、升级和确认关闭。
12. **备份恢复：** 验证加密密钥可用性、恢复完整性、删除标记重放和 RPO 目标。
13. **容量与延迟：** 为 Runtime、模型调用、推荐服务、数据库查询和批处理建立基准测试。
14. **合规期限：** 30 天聊天记录默认期限、30 天 Memory 回收站和 180 天纠纷证据期限，均需经过法务或合规审核，并支持按数据类型配置。

## 15. 验收基线

### 15.1 架构与权限

- 三端 Agent Graph 和 API 边界可以独立测试。
- 未授权 Tool 不会暴露。
- Tool 执行时的权限复核不能被绕过。
- 商户 A 无法访问商户 B 的数据库、缓存、索引或统计明细。
- Agent 无法通过修改输入参数切换租户或任意数据库连接。
- 三端用户上下文和 Memory 默认相互隔离。

### 15.2 推荐与交易

- 推荐结果来自推荐服务，业务事实不由 LLM 臆造。
- 每次创建订单都需要与当前订单内容绑定的明确用户确认。
- 重复提交不会造成重复订单。
- 第一版不会触发真实支付或真实资金操作。

### 15.3 Memory 与隐私

- 未经用户确认的候选记忆不会成为正式长期记忆。
- 删除后的记忆立即不再被 Agent 检索或使用。
- 回收站中的记忆不可用，恢复时以新版本生效。
- 用户能够导出有效记忆。
- 审计记录不包含记忆正文。
- 删除标记在备份恢复后仍然有效。

### 15.4 纠纷与统计

- 管理端 Agent 不直接连接商户数据库。
- 纠纷证据访问必须经过案件授权并生成审计记录。
- 第一版所有正式裁决由人工决定。
- 第一版资金操作自动执行金额上限为 0。
- 统计仓库不包含原始对话或完整订单明细。
- 小样本统计不会展示。
- 隐私规则更新后历史统计结果会重新校验。
- 数据过期或处理失败时明确标记新鲜度，超过有效期限后停止展示。

### 15.5 运维与恢复

- 告警级别、确认关闭、合并、升级和备用通知链路可验证。
- 通知最多重试 3 次后切换备用渠道。
- 每季度恢复演练有记录。
- 重大架构变更后执行额外恢复演练。
- 核心业务数据 RPO 5 分钟、普通日志 RPO 24 小时目标经过测试或演练验证。
- 第一版不承诺硬性 RTO。

## 16. 待确认决策清单

以下事项需要在生产或规模化阶段前进一步确定：

- 三端具体技术栈、部署拓扑和服务拆分粒度。
- 认证协议、会话生命周期、密钥管理和权限撤销传播时间。
- 商户独立数据库的物理部署方式、连接池隔离和凭证轮换策略。
- 推荐服务评测指标、数据字段、模型接口和上线门槛。
- 订单状态机、确认有效期、幂等键保留期限和异常补偿流程。
- Memory Schema、敏感信息分类、导出格式和删除验证机制。
- 统计最小样本量阈值、查询限制和各指标新鲜度期限。
- 纠纷分类、风险规则、证据类型、法定保存要求及补证期限。
- 告警渠道、责任人映射、通知间隔和升级策略。
- RPO 的实际实现方式、演练标准及未来 RTO/SLO 的制定流程。
- 各服务的容量、延迟、可用性、成本和安全基线。
- 数据保留期限及用户数据权利相关设计的法务和合规审核。

## 17. 架构原则摘要

1. **三端独立，底座共享。** 共享代码不等于共享权限、上下文或业务数据。
2. **权限在服务端执行。** Prompt 不是安全边界；每次 Tool 调用都要复核权限。
3. **租户隔离默认开启。** 每个商户使用独立数据库和独立账号，路由由后端控制。
4. **确定性系统负责事实。** SQL、统计和规则引擎产出可核验结果，LLM 负责解释、归纳和提出建议。
5. **高风险动作受人类控制。** 订单创建需要用户明确确认；第一版纠纷正式裁决由人工完成，资金自动执行上限为 0。
6. **数据最小化。** 只访问、保存和输出完成任务所需的数据。
7. **记忆可控、可追溯、可删除。** 正式长期记忆需用户确认，删除后立即不可用，并贯穿备份恢复流程。
8. **隐私规则版本化。** 规则需要人工审核，历史统计也必须重新校验。
9. **运行过程可观测。** 记录关键事件、状态、版本、耗时、错误和审计元数据，不把敏感正文写入普通日志。
10. **第一版先保证边界正确。** 自动化可以逐步提高，但不能牺牲权限、隐私、幂等性和可恢复性。
