入口：用户 → API 混合召回 + RRF 融合 分来源精排（核心，加粗边） 生成与溯源 出口：answer + sources

数量变化一览

阶段输入输出作用
向量召回query → 1024 维向量Top-20pgvector cosine 相似度
BM25 召回jieba 分词后 queryTop-20关键词精确匹配，补向量语义盲区
RRF 融合2 × 20Top-30按排名累加，免归一化
分池取舍303 + 2 = 5画像与 wiki 分池；多路时画像池合并后统一精排取全局 3
生成5 条候选answer + sources带编号引用、区分事实/推断、脱敏

读图要点

  1. 双轨并行：向量与 BM25 两路独立召回，各取 Top-20，互不影响，任何一路失效另一路仍可用。
  2. RRF 免归一化：cosine 距离与 BM25 分数量纲不同，用排名而非分数融合，规避归一化调参；同一文档双路命中则分数累加，天然奖励"双路共识"。
  3. 分池取舍（核心）：本图是单路视角。候选按 source 是否以 .md 结尾拆成两池——画像池取 Top-3、文档池取 Top-2。若单池精排，8110 条画像在数量上会整体挤掉 29 个业务规则分块，SOP / 标签口径类问题将无据可依。
    　多路时两池取舍不同：画像池把各路候选合并后统一精排再取全局 Top-3（画像之间是竞争关系，分路各取 3 个再合并会带回 9 条凑数项；统一精排用原问题打分——改写式只负责召回，不参与评判）；文档池仍是每路各取 Top-2（不同改写式命中的常是不同文件，分路才保得住覆盖）。单路时两者完全等价。
  4. 引用可回溯：候选全程携带 id / source / text，生成后映射回原文，sources 返回编号、来源类型与原文片段（截断 100 字）。

图例

公共预处理（编码 / 分词） 向量召回分支（pgvector） BM25 召回分支（jieba + rank_bm25） RRF 融合与输出

TOP_K 参数表

参数值说明
TOP_K_VECTOR20向量单路召回数量
TOP_K_BM2520BM25 单路召回数量
TOP_K_RRF30RRF 融合后候选数量
rrf_fusion(k)60平滑常数，抑制头部单一排名的主导性
sensitivity_max3向量召回敏感度过滤上限
dept可选传入时对画像表追加 AND dept = %s

真实 SQL（向量召回）

SELECT id, user_id, profile_text, 'user_profile' AS source,
       1 - (embedding <=> %s::vector) AS score
FROM user_profile_vectors
WHERE sensitivity <= %s
  -- [可选] AND dept = %s
ORDER BY embedding <=> %s::vector
LIMIT 20;

RRF 公式

score(d) = Σ_r  1 / (k + rank_r(d) + 1)        k = 60, rank 从 0 计
  • 同一文档在两路中都出现则分数累加——这正是 RRF 既奖励"双路命中"、又不需要归一化的原因。
  • BM25 分支在分词阶段做了三层清洗：同义词归一（女性→女）、停用词过滤（画像文本为统一模板，"用户/累计/订单"等词几乎全量出现，只带噪声）、单字过滤（仅保留"男/女"）。

config.py · 被 5 个模块直接 import api/main.py · 唯一组装点 retrieval/* generation/* db 与离线入库脚本

依赖矩阵

模块依赖角色
config.py（无）零依赖底座，被 5 个模块直接 import
db/connection.pyconfig第二层公共依赖，连接单例 + 探活重连
retrieval/hybrid_retriever.pyconfig, db在线读库；被 api 调用
retrieval/reranker.pyconfig纯模型推理，不碰数据库
generation/generator.py（无，仅第三方 openai SDK）纯 LLM 调用，不感知向量库
api/main.pyretrieval, generation, db唯一组装点，lifespan 预加载
ingest_data.pyconfig, db离线：画像 CSV → 向量入库
ingest_docs.pyconfig, db离线：Markdown → 分块入库

读图要点

  • config.py 是唯一的零依赖底座，被 5 个模块直接 import（db、retrieval×2、ingest×2）——改配置只需改一处。
  • db/connection.py 是第二层公共依赖：在线检索读库（hybrid_retriever）与离线入库写库（ingest_*）都经它拿连接。
  • api/main.py 是唯一组装点；retrieval 与 generation 之间互不感知——检索层不知道有 LLM，生成层不知道有向量库，替换任一侧不影响另一侧。
  • hybrid_retriever.py 与 reranker.py 彼此不 import，两个模块平级，由 main.py 依次调用。

附 · 五个关键设计点

v1.0 / 2026-10
#设计点落点解决什么问题
1双轨召回rerank_by_source画像与业务规则分池取舍：画像池跨路合并统一精排（全局 3 条），文档池每路保名额（各 2 条），避免 wiki 被 8110 条画像在数量上挤掉
2RRF 融合rrf_fusion(k=60)两路分数无需归一化，按排名累加，双路命中获得奖励
3引用溯源候选带 id/source/text生成后映射回原文，sources 返回编号 + 类型 + 片段
4探活重连get_conn()每次调用先 SELECT 1，失败自动重连（规避服务端 kill 后 closed 仍为 0 的坑）
5预加载lifespan启动时一次性加载模型 + BM25 语料，避免首次请求慢
