# 项目背景：电商领域的用户画像智能分析助手

> 本文档描述立项背景、业务痛点、技术路线与能力边界。
> 文中所有技术细节、数据规模、参数取值均取自仓库实际代码与数据目录，不做推测性描述。
> 系统架构与流程图见 `docs/architecture-diagrams.md`，已知问题与优化记录见 `bug/`。

## 一、行业背景

### 1.1 电商行业进入精细化运营时代

中国电商行业已从「流量红利」阶段进入「存量博弈」阶段。主流电商平台的获客成本持续攀升，用户增长趋缓，**从「拉新」转向「留存与复购」成为行业共识**。

在这一背景下，电商企业的核心竞争力从「谁能获取更多流量」转变为「谁能更精准地理解和服务存量用户」。用户画像、分群运营、精准营销，从「加分项」变成「必选项」。

### 1.2 用户数据爆炸式增长

一个中等规模的电商平台，每天产生的用户行为数据包括：

- **交易数据**：订单、支付、退款、优惠券使用
- **行为数据**：浏览、点击、搜索、加购、收藏、分享
- **服务数据**：咨询、投诉、工单、评价
- **营销数据**：活动曝光、触达、转化、退订

这些数据分散在多个系统（CRM、OMS、数据仓库、客服系统）中，**数据量以 TB 级增长，但利用率极低**。

本项目不接生产库，数据底座是公开的模拟数据集：6 个主流电商平台（天猫、淘宝、京东、拼多多、苏宁易购、1688）各 1000 条 2024 年全年中文交易记录，按 `user_id` 聚合为 **8110 条用户画像**。它规模不大，但字段结构与真实画像一致，足以验证「自然语言 → 画像 + 规则 → 可溯源答案」这条链路是否跑得通。

### 1.3 用户画像成为核心资产

电商企业普遍已建成用户标签体系。本项目的画像字段与之对应：

| 标签维度 | 本项目实际字段 |
|---|---|
| 人口属性 | `age` / `gender` / `city` / `member_level`（钻石 / 黄金 / 白银 / 普通，由客单价推导） |
| 行为偏好 | `top_category`（7 大类目）/ `platforms`（活跃平台） |
| 消费价值 | `order_count` / `total_amount` / `avg_amount` |
| 生命周期 | `days_since_last_buy`（以 2024-12-30 为数据快照日） |
| 自然语言画像 | `profile_text`（供向量与 BM25 检索） |

**但「有标签」不等于「会用标签」**——这是当前行业最普遍的困境，也正是本项目要验证的那一段。

## 二、业务痛点

### 2.1 业务人员查数难、用数难

**典型场景**（对应本项目评测集的四个板块）：

| 角色 | 想做的事 | 现状 |
|---|---|---|
| 运营 | 「高客单、喜欢美妆的女性用户有哪些」 | 提需求 → 等分析师排期 → 3 天后拿到 Excel |
| 客服 | 「U2765 是什么用户」「物流延迟投诉怎么回复」 | 打开 3 个系统手动拼凑 + 翻话术文档 |
| 产品 / 分析师 | 「美妆用户的客单价分布」「用户分析报告有哪些板块」 | 写 SQL 或找数据团队 |
| 管理层 | 「本周高价值用户规模有多少」 | 等周报，或临时开会问数据部门 |

**核心问题**：**数据就在那里，但业务人员取不到、看不懂、不会用。**

### 2.2 分析依赖技术团队，响应慢

- 业务提需求 → 分析师理解需求 → 写 SQL 取数 → 出报告 → 反馈
- **一个完整周期 2-5 天**，紧急需求也要半天
- 分析师被大量重复取数需求淹没，无法做深度分析
- 业务人员等不起，活动窗口期错过了

### 2.3 标签口径不统一，理解有偏差

- 「高价值用户」在不同部门定义不同
- 「流失预警」的判定标准散落在文档里，没人完整记得
- 新人上手靠口口相传，容易出错
- **同一句话，运营和数据团队理解不一致**

本项目把口径收拢到 `data/docs/tag_definitions.md` 一处，答案里的每个结论都标注 `[来源N]` 指回该文档——口径不再靠人记，而靠检索。

### 2.4 知识沉淀难，经验无法复用

- 客服话术、营销 SOP、分析报告模板散落在个人电脑里
- 老人离职，新人上手慢
- 历史分析结论没有结构化沉淀，重复分析同样的问题

本项目的知识库目前是 6 篇 Markdown（标签口径 / 分群策略 / 客服 SOP / 营销手册 / 会员权益 / 报告模板），按标题 + 长度两段式切成数十个分块入库。它的价值不仅是「能查到」，更是**把散落的经验变成了可版本管理、可被检索的系统资产**。

### 2.5 通用大模型无法直接用

业务人员尝试用 ChatGPT / DeepSeek 直接提问：

- **不知道数据**：大模型没有企业内部的用户画像数据
- **不知道口径**：「高客单」在你们公司的定义是什么，大模型不知道
- **会编造**：问它「有多少高价值用户」，它会给你编一个数字
- **有合规风险**：把用户数据贴给外部大模型，违反数据安全规定

## 三、现有方案的局限

### 3.1 传统 BI 看板

**优点**：固定指标可视化，管理层日常监控够用。

**局限**：

- 只能看预设的指标，无法回答「临时想到的问题」
- 业务人员要学 BI 工具的操作
- 改动指标要 IT 支持

### 3.2 SQL 取数平台

**优点**：灵活，能回答任意问题。

**局限**：

- **要求会写 SQL**，业务人员门槛高
- 不理解标签口径的人，写出来的 SQL 结果可能是错的
- 没有引用溯源，结论可信度靠人工判断

### 3.3 数据 API 服务

**优点**：程序化调用，可集成到业务系统。

**局限**：

- 只支持预设的查询模式，灵活性差
- 新增需求要开发排期

### 3.4 直接调用大模型

**优点**：自然语言交互，门槛低。

**局限**：

- **无企业内部数据**，回答无依据
- **会编造**，幻觉严重
- **无引用溯源**，无法审计
- **合规风险**，敏感数据外泄

## 四、RAG 技术带来的机遇

### 4.1 RAG 解决的核心问题

**RAG（检索增强生成）= 检索 + 生成**，用企业自己的数据回答业务问题。

| 通用大模型 | 本项目的 RAG 系统 |
|---|---|
| 不知道企业内部数据 | 检索企业画像库（8110 条）+ 知识库 |
| 会编造数字 | 基于检索结果生成；统计类问题走 Text2SQL，数字来自库内真实聚合 |
| 不知道业务口径 | 检索 `tag_definitions.md` 等口径文档，并标注来源 |
| 无合规约束 | 召回前置 `sensitivity` / `dept` 过滤 + 生成层脱敏要求 + 只读 SQL 白名单校验 |

### 4.2 为什么 RAG 适合电商用户画像场景

**电商用户画像有三个特点**，恰好是 RAG 的强项：

1. **数据 + 知识并存**
   - 结构化数据：用户画像字段（可直接聚合）
   - 非结构化知识：标签口径、SOP、营销手册
   - **本项目同时检索两者**——`user_profile_vectors`（画像）与 `wiki_vectors`（文档）是两张独立的表

2. **查询类型多样**
   - 事实查询：「U2765 是什么用户」
   - 语义检索：「很能花钱的女生都有谁」
   - 定义查询：「高客单怎么定义」
   - 流程查询：「物流延迟投诉怎么回复」
   - 统计查询：「各会员等级的用户人数分别是多少」
   - **一条链路统一承接**

3. **合规要求严格**
   - 用户数据分级敏感（表内已有 `sensitivity` / `dept` 列）
   - 不同角色访问权限不同（召回 SQL 支持 `AND dept = %s` 前置过滤）
   - **过滤发生在召回阶段，而不是生成之后**

### 4.3 本项目选择的差异化路线：多路聚合 + 按需 SQL

相比「直接用大模型」或「传统 BI」，本项目采用**多路聚合架构**——检索路与 SQL 路不再是互斥分支，而是同一次问答里的可选路：

```
用户提问
  ↓
① 二分类路由（规则层，零模型开销）
   闲聊 / 域外  → 固定回复，不检索、不调模型
   其余全部     → 多路聚合
  ↓
② 多路规划（1 次 LLM 调用同时产出三件事）
   · 路由复核（捞回关键词路由的漏判）
   · 是否需要追加 SQL 路
   · 需要哪几路检索（直接 / 分解 / 简化 / 关键词 / 假设）
  ↓
③ 多路并行混合检索（每一路独立执行）
   向量召回（pgvector + bge-m3，Top-20）
 + 关键词召回（BM25 + jieba 分词，Top-20）
 → RRF 融合（k=60）→ Top-30
  ↓
④ 分池取舍（bge-reranker-v2-m3 · CrossEncoder）
   画像池：各路候选合并后统一精排 → 全局 Top-3   ← 跨路竞争，只留最相关的
   文档池：每路各自精排 → 每路 Top-2            ← 分路保覆盖，子问题的口径不被挤掉
  ↓
⑤ 各路结果合并去重（不二次竞争，避免三层精排）
   ↓                            ↓
检索路候选                   SQL 路（规划判定需要时才追加）
                              Text2SQL → 安全校验 → 执行
   └──────────┬────────────────┘
              ↓
⑥ 一次生成（DeepSeek）
   引用溯源 [来源N] · 事实 / 推断分离 · 敏感字段脱敏
              ↓
   {answer, sources, route, sql?, rows_count?, trace}
```

**核心理念**：

- 画像数据回答「**谁符合**」（哪些用户满足条件）
- 业务规则回答「**符合什么标准**」（口径怎么定义）
- SQL 路回答「**有多少 / 分布如何**」（数量、占比、排名、两群对比）
- 三者结合，答案既准确又可解释

### 4.4 五个关键设计点

| # | 设计点 | 落点 | 解决什么问题 |
|---|---|---|---|
| 1 | **分池取舍** | `query_processor.search_variants` + `reranker.rerank_by_source` | 两池要的东西不同，所以取舍方式也不同：**画像池跨路合并统一精排（全局 Top-3）**——画像之间是竞争关系，分路各取 3 个再合并会带回 9 条凑数项；**文档池每路各保名额（Top-2）**——不同改写式命中的常是不同文件，分路才保得住覆盖，且 wiki 不会被 8110 条画像在数量上整体挤掉 |
| 2 | **RRF 融合** | `rrf_fusion(k=60)` | 向量分与 BM25 分量纲不同，按**排名**融合即可，无需分数归一化；双路命中获得累加奖励 |
| 3 | **SQL 非分支而是多路之一** | `query_processor.plan_queries` | 关键词判聚合类问题实测漏判率 50%；改为复用规划那一次 LLM 调用判定，免费且更准 |
| 4 | **引用溯源** | 候选全程携带 `id / source / text` | 生成后映射回原文，`sources` 返回编号、来源类型、精排分数与原文片段 |
| 5 | **故障与缺口严格区分** | `pipeline.ROUTE_ERROR` | 数据库连不上时明确回「检索服务暂不可用」，不伪装成「资料里没有」 |

## 五、项目定位

### 5.1 一句话定位

**面向电商业务人员的用户画像智能分析助手，用自然语言查询用户画像、标签定义、运营 SOP、营销策略与聚合统计，答案附引用溯源。**

### 5.2 服务对象

评测集按这四个板块组织（共 33 题，含边界与负样本）：

| 角色 | 核心诉求 | 典型问法 |
|---|---|---|
| 运营 / 市场 | 圈人群、看画像、查策略、做活动 | 高客单、喜欢美妆的女性用户有哪些 |
| 销售 / 客服 | 查客户速览、SOP 流程、话术推荐 | 用户投诉物流延迟怎么回复 |
| 数据分析师 / 产品 | 查标签、分群、报告模板、品类分析 | 美妆用户的客单价分布 |
| 管理层 | 经营快问快答、业务规则查询 | 本周高价值用户规模有多少 |

### 5.3 能力边界（诚实声明）

**当前能做的**：

- ✅ **语义 / 事实检索**：「很能花钱的女生都有谁」「U2765 是什么用户」
- ✅ **标签口径与知识查询**：「高价值用户怎么定义的」「钻石会员有什么权益」
- ✅ **SOP / 策略检索**：「物流延迟怎么回复」「高价值沉默客怎么运营」
- ✅ **组合条件查询**：「高客单 + 美妆 + 女性」
- ✅ **聚合统计（SQL 路）**：「各会员等级的用户人数」「客单价最高的 10 个用户」
- ✅ **两群对比**：「北京和上海的钻石会员在客单价与品类偏好上的差异」
- ✅ **边界处理**：闲聊 / 域外问题拦截；`DELETE` 类注入被 SQL 白名单校验拦下；知识缺口如实回答「数据里没有这个类别」，不编数字
- ✅ **可信输出**：引用溯源 + 事实 / 推断分离 + 敏感字段脱敏要求

**当前不能做的（待扩展）**：

- ❌ **时间序列预测**（「预测明年 GMV」）——库内只有 2024-12-30 的**单时点静态快照**，没有时间序列表。SQL 只能重述历史，无外推能力
- ❌ **多跳关系推理**（「和 U2765 相似的用户」）——只能退化为按画像特征近似匹配，理想解是 GraphRAG
- ❌ **真实时效语义**（「本周」「近 30 天」）——数据是 2024 全年快照，只能按 `days_since_last_buy` 近似处理并**明确声明是近似口径**
- ❌ **全量统计**——画像只有 8110 条样本，「全体用户」结论的统计意义有限

**已知的、待收敛的灰区**（记录在案，不掩饰）：

- 标签口径与画像字段存在**口径错配**：`tag_definitions.md` 中「高价值用户」定义含「近 90 天」时间窗，而画像字段是累计快照，SQL 只能近似实现该口径
- 「是否需要 SQL 路」的判定在**边界题上会漂**：同一问题（如「高客单用户和普通用户的偏好差异」）两轮可能判出不同结果，导致耗时差一倍。已通过细化 prompt 判据把漂移从 4/5 收敛到 10/10，但灰区不会消失

## 六、预期价值

### 6.1 效率提升

| 指标 | 现状 | 本项目 |
|---|---|---|
| 常规画像查询 | 2-5 天 | 秒级~十几秒（实测单次问答 6~20s，视是否走 SQL 路） |
| 标签口径查询 | 问人 / 翻文档 | 秒级 |
| 客服速览用户 | 3 个系统切换 | 一句话搞定 |
| 分析师重复取数 | 占用 60% 时间 | 释放到深度分析 |

**但要说清楚瓶颈在哪**：逐环节实测显示 **LLM 调用占单次问答耗时的 92%~99%**，本地计算（多路检索 + RRF + 精排 + SQL 执行）合计不到 1 秒。所以：

- 当前的主要优化方向是**减少 LLM 往返**（按需多路、关闭思考模式、SQL 段精简、答案缓存 + 流式输出首字）
- 优化检索、融合、精排算法**收益极小**——这一结论是测量出来的，不是猜的

### 6.2 质量提升

- **引用溯源**：每个结论可追溯到数据来源（`sources` 带编号、来源类型、精排分数、原文片段）
- **口径统一**：标签定义直接从知识库引用，避免理解偏差
- **合规可控**：召回前置过滤（`sensitivity` / `dept`）+ 生成层脱敏要求 + SQL 只读白名单校验 + 查询超时保护 + 检索过程 trace 留痕

### 6.3 知识沉淀

- 历史分析报告、SOP、营销策略结构化沉淀为可检索文档
- 新人上手靠问系统，不再靠口口相传
- 知识资产可复用、可迭代（文档改了重跑入库与索引重建即可生效）

### 6.4 业务价值

- **运营**：更快圈人群，抓住活动窗口
- **客服**：更快了解用户，提升满意度
- **产品**：更快洞察需求，优化体验
- **管理**：更快拿到数据，支撑决策

## 七、项目定位与行业趋势

### 7.1 从「数据驱动」到「对话驱动」

过去十年，电商行业完成了从「经验驱动」到「数据驱动」的转型。但「数据驱动」的前提是**人能接触到数据、理解数据、使用数据**。

现实是：

- 数据仓库建好了，但业务人员不会用
- BI 看板做出来了，但只能看预设指标
- 标签体系建完了，但没人知道怎么用

**RAG 代表的「对话驱动」是下一阶段**——让业务人员用最自然的语言（提问）来使用数据，**把「数据民主化」从口号变成现实**。

### 7.2 本项目在技术演进中的位置

```
传统 BI（固定报表）
    ↓
自助 BI（拖拽分析）
    ↓
SQL 取数平台（会写 SQL）
    ↓
【本项目】RAG 对话式分析 + 按需 Text2SQL（自然语言）  ← 当前位置
    ↓
Agent 自主分析（多步推理 + 自动执行）
    ↓
GraphRAG + LLM Wiki（知识沉淀 + 关系推理）
```

**本项目的价值不仅在于解决当下问题，更在于验证「对话驱动」在电商用户画像场景的可行性**——它跑出来的三条结论，正是后续演进的依据：

1. 检索与精排的工程质量够用（本地计算占比不到 1%），**瓶颈在 LLM 调用次数与输出长度**
2. 「是否需要结构化查询」由 LLM 规划统一判定，**比关键词规则可靠得多**，这是走向 Agent 化的一小步
3. 关系推理（「和某人相似的用户」）用检索做不了，**是 GraphRAG 的明确切口**

---

## 八、总结

**电商行业进入存量博弈时代，用户画像成为核心资产，但「有标签不会用」是普遍困境。**

**传统方案**（BI / SQL / API / 通用大模型）各有局限，无法同时满足「自然语言交互 + 企业数据 + 引用溯源 + 合规可控」四个要求。

**本项目用 RAG 技术**，构建面向电商业务人员的用户画像智能分析助手：

- **多路聚合**：二分类路由筛闲聊 → 多路规划 → 向量 + BM25 混合召回 → RRF 融合 → 分池取舍（画像池统一精排 / 文档池分路保名额）
- **按需 SQL**：统计与两群对比由 Text2SQL 承接，数字来自库内真实聚合，受只读白名单与 LIMIT 约束
- **引用溯源**：每个结论可追溯，事实与推断分离
- **合规前置**：召回阶段过滤 + 生成层脱敏 + SQL 安全校验
- **能力边界清晰**：能做检索 / 定义 / SOP / 聚合 / 对比，不能做预测 / 关系推理 / 真实时效

**这是「对话驱动」在电商用户画像场景的一次验证**——它的成功与否，决定了下一阶段是继续深化 RAG，还是转向 Agent 或 GraphRAG。
