## 3. 当前 B 端问题清单

P0 表示可能影响数据理解、操作判断或基础导航的阻碍；P1 为高频操作效率；P2 为一致性与扩展。以下是设计优先级，不是已确认的线上事故。代码定位以本节开头的基线提交和函数名为准。

| 编号 / 优先级 | 当前证据 | 对商家的影响 | 2.0 处理方向 |
|---|---|---|---|
| B01 / P0 | `loadOrders`、`loadAfterSales` 固定 `limit=100`；`ordersView` / `afterSalesView` 将数组长度显示为“共 N 单”，没有翻页。见 [JS](../../web/src/b-workbench.js)。 | 超过加载范围时，容易将当前批次理解为全部订单/售后。 | 先标明“已加载”，完整总数与分页由服务端契约支持，不能用前端切片伪装全量。 |
| B02 / P0 | `onOrderAction` 的标记支付/完成直接调用写接口；`onTicketAction` 直接提交通过、拒绝、验收。取消订单及 Agent 审批已有单独确认，不能说全部操作无确认。 | 不同入口的确认深度不一致，退款与入库后果未在动作前集中核对。 | 对有金额/库存/终态影响的操作统一“对象、金额/数量、后果、确认”步骤；继续保留服务端权限和状态校验。 |

## 4. B 2.0 信息架构与经营概览

### 4.1 导航与现有能力映射

桌面左侧栏建议 232px；窄桌面可折叠为 64px。保留当前商家名称、角色与环境标识；现有权限以 `/me` 返回值决定，不能只靠隐藏导航做鉴权。没有已支持的多店切换契约前，不展示能切换的假控件。

| 分组 | 模块 | 现有入口 / 状态 | 首页联动 |
|---|---|---|---|
| 首页 | 经营概览 | 新增只读聚合视图，数据接口待补 | 待发货、待售后、低库存、待审批进入带条件列表 |
| 交易 | 订单；售后 | `orders`、`after-sales` | 各自独立队列、可关联核对 |
| 商品与库存 | 商品；SKU 库存；库存告警 | 拆分组织现有 `products` 能力 | 告警进入对应商品/SKU；标记处理不改库存 |
| 客户 | 用户画像 | `chat-profiles` | 从订单买家进入有权限的画像；不虚构 CRM 编辑能力 |
| 经营协作 | 调查与审批 | `superagent`，保留技术标识用于排查 | 待审批/执行失败提醒；详情显示依据、拟执行动作与结果 |
| 管理 | 动作策略；执行审计 | `policy`、`audit` | 保持角色限制；策略变更与执行记录可追溯 |

模块顺序可按商家研究调整；不新增营销、结算、采购、财务或客服聊天等“只有入口”的空模块。暂不把独立页面迁为 Vue SPA；入口和构建迁移另作技术决策。

### 4.2 首页构成

```text
商家 / 角色 / 环境                         更新时间与刷新
经营概览                                业务日期范围
待发货       待处理售后       低库存 SKU       待人工审批
待办队列（类型、对象、原因、状态、可执行下一步）
近期订单 / 库存异常摘要                  最近处理结果
```

首屏优先回答“需要处理什么”，不以大图表或欢迎语占据空间。四张数字卡均能进入同口径列表，不显示假趋势、假收入或默认零值。

| 卡片 | 建议口径 | 基线可用性与前置条件 |
|---|---|---|
| 待发货 | 当前商家状态 `PAID` 的订单数；“超时”须另有承诺发货时间 | 列表可筛状态，但目前限量；需完整计数契约 |
| 待处理售后 | 分开计数 `OPEN` 与需要验收的 `RETURN_SHIPPED` | 状态已有；需租户范围、总量与分页一致 |
| 低库存 SKU | 沿用服务端阈值口径：安全库存大于零且可售量不高于安全库存 | 已有商品快照汇总，但受加载范围影响；不得称预测缺货 |
| 待人工审批 | `WAITING_APPROVAL` 工作项，执行失败单列提醒 | 现有列表限制 50；聚合时不得把返回条数当全部 |

补货建议现为 `max(0, safety_stock - available_qty)`；等于安全库存时可能显示低库存但建议补货为零。应保留口径说明，是否改为预测补货由产品另定。没有销量、采购交期、在途等数据时，不添加“还能卖 N 天”。

## 5. 关键页面方案

### 5.1 统一列表与详情契约

- 页面结构：标题/范围 → 常用状态视图 → 搜索与筛选 → 已选条件 → 记录列表 → 总数与分页。筛选改变回第一页；清空搜索保留明确反馈。
- 桌面默认舒适密度：正文 16px、简单行高 48px；可选紧凑密度 14px/40px。多商品摘要行允许 64px，不硬截关键信息。表头固定、数字右对齐；缩小重复留白优先于缩小文字。
- 桌面详情抽屉建议 560–640px，保留列表位置；小于 768px 为全屏详情。复杂编辑进独立页，列表抽屉只承担核对和单一动作。
- 当前详情只突出一个主操作，次操作用普通按钮，危险动作与确认层明确标注。列表里的“查看/处理”使用低强调按钮，避免每行一块主色。
- 关闭详情恢复触发点焦点和筛选位置；Escape 可关闭非提交态，Tab 不逃出模态详情。未保存内容关闭前提示。提交中防重复，失败保留填写内容；成功重新取得状态，不能仅改本地标签。
- 全量搜索、准确总数、排序、跨页选择与批量写入都依赖后端；契约未具备时隐藏对应操作或明示“仅当前加载范围”，不能做出全量能力的外观。

### 5.2 订单列表

桌面建议列：订单号/创建时间、买家、商品摘要/件数、金额、订单状态、物流、操作。默认按创建时间倒序；待发货视图建议按支付时间排序，但需确认该字段及稳定次排序键。订单号可复制，文本截短时详情可看完整值。

筛选首层保留状态、订单号/买家、日期；更多条件按实际支持逐步增加。保存视图是后续增强项，先实现 URL/状态恢复；不要把“商品状态”“支付状态”“物流状态”混成一个标签，基线只有订单状态时照实显示。

详情结构：订单身份与当前状态 → 下单时商品/SKU 快照 → 金额构成 → 物流 → 关联售后 → 操作记录。商品资料修改后不重写历史订单名称、价格或规格；历史快照字段缺失时标为未提供，不用当前商品值补成历史事实。

主操作随状态：`CREATED` 的支付标记需确认它是否只属于演示流程；`PAID` 发货；`SHIPPED` 完成订单仅按现有权限开放。取消放次级危险操作。发货详情底部确认，包含订单号、商品/SKU/数量、承运商、单号与后果；不新增自动支付、批量退款等能力。

### 5.3 商品 / SKU 与库存

商品视图用小缩略图和表格：商品名/ID、状态、分类、SKU 数、价格范围、可售/锁定汇总、低库存提示、更新时间、操作。SKU 视图一行一个规格：商品、SKU、规格、价格、可售、锁定、安全库存、建议补货。显示“可售”而非笼统“库存”，缺值用“未提供”。

搜索支持商品名/ID/SKU，筛选状态、分类、低库存；这些是目标交互，基线仅有低库存筛选，服务端查询需另行补齐。抽屉分“基本信息 / SKU / 图片 / 记录”。现有图片上传、删除及权限完整保留；添加图片是图片分区主操作，不把它提升成全商品页唯一业务目标。

SKU 编辑、价格批改、上下架、库存调整暂列接口依赖，不提供假保存按钮。将来的库存调整必须显示原值、调整量、结果及原因；锁定库存不可当可售库存直接覆盖。告警详情可以关联商品，但“标记已处理”和“补货入库”必须是不同动作。

### 5.4 售后

列表列：工单号/申请时间、关联订单、类型、退款金额、状态、退回物流、操作。默认待处理；类型、状态、订单/工单号、申请日期为筛选目标。没有 SLA 截止时间时显示申请时间，不生成倒计时或“超时”结论。

详情抽屉：申请内容与原文 → 订单商品/金额 → 寄回信息 → 状态记录 → 审核区域。`OPEN + REFUND_ONLY` 与 `OPEN + RETURN_REFUND` 用不同确认文案；`RETURN_PENDING` 表达等待买家寄回；`RETURN_SHIPPED` 的验收明确退款和恢复库存的影响。拒绝理由是设计建议，基线写接口只有布尔值，需后端支持后才能承诺记录。

关联订单从详情可打开，返回后保持当前工单和列表。暂不设计基线未支持的部分退款、换货、多仓验收与自动判责；这些不是简单增加 UI 字段即可实现。

### 5.5 移动端

小于 768px 建议底部“概览 / 订单 / 商品 / 更多”，售后与审批待办在概览直达；更多提供全部完整名称，避免 `Super` 缩写承担主要导航。768–1023px 采用可收起侧栏，1024px 以上常驻侧栏。

订单与售后改紧凑卡片：第一行对象/状态，第二行商品/金额，第三行关键时间/物流，末行“查看处理”。筛选用底部面板，已选条件在列表上方可见；详情全屏，确认操作固定底部并预留安全区，键盘弹出不得遮住必填字段或确认按钮。控件触控区域至少 44×44px，输入文字建议至少 16px；详细审计可横滚，但不能撑宽整页。

移动端保留最常用的查单、发货、售后核对、SKU 查询及已有图片操作。复杂批量编辑和策略配置可提示转桌面，不声称完全等价。离线或权限不足时显示原因，不能静默提交或把失败标成完成。

## 6. 设计原则与 token 建议

遵循 [DESIGN.md](DESIGN.md) 的中性底色、边框优先、少阴影、可核对状态；B 端用表格/队列，C 端用对话/商品浏览。共享语义与组件骨架，不把 C 端聊天气泡、宠物头像、商品大图或低密度卡片复制成工作台主布局。

当前 C 壳为暖色市集方向，DESIGN v1.0 仍以灰青为目标，文档还存在 C 端深浅主题描述不一致。以下是待评审映射，**不直接修改任何现有变量**。

| 语义 token | 建议 | 解释 |
|---|---|---|
| `--b-surface` / `--b-canvas` | 映射 `--ds-paper-0` / `--ds-paper-50` | 与家族中性色同源；不引入大片暖色或蓝紫背景 |
| `--b-text` / `--b-text-secondary` | `--ds-paper-900` / `--ds-paper-600` | 正文与必要说明保证可读；关键状态不用低对比 muted |
| `--b-border` | `--ds-paper-200` | 普通区域细边框，无层层投影 |
| `--b-action` / `--b-action-soft` | 优先评审 `--ds-accent-strong` / `--ds-accent-soft` | 品牌色与当前 C 壳映射须统一决定，保留黑色主按钮的可选方案 |
| 语义成功/警告/危险 | 复用 `--ds-positive-*` / `--ds-warning-*` / `--ds-negative-*` | 状态必须有文字；颜色不能成为唯一信息 |
| 字体 | sans 正文，mono 用于 ID/金额/时间；金额两位小数 | 数字等宽、右对齐；标题 20/28、分区 16/24、字重 400/500/600 |
| 密度 | 舒适 16/24 + 48px 行；紧凑 14/20 + 40px 行；移动正文 16/24 | 现有 17/18px 是近期可读性调整，不应无验证退回 v1.0 的 13px；可保留大字偏好 |
| 控件 | 桌面 36px，移动触控 44px；间距 4/8/12/16/24/32 | 筛选紧凑，但不压缩手机命中区 |
| 圆角 | 控件 8、卡片 12、抽屉 16 | 状态和头像才用全圆 |
| 焦点与动效 | 2px 可见焦点、120/180ms；支持 reduced motion | 抽屉可用键盘，自动刷新不夺焦点 |

正文对比度目标 4.5:1、非文本控件 3:1，来自既有设计规范；本轮未测量新组合，不宣称已达标。表格实际密度要在 1440、1024、768、390、320px 和浏览器放大场景验证。

## 7. 实施优先级与验收建议

以下是后续 UI 开发拆分建议，不属于本次文档 PR 的实现范围。每阶段单独评审和发布，保留现有入口作为可回退路径，不重写权限、Agent Loop 或交易状态机。

| 阶段 | 工作包 | 前置条件 | 交付验收 |
|---|---|---|---|
| P0 壳层与可理解性 | 语义 token、分组导航、角色上下文、手机导航、空/错/旧数据状态；首页队列骨架及真实可用数据 | 确认字体与强调色；梳理模块权限；全量计数未具备前明示加载范围 | 七项现有能力入口全部保留；无假数据；手机无页面横溢；刷新返回可恢复位置；无权限状态明确 |
| P1 订单 / 商品 | 桌面表格、详情、SKU 层级、图片管理保留、筛选与分页、操作确认统一；售后高风险确认一并处理 | 租户内查询/总数/稳定排序；订单快照字段；确认每种写动作契约 | 大于100条场景可访问完整范围；列表/详情金额SKU一致；多SKU差价明确；取消/失败不改变业务状态；角色越权仍被后端拒绝 |
| P2 其它模块 | 售后完整详情、画像、调查与审批、策略/审计的统一结构；保存视图与更丰富概览 | 真实业务时限、审计/拒绝原因等字段；权限评审 | 订单—售后—执行记录可追溯；操作留痕；移动端能力边界清楚；筛选与详情往返保留上下文 |

P2 表示模块整体整理靠后，**不把 B02 的售后操作确认等风险项拖到最后**。P0/P1 过程中若发现实际业务缺陷，应按风险单独处理。

建议实施验证集：空数据、接口失败、已有数据刷新失败、100条以上、长订单号、多商品多SKU、金额缺失、未知状态、未绑定商家、各权限角色、状态被他人更新、提交重试、键盘操作、窄屏与大字。涉及运行时代码时按 AGENTS.md 执行相应测试/Eval；本轮只检查文档证据、链接、范围和差异，不把历史 pytest 数字记作本轮测试结果。
