# B 端 2.0 产品决策记录（v0.1）

> 2026-11-13 · 记录主人已确认的 B 端方向，以及“标记支付 / 完成订单”的调研结论。
> 本轮仍不改生产 UI、API、权限或交易状态机。

## 1. 已确认的产品决策

| 问题 | 决策 | 对设计/实现的影响 |
|---|---|---|
| 店主最高频任务 | 查看流水、经营报告 | 首页默认给店主经营概览、流水口径、报告入口；不能用加载条数冒充全店流水 |
| 客服最高频任务 | 和顾客对话 | 需要“客服会话”工作台；当前 B 端只有用户画像，没有完整客服会话模块，需另立后端/实时消息能力 |
| 仓库最高频任务 | 商品数据更新 | 商品/SKU/库存/发货是仓库默认入口；批量更新优先 |
| 默认字号 | 大字 | B 端正文默认 18px；紧凑模式最低 16px，不退回 13/14px |
| B 端强调色 | 灰青，6:3:1 | 60% 中性纸面、30% 灰青文字/边界/次级面、10% 强调色 |
| 一人多店 | 需要 | 必须服务端商家成员关系 + 店铺切换；不能做纯前端假切换 |
| 跨页批量发货 / 改库存 / 导出 | 需要 | 需要批量选择契约、批量 API、权限、审计、异步导出；不能只做前端按钮 |

### 1.1 角色默认入口

```text
店主：经营概览 / 流水 / 经营报告 → 异常待办 → 订单与售后
客服：客服会话 → 订单/售后查询 → 客户画像
仓库：商品 / SKU 库存 → 待发货 → 批量更新
```

### 1.2 6:3:1 灰青用法

```text
60%：纸面、卡片、背景，接近白/浅中性灰
30%：正文、标题、边框、次级面板，使用灰青色阶
10%：主操作、当前导航、关键状态，使用灰青强调色
```

状态色（成功/警告/危险）属于语义信号，不参与装饰性大面积铺色。强调色不能用于整页背景或每张卡片。

### 1.3 已知依赖

```text
店主流水/经营报告：需要真实支付与收入口径；当前没有真实支付通道
客服对话：B 端当前没有客服会话工作台；需要新增后端和实时消息
一人多店：当前账号只绑定一个商家；需要成员/多店关系
批量操作：当前接口以单条操作为主；需要批量契约
```

在依赖没有落地前，不做假入口、假金额、假趋势、假批量按钮。

## 2. “标记支付 / 完成订单”调研结论

### 2.1 真实电商的普遍语义

调研来源（2026-11-13）：

- [Shopify 订单状态](https://help.shopify.com/en/manual/fulfillment/managing-orders/order-status)：`Paid` 可以来自自动/手动捕获，也可以是订单被标记为已支付；另有 Pending、Authorized、Partially paid、Refunded 等支付状态。
- [有赞：什么是标记支付](https://help.youzan.com/displaylist/detail_5_5-1-61721)：标记支付用于线下收银，资金不经过有赞，系统里只是一个收款标签。
- [有赞：线下刷卡/POS 收款](https://help.youzan.com/displaylist/detail_5_5-1-84763)：线下 POS 资金不进入有赞后台，通过标记收款记录。
- [有赞订单结算规则](https://help.youzan.com/displaylist/detail_5_5-2-22606)：发货后买家确认收货或达到自动确认时间，订单才完成结算；现金/标记收款不会进入店铺余额。
- [抖店订单消息](https://op.jinritemai.com/docs/message-docs/30)：货到付款订单在商家确认订单时创建，实际没有支付行为；买家确认收货或系统自动确认收货后，父订单变为已完成。
- [抖店订单状态说明](https://op.jinritemai.com/docs/question-docs/89/187)：订单发货后的正向状态与售后状态是两个维度，不能用一个状态字段表达全部含义。

### 2.2 三个容易混淆的维度

```text
支付状态      UNPAID / PENDING / PAID / PARTIALLY_PAID / REFUNDED
履约状态      UNFULFILLED / SHIPPED / DELIVERED
订单状态      CREATED / PAID / SHIPPED / COMPLETED / CANCELLED
```

真实系统里：

```text
“标记支付” = 记录一笔线下/手动收款，不等于平台收到了在线支付
“完成订单” = 履约完成 + 买家确认收货 / 系统自动确认，不等于商家点一下按钮
```

### 2.3 千客当前现实

当前 B 端：

```text
PATCH /api/b/workbench/orders/{order_id}/status
只接受 PAID / SHIPPED / COMPLETED / CANCELLED
没有支付渠道回调
没有 payment_method / paid_at / completed_at / completion_source
```

前端：

```text
CREATED → “标记已支付”
SHIPPED → “完成订单”
两个动作都直接改状态，没有金额/库存/终态确认
```

因此当前“标记支付”本质是**后台状态推进**，不是收款；当前“完成订单”也没有真实收货依据。文档和研究都不能把它说成真实支付/真实结算。

## 3. 建议的千客语义

### 3.1 先区分环境，而不是先造“真实模式”

在支付通道落地前：

```text
所有订单明确标记为模拟交易
页面显示“演示环境 / 模拟订单”
“标记已支付”改为“模拟支付（演示）”
“完成订单”改为“模拟完成（演示）”
模拟动作记录操作人、时间、前后状态，不产生真实资金
```

不要在演示环境里出现“已支付”却不告诉商家这是模拟。

### 3.2 未来接真实支付后的动作矩阵

| 场景 | 允许动作 | 谁可以操作 | 禁止 |
|---|---|---|---|
| 在线支付成功 | 支付渠道回调写 `PAID` | 系统 | 人工点“标记支付”覆盖 |
| 线下现金/转账/POS | 记录线下收款 | 店主/财务，独立权限 | 客服/仓库代收 |
| 货到付款 | 记录 COD 应收/已收 | 店主/财务 | 当成在线支付 |
| 已发货待收货 | 买家确认收货 / 自动确认 | 买家或系统 | 商家随意点完成 |
| 异常需强制完成 | 强制完成 | 管理员/运营，填写原因 | 普通客服/仓库 |

### 3.3 必须补的字段与事件

```text
payment_method        ONLINE / OFFLINE_CASH / OFFLINE_TRANSFER / COD / DEMO
payment_source        GATEWAY / MANUAL / DEMO
paid_at
completion_source     BUYER_CONFIRM / AUTO_CONFIRM / ADMIN_FORCE / DEMO
completed_at
is_simulated
```

每次状态变化写审计：

```text
操作人、角色、门店、订单号、动作、金额、前后状态、原因、request_id
```

### 3.4 UI 建议

```text
演示环境顶部固定标识；订单卡显示“模拟交易”
“模拟支付”需要二次确认：订单号、金额、后果、演示标记
真实模式“记录线下收款”需要支付方式、金额、凭证/备注、权限
“完成订单”在真实模式默认不出现；只有系统确认/管理员强制完成才出现
完成后展示完成来源，不允许只用本地标签伪装成功
```

## 4. 对 B 2.0 实施顺序的影响

```text
P0：环境标识、字色 token、分组导航、角色默认首页、店铺切换骨架
P1：订单列表/详情、支付语义拆分、完成语义、模拟/真实动作标识
P2：客服会话、真实经营报告、批量发货/库存/导出
```

P0 不实现“真实支付”，也不把模拟支付包装成真实能力。

## 5. 仍需产品确认

1. 近期是否接真实支付通道，还是继续模拟交易？
2. 客服会话是新建 B 端实时会话，还是复用现有 CApp/IM 后端？
3. 一人多店是同一账号多商家，还是多账号切换？
4. 经营报告的“流水”按支付、发货还是完成口径统计？
5. 批量导出是否需要异步任务和文件有效期？
