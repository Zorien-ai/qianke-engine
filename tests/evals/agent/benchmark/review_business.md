## 1. 审查视角与方法

### 1.1 业务身份与判断立场

以「电商运营业务负责人 + 数据分析师 + 客服主管」三重身份审查。一条 benchmark case 的业务价值由三件事决定：

1. **真实运营/客服会不会问**（有决策场景，而非为了考 SQL 语法而造的场景）；
2. **工具动作是否匹配业务动作**（该查库就查库、该查 SOP 就查 SOP、该算比例才算比例；工具不应由“题型分布”倒推）；
3. **标准答案在业务上是否成立**（不只是数学上对，还要口径唯一、结论不是噪声、不会被运营误读）。

### 1.2 六条判定标准（对应用户要求的 6 个问题）

| 编号 | 审查问题 | 本报告的判定方式 |
|---|---|---|
| Q1 | 是否像真实运营/客服/分析师会问的问题，是否过于像考试题 | 是否带决策对象（人群、城市、品类、权益、SOP 场景）；是否只剩“算一个数/排个名” |
| Q2 | `expected_tools` 是否符合业务动作 | 该动作在真实工作中是否**必须**调用该工具；是否有“题干已给数据/已给口径，却强制调用工具”的伪工具题 |
| Q3 | `acceptance` 是否可验收、能否防止编造 | 验收点是否与 evaluator 能力一致（status + expected_tools ⊆ actual + expected_keywords ⊆ final_answer）；负样本是否真的能拦住编造 |
| Q4 | 覆盖是否均衡（SQL 聚合/分组/排序、RAG 口径/权益/SOP、多工具、负样本） | 对照 policy §5 硬分布 + 业务场景矩阵 + 工具组合矩阵 |
| Q5 | 是否换皮重复、过拟合、无意义题、唯一数字但业务价值低 | 与 regression 20 条逐条比对；40 条内部模板聚类；业务价值分级 |
| Q6 | 是否缺少关键业务场景 | 电商运营/客服常问场景清单 × 当前题库覆盖 |

### 1.3 证据与方法（均已执行）

- **逐条阅读** 40 条 case 的 question / expected_tools / expected_keywords / acceptance / difficulty。
- **口径溯源**：阅读 demo 知识库原文 `data/docs/{member_benefits,cs_sop,marketing_playbook,segmentation,tag_definitions}.md`，核对 RAG 预期答案与口径定义；核对 `tag_definitions.md` 的「流失预警 / 高客单 / 高价值」与 `segmentation.md` 的「沉默客 / 流失客」边界是否互洽。
- **独立抽样复算**（只读连 `vec_db`，未写入）：对 22 个关键数值做 SQL 复核，全部与 builder_notes 一致（见 §1.4）。
- **工具契约核对**（只读）：阅读 `runner.py`、`evaluator.py`、`src/rag_demo/agent/loop.py`、`agent/tools/{sql,calculator}.py`、`tools/sql_tool.py`、`db/schema_facts.py`，确认（a）评测判定规则、（b）Agent 系统提示词实际注入了哪些数据事实、（c）execute_sql 的表白名单与 LIMIT 约束。
- **系统提示词实测**：用项目 venv 运行 `rag_demo.db.schema_facts.get_sql_schema()`，确认注入 Agent 的【当前数据库表结构】包含**城市/会员等级/品类/平台的取值及计数、客单价分位、时间口径结论**（下文 H1/H2 的证据）。
- **不在本报告范围**：对 40 条 expected 的完整复算与关键词/工具名合规性（evaluator 职责）；集合边界与泄漏风险（Lead 职责）。本报告只对业务合理性、工具动作、可验收性与覆盖负责，涉及的跨角色问题在 §6.4 列出。

### 2.2 工具组合真实性（multi_tool 12 条的拆解）

| 组合 | 条数 | 具体 | 业务动作真实性 |
|---|---:|---|---|
| rag + sql + calc | 4 | multi_001/002/004/010 | 前 3 条真实，010 的门槛被题干直接给出（见 M5） |
| rag + sql | 1 | multi_003 | ✅ 真实（口径落地 vs 库内现状对比） |
| rag + calc | 4 | multi_005/006/007/008 | ⚠️ **人为构造**：题干给“5 位/3 位”假想人数，真实动作应先查真实人数再算预算 → 反而缺 execute_sql |
| sql + calc | 3 | multi_009/011/012 | ✅ 真实（占比/倍数） |

**关键判断**：4 条 `rag+calc` 是为了“凑齐 12 条多工具”而把 execute_sql 排除掉设计的。真实运营问“生日券预算”一定是“黄金会员 1217 人 × 100 元 = 12.17 万元”，而不是“若 5 位黄金会员”。这类题**既无业务决策价值，又让“工具组合”指标失真**（H5）。

### 2.6 与 regression 的重复度

逐条比对 20 条 regression 语义后：**39/40 条无换皮**，但发现 1 条明显换皮：

- regression `multi_004`：“统计上海用户中**钻石**用户的数量，并计算其占上海用户的比例”（期望 32 / 4.6%）
- benchmark `multi_009`：“统计上海用户中**黄金**会员的数量，并用 calculator 计算其占上海用户的百分比”（期望 114 / 16.6%）

同城市、同维度、同指标、同工具链，只换了一个等级——这正是 policy §3.5「不允许同一条任务在不同集合里换皮重复」禁止的形态（H4）。其余如 sql_001 ↔ regression sql_005（城市计数，但 benchmark 问第三名）、multi_003 ↔ regression rag_004（钻石门槛，但 benchmark 做口径对比）属“同事实不同考法”，可接受。

## 4. 问题清单

### 4.1 高风险（阻塞冻结，builder 必改）

**H1 · 系统提示词已注入答案，3 条 SQL 题的 expected_tools 失效，且会误伤合规 Agent**
- 事实：Agent 系统提示词由 `loop.build_system_prompt()` 注入 `schema_facts.get_sql_schema()`，实测渲染出：
  - `city：北京(722) / 杭州(714) / 南京(694) / 上海(686) / …`
  - `platforms：未标注来源(7277) / 拼多多(959) / 京东(955) / 苏宁易购(952) / 天猫(947) / 1688(943) / 淘宝(937)`
  - `top_category：电子产品(2235) / 家居(1794) / …`
  - 以及 `时间口径…无法回答未来时点问题`、`P25=1326 / P50=2496 / …`
- 影响：`bench_sql_001`（南京 694）、`bench_sql_008`（淘宝 937）、`bench_multi_012`（电子产品 2235）的**答案已在上下文里**。一个依据上下文作答、不调用 SQL 的 Agent 会被判 Tool Selection 失败；一个照抄上下文的 Agent 即使调用 SQL 也没有考察价值。三条题的 measurement validity 都不成立。
- 要求：换成**必须计算才能得到**的题（示例见 §6.2 B1–B3），或在 benchmark 运行配置中关闭 schema facts 的取值分布（Lead 决策，见 §6.4）。不允许“照抄上下文也能过”的题留在 benchmark。

**H2 · 6 条 negative 题的 expected_tools 与“正确业务行为”冲突**
- 事实：`neg_001/002/003/004/005` 强制 `execute_sql`。但 schema 提示词已列出全部表/字段，且明确写了“无时间序列、无法回答未来时点问题”。**一个业务上完全正确的拒答（说明缺什么、不编造）很可能一次工具都不调用**，因此 task_success=false。
- 影响：负样本考的是“会不会先跑一条无意义 SQL”，不是“能不能识别数据不可用”。与 policy §4「负样本用拒答/无数据作为正常完成」的本意相反。
- 要求（二选一，需 Lead/evaluator 与 builder 共同定）：
  - (a) negative 的 `expected_tools` 改为 `[]`（或只保留真正必需的定义检索，如 neg_006 的 rag_search），并在 acceptance 写明“工具调用非强制”；
  - (b) 若坚持要求核验，则题目必须改成“从 schema 看不出结论、必须实际查询才能判断”的形态（当前 6 条都不满足）。

**H3 · 负样本“防止编造”目前不可验收**
- 事实：evaluator 只做 `expected_keywords ⊆ final_answer` 子串判定。neg 的关键词是“无法 + 实体词”，因此“无法精确统计，但按活跃用户推算约 2500 人”这类**先编造再免责**的回答会通过；反之，用“没有/不存在/未提供”正确拒答的回答会失败（builder_notes §9.2 已自认该风险）。
- 影响：6/40 = 15% 的题处于“验收声明 > 实际可验收能力”状态。policy §7 要求业务评审检查“acceptance 是否可验收”，这一条不通过。
- 要求：builder 在 acceptance 中把负样本验收写成**可判定的二值条件**（例如“最终回答不得出现任何具体人数/比例/金额数字；出现即失败”），并由 Lead 决定是否在 evaluator 增加 forbidden-substring 检查或改为人工复核。仅靠 `无法` 关键词不构成验收。

**H4 · 与 regression 换皮：`bench_multi_009` ↔ `regression multi_004`**
- 事实：regression multi_004“统计上海用户中**钻石**用户的数量+占上海比例”；benchmark multi_009“统计上海用户中**黄金**会员的数量+占上海比例”。同城市、同指标、同工具链，只换等级。
- 影响：直接违反 policy §3.5 / §5「不允许同一条任务在不同集合里换皮重复」，也削弱“benchmark 比 regression 更难/更独立”的定位。
- 要求：替换（建议改为“上海各会员等级人数与结构占比”或“北京 vs 上海 会员结构差异”，见 §5），或至少改为不同城市×不同指标的组合，不能只换等级。

**H5 · multi_tool 模板集中 + 内部换皮：4 条 rag+calc 是“假想人数算券”**
- 事实：
  - `multi_006`（黄金生日券 100 × 5 = 500）与 `multi_008`（流失挽回券 100 × 3 = 300）是**同一模板换皮**；
  - `multi_005`（380×2=760）、`multi_007`（48−24=24）也是同一“权益数值 + 四则运算”模板；
  - 4 条都不是真实运营问法：真实预算是“黄金会员 1217 人 × 100 元 = 121,700 元”，不是“若 5 位会员”。
- 影响：12 条 multi 中 4 条（1/3）由同一模板构成，且为凑“rag+calc”组合主动放弃了真实的 execute_sql 动作；这是题库设计层面的过拟合。
- 要求：至少替换 2 条（必改 multi_008；建议再换 multi_005 或 multi_007），改为“真实人数 × 券面额 = 预算”的 rag+sql+calc 三工具链路（示例见 §6.2 B4）。

**H6 · `bench_sql_006` 是“噪声级差异”的伪洞察题**
- 事实：各城市平均年龄 上海 42.58 > 深圳 42.42 > 杭州 42.08 … 重庆 40.90；第一名与第二名差 0.16 岁，而单城平均年龄标准误约 0.52 岁（我复核：SD≈13.5–14.1，n≈640–720）。差异不到 0.2 个标准误，城市间极差也只有 1.68 岁。
- 影响：标准答案会诱导 Agent 输出“上海用户年龄最大”的运营结论，业务上不成立；这是典型的“数学对、业务错”。
- 要求：替换为有区分度的城市指标（如城市人均累计消费：成都 11,984.84 最高 vs 西安 10,222.56 最低，差 17.2%，是真实的资源投放依据），或在 acceptance 强制要求说明差异不显著（且这需要 evaluator 支持，见 M11）。

### 4.2 中风险

**M1 · SQL 题模板集中（10 条里 4 条是“GROUP BY 维度 + ORDER BY 聚合”）**
- `sql_002`（按等级 AVG order_count）与 `sql_010`（按等级 SUM total_amount）同维度同排序模板；`sql_001`（按城市 COUNT 排序）与 `sql_006`（按城市 AVG age 排序）同模板。加上 sql_005（按品类 AVG 排序），10 条里 5 条同一形态。
- 建议：保留最有业务价值的两条（sql_002、sql_010），把 sql_006 换成城市 ARPU（见 H6），并补 HAVING/CTE/分位类业务题（见 §5），避免“只考一种 SQL 模板”。

**M2 · 结论在噪声内的题：sql_005 / sql_006**
- sql_005：运动 1501.62 与服装 1509.43 仅差 0.5%，且 avg_amount 是用户客单价，不能读成“运动品类便宜”。
- sql_006：见 H6。
- 建议：sql_005 保留但 acceptance 必须写明“差异极小、不构成品类定价结论；该指标是偏好该品类的用户客单价，不是品类商品价”；sql_006 直接替换。

**M3 · `multi_001` 的标准答案在业务上是误导性结论**
- 事实：高客单口径（avg_amount≥1000）覆盖 6708/8110 = 82.71%，而全库 AOV 中位数是 2496.24（远高于 1000）——即“高客单”标签几乎覆盖全库，没有分层价值。
- 影响：题目只要求给数量和占比，acceptance 未要求提示标签失效；基准因此把“82.7% 用户是高客单”固定成正确结论，训练/评测出的是“数学正确、业务误导”的行为。
- 建议：acceptance 增加“必须说明该口径已覆盖 82.71%、标签区分度低，并给出 P50=2496.24 作为参照”；或把题目改为按中位数/分位口径统计（P50 已在系统提示词中，注意 H1 式泄漏）。

**M4 · 口径近似被写在题干里（multi_002 / multi_004）**
- 题干直接写“用 days_since_last_buy 近似‘近 30 天未活跃’”“用 days_since_last_buy 对应‘31–90 天无行为’”，等于把分析方法和字段都告诉模型（真实运营提问不会说字段名），同时把“口径近似”这一核心考点降级为“照做”。
- 建议：题干改为“近 30 天未活跃/31–90 天无行为分别有多少人、占比多少”，近似口径与限制写在 acceptance 与 builder_notes，不写进 question。

**M5 · 题干泄答案 / 工具提示（multi_005、multi_010，以及 12 条 multi 全部点名 calculator）**
- `multi_005` 题干“计算双倍积分”直接泄露第一问答案（2 倍）；
- `multi_010` 题干给出“白银会员门槛（2495 元）”，而这道题的 expected_tools 包含 rag_search——检索变成走过场；
- 12/12 multi 题在题干里写“用 calculator 计算/请先查库再计算”。这使 Tool Selection Accuracy 测的是“是否听话”，而不是“是否选对工具”。
- 建议：题干不点名工具、不给出 RAG 事实；工具要求只写在 acceptance。此举不改变 expected 结果，只提升评测效度。

**M6 · 7 条业务价值过低的题**
- sql_004（大盘平均年龄+平均订单数）、calc_001（三件加总）、calc_003（先涨后降）、calc_004（北京占比，数据由题干给出）、multi_005/006/007（假想券预算/减法/口算）。
- 影响：约占 40 条的 17.5%。benchmark 定位是“更难、更独立的阶段评测”，不是计算器回归集。
- 建议：保留 1 条纯计算作 smoke（calc_001 或 calc_004），其余替换为真实场景计算（见 §5）；不阻塞冻结。

**M7 · `sql_002` 的“最高”是近似打平**
- 白银 2.98 vs 黄金 2.90，差 0.08，合并标准误约 0.05（我复核 SD 1.50/1.36，n=2434/1217）→ 约 1.6 个标准误，7 个等级两两比较下不稳健；黑卡 n=3。
- 建议：acceptance 要求同时说明“白银与黄金接近、黑卡样本仅 3 人不可下结论”。

**M8 · 小样本结论：sql_007（黑卡 n=3）、multi_011（黑卡 n=3 算倍数）**
- 两题都已在 acceptance 提示小样本（sql_007 只要求“指出集中分布”，multi_011 要求提示样本不稳定），但关键词无法验收这些附加要求。
- 建议：acceptance 明确“必须出现样本量提示（如‘仅 3 人’）”，并作为人工复核项；或替换为更有业务价值的黑卡题（如黑卡贡献 GMV 占比 146,613.98 / 91,923,627.92 = 0.16%，说明“顶级会员规模极小、需单独服务成本核算”）。

**M9 · “流失预警”与“沉默客/流失客”口径重叠未要求说明**
- `tag_definitions.md`：流失预警 = 近 30 天未活跃 + 客单价>500 + 购买≥3（2616 人）；`segmentation.md`：沉默客 31–90 天（2383 人）、流失客 >90 天（4057 人）。即“流失预警”横跨沉默客与流失客两群，命名与分群体系冲突。
- 影响：multi_002（2616）与 multi_004（2383）两条题放在一起看会像“同一件事两个数”，但都没有要求解释边界。业务评审认为至少应在 acceptance 要求说明这一重叠。
- 建议：multi_002 acceptance 增加“需说明流失预警口径覆盖沉默客+流失客（>30 天未购），与 segmentation 分群命名存在重叠”。

**M10 · `neg_006` 的“允许近似”与“不得编造”边界不清**
- acceptance 允许给近似口径（≈430 人），但关键词只有“90”“无法”。因此：给 430 但没标“近似”也会过；给 430 且标了“近似”也会过；给一个编造数字+“无法精确”也会过。
- 建议：acceptance 写成可判定条件——“必须说明无法精确计算及缺近 90 天窗口/行为日志；若给近似值必须标注假设与口径；不得把近似值表述为官方口径”。接受人工复核。

**M11 · acceptance 中约 11 条“回答须说明…”无法被 evaluator 验收**
- 涉及：sql_002（样本量）、sql_007（集中分布）、sql_008（缺失字段）、multi_001（未要求但应补）、multi_002（近似口径）、multi_003（解释差异）、multi_011（样本不稳定）、neg_006（近似边界）、rag_006（完整流程步骤）。
- 影响：acceptance 文档承诺高于实际判定能力，报告会显示 PASS 但业务要求未达成。
- 建议：在 acceptance 中把这类条款显式标注为“人工复核项（evaluator 不校验）”，由 Lead 决定是否扩展 evaluator（forbidden numbers / required-any-synonyms）。

**M12 · 缺失“知识库无此政策”的客服负样本**
- 现有 6 条负样本全部是“数据库缺表/缺字段/缺时间序列”，没有一条考“知识库没有该政策时不得编造话术”。对客服 Agent 来说，这是最高频也最高风险的编造场景（如用户问知识库不存在的退换/补偿政策）。
- 建议：新增 1–2 条（policy §9 允许追加），见 §5。

### 4.3 低风险

- **L1 · sql_003 格式约束偏严**：要求“精确到分”，运营通常报“9,192.36 万元”。关键词尾 627.92 能把万元表述判错。建议 acceptance 明确“本题为格式测试，必须用元”；或关键词兼容万元写法。
- **L2 · rag_006 关键词偏弱**：5 步 SOP 只用“有效期/工单”两个词，答 2 步即可通过。建议加“升级/续费”等稳定词，或标人工复核。
- **L3 · calc_002 的“某数据集”表述**：输入值 P25=1326.22 / P50=2496.24 与 demo 实测完全一致（已复核），建议题干写明“demo 数据集”，与 dataset 字段一致，避免被理解为虚构数据。
- **L4 · execute_sql 工具契约与 acceptance 示例不一致**：Agent 工具的 `validate_sql` 强制 SQL 带 `LIMIT`，而 sql_003 / sql_004 / multi_001 / multi_004 的 acceptance 复算 SQL 没有 LIMIT。不影响判定（模型会重试），但 acceptance 作为“标准依据”应写成可被 Agent 执行的形态。
- **L5 · difficulty 标注**：easy 16 / medium 19 / hard 5。作为“更难”的 benchmark，easy 占比 40% 偏高；建议复核 easy 里业务价值低的题（见 M6）是否配得上 easy。
- **L6 · 关键词“黄金”“运动”类单实体词偏弱**（sql_005/sql_010）：模型列举全部维度数值时可能顺带命中，导致“结论说错但关键词命中”。建议至少加一个数值或结论词。

## 6. 最终结论与修订要求

### 6.1 最终结论

# 结论：FAIL

**理由（按业务严重度排序）**：

1. **测量效度问题（H1/H2）**：3 条 SQL 题的答案、6 条负样本的拒答依据都已在 Agent 系统提示词中可见；expected_tools 仍强制 SQL，导致“答对但没调工具”被判失败、“照抄上下文”也能过——工具选择指标不可信。
2. **可验收性问题（H3）**：6 条负样本的核心验收点（不得编造）目前机器验收不到，“无法”关键词可被“先编造再免责”绕过。
3. **policy 违规（H4）**：`multi_009` 与 regression `multi_004` 同城市同指标换皮，违反 §3.5。
4. **业务合理性（H5/H6）**：4/12 multi 题是“假想人数算券”的同一模板，其中 multi_006/008 内部换皮；sql_006 的结论是噪声级伪洞察。
5. **业务价值密度（M6）**：约 17.5% 的题属于纯考试/纯口算，与 benchmark“阶段评测、对外汇报”的定位不匹配。

**同时必须承认题库的优点（不建议重写）**：RAG 8 条是本批最扎实的部分（权益/SOP/分群口径都是真实客服问题，关键词也能防错）；`multi_003` 与 `multi_010` 是真正专业的口径落地题；6 条负样本的选题方向正确（缺表/缺字段/口径冲突/不可预测）；数据底座与文档口径自洽（等级门槛与 avg_amount 分布一致），抽查 22 项 expected 全部可复算。**修订应是定点修复（约 6 条改题 + 4 条替换 + 14 条补 acceptance），不是重写整个集合**——符合 policy §7“builder 只修复被指出的问题”。
