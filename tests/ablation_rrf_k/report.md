# RRF 融合参数 k 消融实验报告（纯检索口径）

> 实验日期：2026-10-30 20:17–20:18 · 数据集 `demo` · 测试集 `src/rag_demo/tests/eval_questions.json`（33 题）· 唯一变量：RRF `k`
> 代码默认 `k=60`，实验结束已恢复默认（`summary.json.restored_default_k=60`，脚本 `finally` + 独立进程双重验证）
> 本文件 = `scripts/run_ablation_k.py` 生成的机器表格 + Lead 人工归因分析；原始逐题数据见同目录 `k_*.json`。

## 1. 结论摘要（先给结论）

1. **`k ∈ [30, 100]` 在本测试集上不可区分**：RRF 层聚合指标浮点值完全相同（MRR `0.8985507246`、Recall@5 `97.83%`、召回 100%）；最终上下文层 4 个 k 的逐题来源与顺序 **33/33 题完全相同**。
2. **`k=10` 与其余三档的差异只来自 1 道题**：MGT-01（"本周高价值用户规模"）的期望来源首次命中名次 `#4 → #3`，使 RRF 层 MRR 从 `0.8986 → 0.8949`（Δ=0.0036 = 单题 1/12 ÷ 23 题）；同一题的 Recall@5 在 k=10 反而更高（100% vs 97.83%，因为 k=10 时 `user_profile` 落在第 4 位、k≥30 时落到第 6 位）。**两项差异方向相反、都只有 1 题，不构成显著优劣，也看不到 k 与指标的单调关系。**
3. **k 对"最终喂给 LLM 的上下文"完全没有影响**：`final` 层 33/33 题的来源列表在 4 个 k 下逐题相同 → 宏召回 `97.83%`、微召回 `96.67%`、Recall@5 `97.83%`、MRR `0.7608695652` 四档全等。原因：k 只改 RRF 的名次权重，候选进入精排后由 reranker + 分池 Top-K（画像 3 / 文档每路 3）重新决定顺序与取舍，**融合顺序差异被下游精排吸收**。
4. **架构结论（严谨版）**：k=60 位于 `[30,100]` 的平稳平台，没有换值的理由，也没有换值的收益 → **保留默认 60 是低风险、可辩护的工程决策**。但必须诚实地说明：本实验**不能证明"60 是全局最优"**，只能证明它"不劣于 30/100、优于 10 没有证据"；33 题 / 23 道有期望来源 / RRF 层召回已到 100% 天花板，统计功效不足以区分 30 与 60 的细微差别。
5. **Pass Rate：不适用（—）**。本实验按"纯检索口径"运行：不调多路规划的 LLM、不生成回答、不跑 LLM-as-a-Judge，因此不存在通过率。JSON 中 `pass_rate` 字段为 `null` 并注明原因，**未伪造任何分数**；反过来这也保证了测试集与 Judge Prompt 在 4 个 k 下绝对一致（裁判侧从未被读取/调用）。

## 2. 实验设计（控制变量）

| 维度 | 取值 |
| :--- | :--- |
| 测试集 | `src/rag_demo/tests/eval_questions.json`，33 题；其中 **23 题**有 `expect_sources`（共 **30 个**期望来源），参与召回/MRR；其余 10 题（负样本/纯 SQL/闲聊）不计入 |
| 数据集 | `demo`（评测基线库，`user_profile_vectors=8110` / `wiki_vectors=36` / `search_index=8146`） |
| 检索配置 | 向量 top-20 + BM25 top-20（`config.KEYWORD_RETRIEVER=bm25`）→ RRF |
| 唯一变量 | `k ∈ {10, 30, 60, 100}`，通过 `hybrid_retriever.set_rrf_k(k)` 在进程内切换，结束恢复默认 60 |
| 检索式 | 每条题固定单路「直接检索」（不做 LLM 多路改写）→ 4 个 k 的输入检索式完全相同，差异只可能来自 k |
| 大模型 | **不调用**（无规划 / 无生成 / 无裁判）；CPU 推理（本机 GPU 被常驻服务占用，且 CPU 更利于复现） |
| 运行方式 | `uv run python scripts/run_ablation_k.py --ks 10,30,60,100`（本次等价命令见 §6） |

两层指标（口径复用 `rag_demo.eval_utils`，与 `run_eval.py` 同一套判定函数）：

- **RRF 融合层（layer=rrf）**：`hybrid_search(q)` 的 top-30 候选（k 直接作用的一层）。
- **最终上下文层（layer=final）**：`search_variants([(direct, q)])` 走完「分池取舍 + reranker 精排 + 去重」后的最终候选（等价于 `ENABLE_MULTI_QUERY=False` 的真实检索路径）。
- **Source Recall** = 期望来源命中数 / 期望数（宏=题均值，微=总命中/总期望）。
- **MRR** = 首个命中的期望来源 `1/名次` 的题均值；未命中记 0（不能剔除，否则"排到 30 名外"不扣分会虚高）。
- **Recall@5** = 期望来源落在前 5 位的比例。

### 3.3 逐题差异（只有 1 道题变了）

| 题号 | 期望来源 | k=10 | k=30 | k=60 | k=100 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| MGT-01 | user_profile、tag_definitions.md | RRF 首命中 **#4**、Recall@5 命中 2/2 | **#3**、Recall@5 1/2 | #3、1/2 | #3、1/2 |
| 其余 22 题 | — | 四档首命中名次完全相同 | 同左 | 同左 | 同左 |

排序稳定性（全 33 题、RRF 层 top-30 顺序）：

- k=10 与 k=30/60/100：仅 **19/33** 题顺序完全一致（14 题顺序变化）；
- k=30 与 k=60：**22/33** 一致；k=30 与 k=100：21/33；k=60 与 k=100：**26/33**（k 越接近，顺序越接近）；
- 但**期望来源的首次命中名次**在 k≥30 三档间 100% 相同，仅在 k=10 与其余档之间差 1 题 → 名次变化主要发生在与期望来源无关的候选上（画像候选之间的相对顺序），不影响来源命中。

最终上下文层：**4 个 k 两两对比，33/33 题的来源列表逐题完全相同**（含顺序），因此该层所有指标四档全等。

### 3.4 未满分项与 k 无关

最终上下文层唯一未打满的来源召回来自 **MD-01**："用户分群有哪几种，各自该怎么运营"（期望 `segmentation.md` + `marketing_playbook.md`）。4 个 k 下最终候选都是 `['user_profile', 'segmentation.md']`，`marketing_playbook.md` 均未被精排保留（reranker 相关度阈值/名额所限）——这是精排/名额问题，不是 RRF k 问题。

## 4. 为什么最终上下文层对 k 不敏感（机制解释）

RRF 只决定「哪些候选进入 top-30 候选池、以什么顺序进入」。进入 `search_variants` 之后：

1. 画像池把所有候选**合并后统一精排**取全局 Top-3（顺序无关，reranker 重新打分）；
2. 文档池按每条检索式**各自精排**取 Top-3 上限（还含相关度阈值过滤 + 父块回填）；
3. 两池合并去重，**不再按 RRF 名次二次竞争**。

因此只要期望来源在 top-30 候选池里（本测试集 RRF 召回 100%），k 改的只是"进池顺序"，对最终上下文没有影响。**这次实验实际上验证了：在当前"RRF top-30 → 精排 → 分池 Top-K"的架构里，RRF 的 k 是一个低敏感参数。** 如果去掉 reranker（纯 RRF 排序直接进上下文），k 对 MRR 的影响才会变成用户可见的差异。

## 5. 统计效力与限制（必须一起读）

1. **样本小**：23 道有期望来源的题 / 30 个期望来源。单题变化就会带来约 0.0036 的 MRR 波动，不足以支撑"k=60 最优"这类强结论。
2. **指标天花板**：RRF 层宏召回已 100%，无法区分"召回质量"；MRR 对 60→30 几乎饱和（两者聚合值完全相等）。
3. **纯检索口径**：未跑 LLM 裁判，因此没有 Pass Rate / 答案质量维度；本实验只回答"检索候选排序/命中"问题。
4. **检索式固定为单路直接检索**（无 LLM 多路改写）：绝对指标会低于全链路基线，但 4 个 k 的输入完全一致，横向比较仍然有效。
5. **设备**：CPU fp32 embedding（与 GPU fp16 有微小数值差），对同一进程内 k 的横向对比无影响；耗时不代表生产环境。
6. **k=10 的 RRF 层耗时受冷启动污染**（首轮缓存未热），不可引用为"k=10 更慢"。
