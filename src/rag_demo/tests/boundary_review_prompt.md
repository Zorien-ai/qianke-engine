# 边界问题集 · 专用评审提示词

> **用途**：评审 `eval_boundary_questions.json`（20 条：CPLX-01~09 + ODD-01~11）。
> **为什么单独写一套**：上一轮用通用三维模板（可答性 / HF 有用性 / 独立性）评这套题，
> 其中两个维度口径错位，8 条"设计使然"的探针被打了低分，差点被误删。
> 本提示词是针对**边界能力探针集**重写的，维度与判废规则都换过。
>
> **用法**：把「二、数据集上下文」+ 待评单题 JSON 一起贴给模型，按「七、输出格式」收结果。
> 全部评完后，再跑一次「六、整套一致性检查」。

---

## 一、先读这段：这套题评的是什么

这套题**不是**"难题库"，是**边界探针集**。评审对象不是"业务难度"，而是三件事：

1. **探针准不准** —— 这道题能不能真的压到它声称要压的那个机制上？
2. **失败看不看得见** —— 系统答错时，评审者能不能从输出里识别出来？
3. **期望行为定不定** —— "答对"的标准是否唯一、可判定？

由此推出三条硬规则，违反即评审无效：

- **规则 A**：`expected_outcome` 为 `partial` 或 `refuse` 的题，**可答性低是设计意图，不是缺陷**。
  这类题问的是"答不出来的时候行为对不对"，用可答性给它们打低分等于把探针全删了。
  `expected_outcome=full` 的题若可答性低，那才是题目有问题。
- **规则 B**：`severity=高` 的含义是"**会静默给出错误答案**"，不是"答不出来"。
  答不出来是可见的、可接受的；静默答错才危险。不要把"系统拒答"计为高严重度失败。
- **规则 C**：**禁止以"系统答不出"为由提议删题**。删题只允许基于
  「探针压不到机制」或「失败信号不可观测」或「与主集既有题完全重复」。

## 二、数据集上下文（每次评审必须附带）

### 2.1 字段契约

| 字段 | 含义 | 评审时怎么用 |
|---|---|---|
| `expected_outcome` | `full` 有唯一正确答案 / `partial` 只能近似且必须声明口径 / `refuse` 本该拒绝或引导 | **决定可答性低分是否算缺陷**（规则 A） |
| `probe` | 这道题压什么机制，含代码落点 | 维度 D1 的核对依据 |
| `fail_signal` | 失败长什么样 | 维度 D2 的核对依据 |
| `severity` | 高 = 会静默给错答案；中 = 答不出但可见 | 决定要不要优先修，不决定题目去留 |
| `must_include_sources` | 要答对必须进上下文的文档 | 核对 `acceptance` 是否自洽 |
| `expect_certain` | `false` 表示期望行为本身是产品决策，未定 | 这类题只输出产品决策建议，不打分 |

## 三、评分维度（5 个，替代原来的三维）

**可答性不再作为评分维度**，只在输出里作为记录字段，且必须与 `expected_outcome` 联合解读。
**HF 生态有用性维度已废弃**——本题集是电商画像系统的边界集，该维度无区分力。

### D1 探针命中度（1-5）

| 分 | 标准 |
|---|---|
| 5 | 直击机制，且从问题本身无法绕开该机制 |
| 4 | 能压到，但存在一条不触发该机制的替代路径 |
| 3 | 机制相关但只是间接暴露 |
| 2 | 机制存在，但本题基本压不到 |
| 1 | `probe` 声称的机制在代码里不存在，或与题目无关 |

> 打 1-2 分必须指出代码里哪一行对不上。

### D2 失败可观测性（1-5）

| 分 | 标准 |
|---|---|
| 5 | 系统答错时，输出与答对时形态明显不同，一眼可辨 |
| 3 | 能看出异常，但需要比对 `sources` / `sql` / `rows_count` 才能确认 |
| 1 | 失败与成功长得一样，评审者无法从输出区分 |

> 这是**最容易致命**的维度：压得很准但失败看不出来的题，实际是废题。

### D3 期望行为确定性（1-5）

| 分 | 标准 |
|---|---|
| 5 | `acceptance` 无歧义，标准答案唯一 |
| 3 | 大致可判，但边界情形需要讨论 |
| 1 | 不先做产品决策就无法判定对错 |

> `expect_certain=false` 的题（ODD-06 / ODD-09）按定义落在 1-2 分，
> 且**不得因此建议删题**——应输出产品决策建议。

### D4 自足性（1-5，带豁免）

脱离系统上下文能否读懂"在问什么"。

**豁免清单**（这些题考的就是依赖本身，低分属设计使然，不得建议删改）：
`ODD-01`（无效输入）、`ODD-03`（无上下文指代）、`ODD-07`（引用"以上指令"）、
`ODD-11`（问系统自身）、`ODD-06` / `ODD-09`（显式引用内部字段名）、
`CPLX-02` / `CPLX-04`（依赖内部标签口径）。

### D5 覆盖面增量（1-5）

| 分 | 标准 |
|---|---|
| 5 | 主集 33 题完全没有的新机制 |
| 3 | 主集有相邻题，但压力点不同 |
| 1 | 与主集某题实质重复 |

> 打 1 分必须指名重复了哪道题（如 `SEC-01` / `TM-01` / `MQ-01` / `CH-01` 等）。

## 四、反模式清单（上一轮真实踩过，逐条禁止）

1. **用可答性筛题** —— 见规则 A。`partial`/`refuse` 题的可答性低是卖点。
2. **用 HF 有用性筛题** —— 该维度对本题集无效，已废弃。
3. **把"依赖系统内部资产"当缺陷** —— 边界集不引用内部资产就没法测边界，见 D4 豁免清单。
4. **把"系统拒答"当失败** —— `refuse` 题的正确答案就是拒答。
5. **因为 `fail_signal` 没写清楚就说题不好** —— 应先要求补 `fail_signal`，而不是删题。
6. **rewrite `probe` 的事实内容** —— 除非能指出代码里对应位置有误，否则不得改动机制描述。
7. **建议删题但不说该机制由谁覆盖** —— 删题必须补一句"此机制已由 X 覆盖"或"无替代"。

## 五、单题评审提示词（可直接复制）

```text
你是 RAG 系统评测集的评审员，现在评审**边界能力探针集**里的一道题。
请严格遵守下面的规则，它们是这套题的特殊约定，与通用题库不同。

【这套题评的是什么】
评的不是业务难度，而是三件事：探针准不准（D1）、失败看不看得见（D2）、
期望行为定不定（D3）。另有两个辅助维度：自足性（D4）、覆盖面增量（D5）。

【硬规则】
A. expected_outcome 为 partial 或 refuse 时，可答性低是设计意图，不是缺陷。
   expected_outcome=full 时可答性低才是题目有问题。
B. severity=高 的含义是「会静默给出错误答案」，不是「答不出来」。
   系统拒答不算失败。
C. 禁止以「系统答不出」为由提议删题。
D. D4 自足性有豁免清单：ODD-01/03/07/11、ODD-06/09、CPLX-02/04
   考的就是依赖本身，低分属设计使然。

【被评题目】
{单题 JSON}

【机制索引（核对 D1 用，不必通读仓库）】
{第二节 2.2 的机制索引表}

【主集已覆盖范围（核对 D5 用）】
{第二节 2.3 的清单}

【评审要求】
1. 逐维度打 1-5 分并给出一句话理由；理由必须引用题目字段或代码落点，不许空泛。
2. 记录可答性（1-5），但不得单独据此下任何结论。
3. 检查题面是否有隐藏缺陷：隐性前指、前提预设、歧义、可被一句话绕开。
   上一轮就漏了「客单价这么高」这种隐性前指。
4. 给出建议：保留 / 修订 / 删除。
   - 修订必须给出改后的题面。
   - 删除必须满足 D1<=2 或 D2<=2 或 D5=1，并说明该机制由哪道题覆盖。
5. 若 expect_certain=false，不要打分，改为输出「产品决策建议」：
   列出可选行为与各自代价，给出你的倾向与理由。

【输出格式】
严格输出下面这个 JSON，不要有任何额外文字：

{
  "id": "...",
  "D1": {"score": 0, "reason": "..."},
  "D2": {"score": 0, "reason": "..."},
  "D3": {"score": 0, "reason": "..."},
  "D4": {"score": 0, "reason": "..."},
  "D5": {"score": 0, "reason": "..."},
  "answerability_recorded": 0,
  "hidden_defects": ["..."],
  "verdict": "保留 | 修订 | 删除",
  "revised_question": "（仅修订时需要）",
  "delete_justification": "（仅删除时需要，含机制由谁覆盖）",
  "product_decision_advice": "（仅 expect_certain=false 时需要）"
}
```

## 六、整套一致性检查提示词（20 条全评完后跑一次）

```text
下面是一套边界探针集（20 条）的逐题评审结果 JSON 数组。
请做交叉一致性检查，只报告问题，不要重新打分：

1. 维度间自相矛盾：例如 D1=5（探针精准）却建议删除，或 D2=1（失败不可观测）
   却建议保留。列出所有这类矛盾。
2. 违反硬规则：有没有题因「系统答不出」被建议删除？有没有 partial/refuse 题
   因可答性低被扣分？有没有命中 D4 豁免清单却被建议改题面？
3. 机制重复：不同题是否压到了同一个机制？若是，指出哪几条该合并。
4. 覆盖空洞：这套题声称要测的机制里，有没有哪一条实际上没有题在测？
5. 期望未定清单：汇总所有 expect_certain=false 的题，列出待产品决策的点。

输出：问题列表，每条含「题 ID + 问题类型 + 具体矛盾 + 建议动作」。
没有问题的项也要明确说「无」。
```

## 七、输出与归档

- 单题结果收成 JSON 数组，文件名建议 `boundary_review_<日期>.json`，放 `tests/` 下。
- 汇总表建议列：`题目ID, D1, D2, D3, D4, D5, 可答性(记录), 隐藏缺陷, 建议, 修订后题面`。
- **不要再用上一轮那种「可答性 / HF 有用性 / 独立性」三维 CSV**——那套口径对本题集无效。
- 评审结论只有两种落地方式：改 `eval_boundary_questions.json`，或改被测系统。
  纯粹的"分数"不留档。

## 八、这套提示词自身的已知局限

1. **机制索引是人工整理的**，可能滞后于代码。评审时若发现某条落点已变，
   请一并反馈——那说明索引需要更新，而不是题目需要改。
2. **D2 失败可观测性依赖评审者对系统输出的熟悉程度**。若评审者没见过
   `sources` / `sql` / `rows_count` / `trace` 这些字段长什么样，容易高估可观测性。
3. **本提示词没有覆盖"该测但还没想到的边界"**。它只能评审已有题目，
   不能替代"还能测什么"的开放性思考——那一项建议人肉做。
