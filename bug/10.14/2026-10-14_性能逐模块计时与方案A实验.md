# 性能逐模块计时分析 & 方案 A（合并 Text2SQL）实验

**日期**：2026-10-14
**目的**：先测量再决定优化方向，避免又一次「按代码结构猜瓶颈」
**结论**：**本地计算优化空间约 0.5s/题（1.5%）；耗时由服务端吞吐支配，方案 A 实测不可行**

---

## 一、测量方法

用 monkey patch 对**每个函数**单独计时（不侵入生产代码），跑 6 道题覆盖不同路径：

| 题目 | 类型 | 走 SQL |
|---|---|---|
| `OPT-05` | 对比 | ✅ |
| `DA-04` | 统计 | ✅ |
| `MGT-01` | 规模 | ✅ |
| `CS-01` | 纯 RAG·SOP | ❌ |
| `OPT-03` | 纯 RAG·定义 | ❌ |
| `DA-02` | 纯 RAG·策略 | ❌ |

打点位置：`vector_search` / `bm25_search` / `rrf_fusion` / `rerank` /
`_expand_to_full_doc` / `plan_queries` / `text2sql` / `execute_sql` /
`build_context` / `generate_stream`，并记录每次 LLM 调用的输入输出字符数。

> **预热必须用真实业务问题**。第一版预热用了「预热一下」四个字，被判成闲聊直接返回，
> 根本没走到检索与精排，于是模型加载开销落到第一道真题上，
> 表现为「CrossEncoder 峰值 17.4s」「向量召回峰值 12.6s」这种假峰值。

## 四、三个关键发现

### ① 每次 LLM 调用有 2~3s 的固定开销

「多路规划」平均 3.84s，而它**只输出 40 个字**：

| 轮次 | 耗时 | 输入 | 输出 |
|---|---|---|---|
| #3 | 3.58s | 1512 | 69 字 |
| #6 | 2.66s | 1507 | 39 字 |
| #12 | 2.64s | 1509 | 25 字 |

**25 个字用掉 2.64s** —— 时间不在生成上，在连接 + prefill + 服务端排队。

**推论**：每减少一次调用，理论上可省这 2~3s 固定成本。

### ② 服务端吞吐波动 11~14 倍 —— 耗时不确定的主因

| 调用 | 输出 | 耗时 | 速度 |
|---|---|---|---|
| `OPT-05` Text2SQL | 501 字 | 17.76s | 28.2 字/s |
| `DA-04` Text2SQL | 469 字 | **6.11s** | **76.8 字/s** |
| `MGT-01` Text2SQL | 118 字 | 1.58s | 74.7 字/s |

**输出量只差 7%，耗时差 2.9 倍。** 全局速度范围 5.5 ~ 76.8 字/s。

**这意味着**：任何"缩短输出 / 精简 prompt"的优化，收益都会被这个波动淹没。
改完测一次看着变快了，很可能只是抽到了快的那次。

### ③ 调用次数由路径决定

| 路径 | LLM 调用次数 | 实测平均 |
|---|---|---|
| 纯 RAG | **2 次**（多路规划 + 答案生成） | 25.1s |
| SQL | **3 次**（+ Text2SQL） | 34.5s |

**纯 RAG 已经是最少的 2 次，没有压缩空间。**

## 五、方案 A 实验：把 Text2SQL 并入多路规划

### 设计

| 组 | 做法 | 往返次数 |
|---|---|---|
| 现状 | `MULTI_QUERY_PROMPT` + `TEXT2SQL_PROMPT` | 2 次 |
| 方案 A | 在规划 prompt 末尾追加「顺手输出 SQL」的要求 | **1 次** |

不修改生产代码，用原型 prompt 对比。**每题每方案跑 5 轮取中位数**——
这是必须的，因为发现 ② 已经证明单次测量不可信。

### 结果：方案 A 更慢，且更不稳

**`OPT-05`（SQL 题）**

| | 中位 | 5 轮分布 |
|---|---|---|
| 现状 | **9.84s** | [8.1, 9.8, **47.1**, 17.6, 8.0] |
| 方案 A | **20.39s** | [23.1, 30.5, **2.9**, 20.4, 16.4] |

**中位差 -10.56s（方案 A 慢一倍）**。

**`CS-01`（纯 RAG 题）**：现状 2.93s vs 方案 A 2.67s（±0.27s，无差异）
—— 说明追加的 SQL 要求没有干扰纯 RAG 题的判定。

### 质量：没有变差，但也没有变好

| 指标 | 现状 | 方案 A |
|---|---|---|
| SQL 判定准确率 | 5/5 | 5/5 |
| 产出 SQL | — | 5/5 |
| 通过校验并执行成功 | — | **5/5** |

### 为什么反而更慢？——诊断结果推翻了原假设

原本假设「合并后模型输出复杂 SQL，decode 变慢」。逐次记录输出后，假设**不成立**：

| 轮次 | 输出总长 | SQL 字符 | SQL 行数 | CTE/UNION | 耗时 |
|---|---|---|---|---|---|
| #3 | 352 | 228 | **1** | False | **2.89s** |
| #1 | 399 | 318 | 1 | False | 23.09s |
| #2 | **306** | 220 | 1 | False | **30.49s** |
| #4 | 455 | 368 | 1 | False | 20.39s |
| #5 | 380 | 296 | 1 | False | 16.42s |

- prompt 里「禁止 CTE / UNION / 嵌套」的要求**生效了**（所有 SQL 都是 1 行）
- 输出量与耗时**完全无关**：#2 输出最短（306 字）却最慢（30.49s），
  #3 输出更长（352 字）却只要 2.89s

现状那组同样如此：`#3` 的 Text2SQL 用 **44.03s**（输出 684 字），`#5` 输出 406 字只花 4.72s。

**结论：耗时由服务端吞吐决定，与我们的输出长度、prompt 复杂度、SQL 复杂度都没有稳定关系。**

方案 A 更慢的可能原因（推测，未进一步验证）：合并后 prompt 从约 1500 字涨到约 2400 字
（追加 schema + 要求），单次调用的 prefill 成本上升，而**省下的那次往返本来就只有 2~3s**——
两相抵消后净收益为负，再叠上服务端波动，结果就是更慢。

## 六、结论

### 1. 本地计算没有优化空间

0.5s / 题（1.5%）。**明确不要做**：检索并发化、精排换模型、SQL 建索引、RRF 优化。

### 2. 方案 A 不可行（已用数据否决）

- 耗时中位反而 **+10.56s**
- 波动更大（2.9 ~ 30.5s，对比现状的 8.1 ~ 47.1s 分布同样很差，但中位更低）
- 质量无提升
- **记录为「已证伪」，不要再尝试**

### 3. 真正的问题不是「优化」，是「度量」

服务端吞吐波动 11~14 倍，**当前没有任何可复现的基线**。
在这个前提下：
- 改任何东西跑一次评测，都分不清是改进还是抽到了快的那次
- 连「哪个方案更快」都无法判断

**建议先做度量基线**：固定一组题目，同一配置连跑 3 轮取中位数并记录分布。
**否则后续所有优化都无法验证。**

### 4. 唯一确定有效的仍是缓存

同一问题第二次问直接命中，跳过全部 LLM 调用（0 秒）。
对「反复试同一批问题」的 demo 场景，这是唯一 100% 确定的手段。

### 5. Prompt 长度对耗时的影响无法忽略

虽然单次调用的耗时波动掩盖了一切，但方案 A 的实验侧面提示：
**prompt 从 1500 字涨到 2400 字，可能带来可观的 prefill 成本**。
台账 P4（SQL 汇总重复注入完整 schema，约 500 字）因此**值得重估**——
此前认为「微不足道」，但按本次数据，500 字的 prompt 增量未必小。
**待单独测量后再下结论。**

---

## 七、遗留

1. **建立可复现的耗时基线**（最高优先级，见结论 3）
2. **重估 P4**（schema 无条件注入）——本次数据提示 prompt 长度的影响可能被低估
3. **`Text2SQL` 的第二次往返是否有别的合并方式**——方案 A 已证伪，但可以试
   「只让规划输出 SQL 骨架 / 用更小的模型单独跑 Text2SQL」等方向
4. **服务端耗时波动本身**：是否与请求时间、并发量相关？
   若能用 `stream=True` 测 TTFT 并记录，可区分「排队」与「生成慢」——
   本次未做（非流式调用拿不到 TTFT）
