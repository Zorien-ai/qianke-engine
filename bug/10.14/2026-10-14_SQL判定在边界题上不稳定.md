# SQL 判定在边界题上不稳定（temperature=0 挡不住）

**日期**：2026-10-14
**发现场景**：用 `tools/profile_pipeline.py` 测耗时，同一道题两轮跑出**不同结果**
**严重度**：🟡 中 —— 同一问题耗时差一倍（28.77s vs 60.39s），答案内容也不同

---

## 现象

测 `OPT-05`（「高客单用户和普通用户的偏好差异」）耗时，脚本连跑两轮（同一 prompt、`temperature=0`）：

| 轮次 | `need_sql` | 总耗时 | 答案长度 |
|---|---|---|---|
| 第 1 轮 | **False** | 28.77s | 768 字 |
| 第 2 轮 | **True** | **60.39s** | 931 字 |

**同一道题、同一份代码、同一个 prompt，判定结果不同，耗时差了一倍多。**

这不只是性能问题——它意味着**评测基线本身是不稳的**：优化耗时前如果连「优化的是哪条路径」都不确定，数字就没有可比性。

---

## 探针

`_probe_stability.py`：直接打印模型原始输出的判定行，绕开所有解析逻辑。

**改动前**（每题 5 次不带 seed + 5 次带 `seed=42`）：

| 题目 | `路由` | `SQL` | `策略` |
|---|---|---|---|
| `OPT-05` 高客单 vs 普通用户偏好差异 | 10/10 rag ✅ | **4×需要 / 1×不需要 / 5×需要** | 稳定 |
| `MGT-01` 本周高价值用户规模有多少 | 10/10 rag ✅ | 10/10 需要 ✅ | 稳定 |
| `CS-01` 用户投诉物流延迟怎么回复 | 10/10 rag ✅ | 10/10 不需要 ✅ | **5×none / 5×关键词** |

三点结论：

1. **`路由` 从不漂移** —— 二分类判据（闲聊 vs 业务）足够清晰
2. **`SQL` 只在「边界题」上漂** —— `OPT-05` 漂，`MGT-01` 不漂
3. **`seed=42` 完全无效** —— 加了 seed 照样漂（s#5 仍判成「不需要」）

---

## 根因

### 第一层：`temperature=0` 不等于确定性输出（改不了）

这是常见误解。`temperature=0` 只表示「采样时取概率最高的 token」，
但服务端仍有非确定性来源：

- **DeepSeek 是 MoE 架构** —— token 路由到哪个专家子网络，会受**同批次其他请求**影响，而 batch 组成每次不同
- GPU 浮点运算的累加顺序不固定
- 服务端缓存命中与否可能走不同计算路径

`seed` 参数只在服务端**真正实现**它时才有效。实测无效，说明 DeepSeek 不保证这一点。
**这一层是外部约束，代码层面无法消除。**

### 第二层：prompt 对「两群对比」的判据太笼统（本次修复）

`OPT-05` 的问题本来就在边界上：

> 「高客单用户和普通用户的**偏好差异**」
>
> - 读成「**统计**两组人的品类分布然后对比」→ 需要 SQL
> - 读成「**描述**两组人分别是什么特征」→ 画像检索就够

而 `MULTI_QUERY_PROMPT` 里对这条的说明只有四个字：

```text
- 需要：要的是「数量 / 排名 / 分布 / 占比 / 平均 / 最高最低 / 两群对比」这类结果，
       必须查结构化数据才算得出来。例：「有多少美妆用户」「哪个城市的人最多」
```

**「两群对比」太笼统**，且两个例子都是**明确的量化问法**（「有多少」「哪个最多」），
没有覆盖「差异」这种模糊措辞——模型在边界上摇摆是合理的。

**对照组 `MGT-01`**：「本周高价值用户**规模有多少**」——`规模`、`多少` 把意图钉死了，
所以 10/10 稳定。**漂移是问题措辞的模糊性放大的，不全怪模型。**

---

## 修复

细判据、补反例（`src/rag_demo/prompts.py` → `MULTI_QUERY_PROMPT` 第二步）：

```text
- 需要（**「两群对比」怎么算**）：问题在比较两个群体的特征分布，也就是问
       「A 和 B 有什么差异 / 区别 / 不同 / 谁多谁少」。
       即使句子里没有「多少」两个字，只要比的是两群人的数据，就算需要。
       例：「高客单用户和普通用户的偏好差异」「北京和上海的用户谁多」
- 不需要：业务知识、标签定义、流程规范、策略方案等，靠资料检索就能回答。
       **注意区分**：问某个标签「是什么 / 怎么定义」、某项权益「有哪些」，
       那是在查定义，不是在比数据。
       例：「钻石会员有什么权益」「流失预警怎么判定」→ 不需要
```

**刻意没有采用的方案**：把「拿不准」的默认方向改成「需要」。
代价不对称看着支持这么做（漏判 SQL → 答案缺数字；误判 SQL → 多花 20s），
但那等于**用时间换效果**，与当前「优化耗时」的目标直接冲突。
本次只做「把判据说清楚」，**不改变整体判定倾向**。

**代码兜底方案也考虑了但没做**：加 `looks_comparative()` 规则（命中「差异/对比」就强制开 SQL）。
放弃原因：容易误伤——「钻石会员和非钻石会员的权益有什么区别」命中规则，但它其实是查定义。

## 局限性

### 1. 没解决服务端非确定性，只是收窄了暴露面

本层修复的本质是**把边界题的判据写得更明确**，让模型「少有机会摇摆」。
但边界不会消失——总会有新的、措辞模糊的问题落在灰区。

### 2. 只验证了 1 个漂移样本

`OPT-05` 是本次唯一发现的漂移案例（因为是它暴露的）。是否还有其他会漂的题，
**没有系统性排查**——正确做法是拿评测集 20 题各跑 10 次统计稳定率，本次未做。

### 3. `策略` 字段的漂移未处理

`CS-01` 在 `none` / `关键词` 之间 5:5 漂（多一路检索）。本次只修了 `SQL` 判定，
`策略` 的波动还在。影响较小（多走一路检索约 +0.2s），但性质相同。

### 4. `seed` 无效是供应商行为，需持续观察

如果后续换成支持确定性推理的服务端（或有 `logit_bias` 等更强约束），这条可以再评估。

### 5. 漂移的代价不对称，值得单独定策略

| 判错方向 | 后果 |
|---|---|
| 漏判 SQL（该走没走） | 答案**缺数字** → 效果损失 |
| 误判 SQL（不该走走了） | 多花约 20s → 时间损失 |

本次选择「只收窄、不转向」。若后续确认「效果优先于耗时」，可把「拿不准」的默认方向改成「需要」——
但那会让平均耗时上涨，**属于产品决策，不是 bug 修复**。

## 顺带记录的测量结论

本次为查这个问题重写了 `tools/profile_pipeline.py`（原版用的是已废弃的 `build_query_variants`，
且**完全没有 SQL 路的计时**）。当前链路的实测分布（`OPT-05` 第 2 轮）：

| 环节 | 耗时 | 占比 |
|---|---|---|
| 答案生成（LLM） | 31.42s | 52.0% |
| **Text2SQL（LLM）** | **20.85s** | **34.5%** |
| 多路规划（LLM） | 7.45s | 12.3% |
| 检索（3 路） | 0.45s | 0.8% |
| 精排 + 全文扩展 | 0.16s | 0.3% |
| SQL 执行（DB） | 0.06s | 0.1% |
| **合计** | **60.39s** | |

**LLM 调用占 98.9%，本地计算只占 1.1%。**

→ **优化检索 / 精排 / 融合 / SQL 执行毫无意义**（合计 0.67s）。
  与台账 P1「性能问题必须先测量再下结论」是同一条教训。

→ `Text2SQL` 花 20.85s 是最大可优化项：它生成的 SQL 常达 50+ 行、5 个 CTE、
  以 `UNION ALL` 拼多类指标——**输出 token 数是主因**。
  潜在方向：并入多路规划那次调用（省一次往返）、或在 prompt 里限制 SQL 复杂度。
  **均需单独验证效果不降，不在本次范围。**
