# 数据库故障被伪装成「资料里没有」

**日期**：2026-10-14
**发现场景**：改完 prompt 跑评测，结果 `自动判定通过 0/20`、`来源命中 0`
**严重度**：🔴 高 —— 系统故障被报告成知识库缺失，**排查方向会被带偏**

---

## 现象

改完 `MULTI_QUERY_PROMPT`（细化 SQL 判定）后跑 `run_eval --tag v14`：

```
成功执行: 20/20
自动判定通过: 0/20
RAG 路由: 20 条 | 来源命中 0 | 期望文档命中 0
平均耗时: 14.47s
```

**所有题的 `actual_sources` 都是 `[]`、`answer` 都是同一句**：

```json
{
  "answer": "根据现有资料无法确定。",
  "sources_count": 0,
  "actual_sources": []
}
```

---

## 误判风险（本条最重要）

第一反应是「**prompt 改动导致回退了**」——因为改动内容恰好就是 SQL 判定逻辑。

**差点就去改 prompt、回滚提示词了。** 实际情况是：**PostgreSQL 没在运行**。

两个因素合起来制造了这个假象：

**① 出错日志被命令自己吞掉**

跑命令时习惯性加了 `2>$null`（为了压掉模型加载的进度条）。
但 `logging` 默认输出到 **stderr**，于是所有「检索失败」警告一起被丢掉了。

```powershell
uv run python ... 2>$null      # ← 进度条没了，错误也没了
```

去掉这个重定向，一行就说明问题：

```
psycopg2.OperationalError: connection to server at "localhost" (::1),
port 5432 failed: Connection refused (0x0000274D/10061)
```

> **教训**：「让输出清爽」的写法，在排查问题时是**负资产**。

**② 系统把「连不上」和「没资料」报成了同一句话**

这是代码问题，比上一条严重。见下节。

---

## 根因

`retrieval/query_processor.py::search_variants`：

```python
for strategy, text in variants:
    try:
        hits = hybrid_search(...)
    except Exception as e:
        logger.warning("策略「%s」检索失败，跳过: %s", strategy, e)
        continue            # ← 逐路跳过
    ...
if not result_lists:
    return []               # ← 全部失败也返回空列表
```

`except` 逐路跳过的设计**本身是对的**——某一路挂了不该拖垮其他路。问题在于
**没有区分「部分失败」和「全部失败」**：

```
PG 连不上 → 每路都抛异常 → 全被 continue 吃掉 → result_lists 为空
          → candidates 为空
          → generator.generate() 看到「没有 candidates」→ 「根据现有资料无法确定。」
```

三种情况被压成了两种输出：

| 实际情况 | 应该告诉用户 | 实际输出 |
|---|---|---|
| 某一路失败，其他路有结果 | 正常回答 | ✅ 正常回答 |
| **全部路失败（基础设施故障）** | **服务不可用** | ❌ **「根据现有资料无法确定」** |
| 全部路成功但都没命中 | 资料里没有 | ✅ 「根据现有资料无法确定」 |

后两种在生产环境下**完全无法区分**。对排查的破坏性极大：
故障被报告成业务结论，人会去翻知识库、调检索参数、换 embedding 模型——
**全都在错误的战场上**。

---

## 修复

**① 新增异常类型**（`query_processor.py`）

```python
class RetrievalUnavailableError(RuntimeError):
    """检索基础设施不可用（数据库连不上、索引表缺失等），与「检索无命中」严格区分"""
```

**② 全路失败时抛出，而不是返回空**（`search_variants`）

```python
if not result_lists:
    # 全部路都抛异常 -> 检索不可用；全部路都无命中 -> 正常的空结果
    if trace_out and len(trace_out) == len(variants) and all(v.get("error") for v in trace_out):
        raise RetrievalUnavailableError(
            f"全部 {len(variants)} 路检索均失败：{trace_out[0].get('error')}"
        )
    return []
```

**③ 新增独立文案与 route**（`prompts.py` / `pipeline.py`）

```python
ROUTE_ERROR = "error"   # 既不是 rag，也不是 chitchat，而是基础设施故障

RETRIEVAL_UNAVAILABLE_REPLY = (
    "检索服务暂时不可用（数据库连接失败），这次没能取到任何资料，请稍后重试。\n\n"
    "若持续出现，请检查 PostgreSQL 是否在运行。"
)
```

**④ `pipeline` 捕获并区分**（`answer_question` / `prepare` 两条路都改）

**⑤ API 层处理 `error` 路由**：直接告知，**不写缓存**
（否则数据库恢复后，缓存里那条错误还会继续返回）

**⑥ 顺带对齐**：`generator._build_sources` 的 `text` 截断从 100 字改为 400 字，
与 `pipeline.prepare` 保持一致——同一个字段在两条路径上长度不同，很容易被当成 bug。

---

## 验证

用 `mock.patch` 让 `get_conn` 抛异常模拟数据库故障（不真去停库）：

| 场景 | `route` | 输出 |
|---|---|---|
| 数据库正常 | `rag` | 来源 4 条，正常回答 ✅ |
| **数据库连不上** | **`error`** | 「检索服务暂时不可用（数据库连接失败）…请检查 PostgreSQL 是否在运行」✅ |

日志链也变得可读：

```
策略「直接检索」检索失败，跳过: ... Connection refused
策略「关键词扩写」检索失败，跳过: ... Connection refused
检索不可用: 全部 2 路检索均失败：... Connection refused        ← 新增
```

**评测回归**（`gpu_v14`，数据库恢复后）：20/20 执行成功、自动判定 17/20、来源命中 17、
文档命中 13、平均 28.57s —— **与 `gpu_v13` 完全一致，无回退**。

## 局限性

### 1. 只覆盖了「全部路失败」

若**部分路失败但恰好返回了无关结果**，仍会正常回答——这种情况无法自动识别
（系统不知道「本该有 3 路，实际只有 1 路成功」是否影响质量）。
`trace` 里记录了每路的 `error` 字段，但目前只展示、不做判定。

### 2. 其它基础设施故障未纳入

只处理了检索侧（`hybrid_search` 抛异常）。以下情况仍会静默降级或抛未捕获异常：

- **LLM 服务不可用**：`plan_queries` 已有 `except`，会「退化为单路检索」——
  这是**有意的降级**（保证还能答），但用户无法从回答里看出「这次没做多路规划」
- **精排模型加载失败**：未处理
- **`search_index` 表为空**（未跑构建脚本）：不报错，表现为「检索无命中」——
  **仍属于本 bug 的同一类伪装**，未修

### 3. `route="error"` 是新值，下游需适配

- 前端 `app.js` 的徽章样式只定义了 `.badge.rag` / `.badge.sql`，`error` 无样式
- 评测脚本按 `rag` / `chitchat` 分支统计，`error` 目前会被算进 rag（本次未发生）

### 4. 根本解是「启动自检」

本次是**运行中发现**的。更彻底的做法：API 启动时（`lifespan`）探一次数据库，
连不上就**拒绝启动**或持续告警——让「带病运行」不可能发生。
本次未做，记录在案。
