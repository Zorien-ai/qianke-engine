# 规划调用拆分实验 & SQL 段精简

**日期**：2026-10-14
**前置**：同日完成「关闭思考模式」（评测 28.57s → 6.30s，质量零损失），见台账 P9。
下面两个实验都在**关思考**的前提下进行——否则任何耗时结论都会被思考长度波动淹没。

---

## 实验一：把 `plan_queries` 拆成「只判断」+「只改写」

### 动机

`plan_queries` 一次 LLM 调用同时做三件事（路由复核 / SQL 判定 / 变体改写）。
如果拆成两次调用——第一次只判断（输出策略名）、第二次只改写——会不会更快？

「公平对比」的前提：**两边都用 LLM 改写**，差别只在调用结构（1 次 vs 2 次），
不引入规则改写，否则质量基线就不同了。

### 设计

| | 调用 1 | 调用 2 | 合计 |
|---|---|---|---|
| A 现状 | 判断 + 改写（合并） | — | **1 次** |
| B 拆分 | 只判断（禁输出改写内容） | 按选中策略改写 | **2 次** |

B 组调用 2 只针对**被选中的策略**生成，不是五路全跑。

### 结果：拆分更慢，明确否决

| 题目 | A 现状（中位） | B 拆分（中位） | 差 |
|---|---|---|---|
| `OPT-05` | **0.78s** | 1.74s | **-0.96s** |
| `OPT-03` | **0.75s** | 1.64s | **-0.88s** |

SQL 判定准确率两组均 **5/5**。

拆分的两段是两次独立调用（判断 0.87s + 改写 0.87s），**固定开销叠加**；
而合并调用并没有因为「任务更复杂」而变慢——**关思考后模型不纠结**，
任务复杂度对耗时的影响远小于调用次数。

### ⭐ 本实验真正的收获

**关思考后，`plan_queries` 只要 0.78s**（开思考时是 3.84s，**快 5 倍**）。

也就是说「query 问题处理」模块现在只占单题 6.3s 里的 **12%**。
在这个基数上，拆不拆分都是零头——**实验一的价值不在方案本身，而在于证实了
该模块已不再是瓶颈**。

## 实验二：SQL 段精简（去 SQL 原文 + rows 截断）

### 动机

逐模块计时发现：`OPT-05` 的 context 3146 字里，**SQL 段占 1503 字（48%）**，
比全部检索资料（1296 字）加起来还大。

两处浪费：
1. **SQL 原文**——模型需要的是「结果」，不需要知道「查询怎么写」（它又不改 SQL）
2. **结果行未处理**——一格可能是整段文本或十几个字段

> 顺带验证过「去重原问题」：每条资料的溯源里都重复写了一遍原问题，
> 但 5 条合计只有 40~60 字（**占 context 1.9~2.6%**），**不值得做**。
> 正文之间也完全无重复（20 字片段重复率 0.0%）。

### 实现（全部带开关，便于回退）

`config.py`：

```python
CONTEXT_INCLUDE_SQL_TEXT = False   # 是否把 SQL 原文放进 context
SQL_ROWS_MAX = 20                  # 最多送多少行
SQL_CELL_MAX_CHARS = 40            # 单元格最长字符
```

`generator.build_context()`：单元格逐个截断、行数限流、SQL 原文可选。

### 结果：有效，但比预期小

| 题目 | 旧 context | 新 context | 减少 |
|---|---|---|---|
| `OPT-05` | 2638 字 | 2253 字 | **-14.6%** |
| `MGT-01` | 1329 字 | 1199 字 | **-9.8%** |
| `DA-04` | 1051 字 | **625 字** | **-40.5%** |

省下的主要是 **SQL 原文**（`OPT-05` 384 字 / `MGT-01` 129 字 / `DA-04` 425 字）。
`rows` 截断本次基本没触发——这些样本的单元格本来就短，属**防御性开关**。

**之前估的 -43% 偏乐观**：那是我按「SQL 原文 500~800 字」估的，实测只有 129~425 字。

精简后的 SQL 段：

```
[结构化查询结果]
（共 14 行，下列 14 行）
普通用户 | 美妆 | 287 | 579.88 | 1102.61 | 1.73
普通用户 | 服装 | 270 | 601.28 | 1187.46 | 1.81
```

### 评测回归（`gpu_v16`）

| 指标 | `gpu_v15` | **`gpu_v16`** |
|---|---|---|
| 自动判定通过 | 17/20 | **17/20** |
| 来源命中 / 文档命中 | 17 / 13 | **17 / 13** |
| 分板块 | 5/6, 5/5, 4/4, 2/2, 1/3 | **完全相同** |
| 平均耗时 | 6.30s | **6.01s（-4.6%）** |

**质量零损失；耗时略有改善，但在波动范围内（关思考后波动约 7%），
不能算作确定收益。**

## 结论汇总

| 实验 | 结论 | 处置 |
|---|---|---|
| 一：拆分 `plan_queries` | **更慢 0.9s，明确否决** | 维持合并调用（1 次） |
| 二：SQL 段精简 | **context -10~40%，质量零损失** | 已采用，开关可回退 |

### 两件事值得单独记

**1. 关思考把「值得优化的东西」重新排序了**

实验一在开思考时的意义是「省 0.9s / 3.84s = 23%」；
关思考后变成「省 0.9s / 0.78s」，但**基数已经小到不值得动**。
同一份代码，优化价值可以因为一个上游参数而彻底改变。

**2. context 长度不是当前的瓶颈**

SQL 段砍掉 40%，总耗时只降 4.6%（且不排除波动）。
关思考后生成耗时约 5s，其中 prefill 占比很小，
**输出长度（decode）才是主导**——这与逐模块计时的结论一致。

**所以下一步若还要压耗时，方向只有两个**：

- 换更快的模型 / 服务（收益未知，需评估质量）
- 缩短**答案输出**（会损质量，需产品决策）

**不建议再动 context 和本地计算。**
