### 2. M1 整体冻结到 `prototype/m1_mock/`

**原因**：`mvp/app.py` 的原设计是「M2 把本文件里的 mock 实现换成真实实现，前端一行不用改」
（见其模块注释）。也就是说 M2 第一天就会改到**真人测试环境正在跑的那份文件**——
测试者会看到页面在自己眼皮底下变化，出了问题也分不清是「新代码的 bug」还是「正在改的中间态」。

**冻结程度**：不止前端。整个目录**不 import `rag_demo` 的任何模块**，连切分器都复制了一份
（`split_estimate.py`）。理由：只要还 import 一次 `rag_demo.*`，M2 重构那个模块时
（改签名、换依赖、甚至只是 import 期间抛错）就能把 8001 打挂——「独立」必须连依赖一起独立。

**启动**（URL 与端口不变，只是命令多了 `--app-dir`）：

```bash
uv run uvicorn m1_mock.app:app --port 8001 --app-dir prototype
```

**验证**（23 项断言，临时脚本已删）：

- 子进程 `import m1_mock.app` 后，`sys.modules` 里**没有** `rag_demo*`、**没有** `torch`
- 静态三件套与 `src/rag_demo/mvp/static/` **逐字节一致**（测试者看到的页面不变）
- 真实起服务后四步流程全通：`/` → `/api/mvp/sample` → `analyze`（识别字段 + 预估分块）→
  `build`（5 步跑到 100%）→ `query`（命中答案库且带引用来源；未命中的走兜底话术）

**遗留（需一次重启）**：8001 上仍挂着一个 **19:14 启动的旧进程**
（`uvicorn rag_demo.mvp.app:app --host 0.0.0.0 --port 8001`），跑的是冻结前的代码。
它与快照**行为一致**（本轮只改了 docstring，没动逻辑），所以链接不会断；
但它的代码来源是被 M2 接管的 `src/rag_demo/mvp/`，重启一次即锚定到快照。

### 踩坑：同端口双进程同时监听

验证时 `POST /api/mvp/build` 成功、紧接着 `GET /api/mvp/build/{id}` 却 404，
排查过程值得记一笔：

- Windows 下 `SO_REUSEADDR` 的语义与 Unix 不同，**已有一个进程监听 `0.0.0.0:8001` 时，
  另一个进程还能成功绑定 `127.0.0.1:8001`**，且 uvicorn 不报错；
- 于是新连接被**随机分流**到两个进程：`POST` 落到 A（任务存在 A 的内存字典里），
  `GET` 落到 B（查不到 → 404）。表现像「偶发 404」，实际是两个进程在抢同一个端口。
- 教训：验证脚本必须**先确认能独占端口**，并**校验身份**（这里用「新进程的
  `build_tasks` 必须是 0」）——否则测的根本不是自己起的那个服务。

## 五、M2 第一步已落地：真上传 + 真解析

| | M1（已废弃） | 现在 |
|---|---|---|
| 谁解析文件 | 浏览器：JS 解码、按 `\n` 数行、数逗号数列 | 服务端：multipart 落盘 → 统一 UTF-8 → pandas 真读 |
| 行数 | 估的，页面只能写「约」 | 真值（字段里带引号换行的记录不再被多算） |
| 编码 | 前后端各写一套判断，且只服务展示 | **落盘即转 UTF-8**——这正是 `ingest_data.load_transactions` 一直假定、但之前没人真正实现的契约 |
| 状态存放 | 进程内字典，服务一重启上传的东西就没了 | 磁盘 `data/uploads/<批次号>/`，重启后仍在 |
| 每步总量 | 前端报上来的（可伪造、也不该它统计） | 构建时按落盘文件真算（清洗 N 行 / 切分 M 块） |

两个设计决定：

- **示例数据也走真流程**：不再返回一份编造的文件清单，而是把仓库自带的 6 个平台 CSV
  与规则文档复制进上传目录，走与真人上传完全相同的路径。否则示例只能证明「界面能点」，
  证明不了「数据能进」——而后者才是 M4 拿真实数据时要面对的。
- **旁挂 `_meta.json` 记录原始编码**：落盘时已统一成 UTF-8，原始编码这个信息会丢，
  但它是用户最关心的（「我用不用自己转」），所以单独记一份给界面用。

验证 46 项（临时脚本已删）。其中一条是**发现并修掉自己的 bug**：
`decode_bytes` 抛错没有按文件兜住，导致「一个空文件让整批上传失败，且只报这一个文件名，
其余文件静默消失」——正是那种「用户以为传上去了、其实没有」的失败。
现在空文件/坏编码/不支持的后缀都只跳过自己，同批其他文件照常入库。

仍未真实的部分：第 3 步构建（进度是模拟的）、第 4 步查询（答案是内置样例）。
两者是下一步的工作，接口形状已经按真实实现设计好（`upload_id` + 落盘文件）。
