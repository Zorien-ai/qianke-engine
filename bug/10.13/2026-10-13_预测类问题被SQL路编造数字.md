# 预测类问题被 SQL 路编造数字（别名伪造结论）

**日期**：2026-10-13
**发现场景**：路由改二分类、SQL 并入多路聚合后的首次回归（`gpu_v13`），边界负样本 `EDGE-02`
**严重度**：🔴 高 —— 输出一个**看起来有来源、实际无依据**的具体数字，比直接答不出更危险

---

## 现象

评测集边界题 `EDGE-02`（负样本，期望「说明无法预测，只能做历史检索」）回答为：

```
预测明年 GMV 约 91,923,627.92 元，约 9,192.36 万元。 [来源6：结构化查询结果]

这个数是结构化查询直接给出的，SQL 别名就是 `predicted_next_year_gmv`。 [来源6]
- “按元、约 9192 万”是推断：资料没写币种和单位。
- 资料也没写“明年”具体是哪一年、预测模型、数据范围……
对外汇报建议写：**预测明年 GMV 约 9,192.36 万元；口径：`user_profile_vectors.total_amount` 汇总，预测口径待确认。**
```

**带具体数字、带来源标记、还给了对外汇报话术**。`gpu_v12` 该题只是 `passed=None`（未走 SQL），
`v13` 变成 `sql=有 rows=1`，说明是本次改造新引入的行为。

题目本身的答案在**数据层就不存在**，逐层看：

| 层 | 事实 | 能否支撑预测 |
|---|---|---|
| `total_amount` | 「用户**累计**总消费」——到快照日为止的个人历史总和，是一笔**存量** | ❌ 拿存量冒充「明年 GMV」（期间流量），口径就错 |
| 时间维度 | 全表**无任何时间字段**；`days_since_last_buy` 以 2024-12-30 为**单一快照日** | ❌ 没有序列可外推 |
| 表形态 | `user_profile_vectors` 8110 行 = 8110 个用户的状态切片，非订单明细 | ❌ 没有可增长/可归期的粒度 |
| SQL 能力 | `SUM / AVG / COUNT` 只能**重述历史** | ❌ 数学上产不出未来值 |

---

## 诊断

实际生成的 SQL：

```sql
SELECT ROUND(SUM(total_amount), 2) AS predicted_next_year_gmv
FROM user_profile_vectors
LIMIT 50
```

**这条 SQL 里没有任何预测**：就是把历史 `total_amount` 全量求和，
再把**输出列的别名**起名为 `predicted_next_year_gmv`。
没有增长率、没有年份维度、没有时间序列、没有任何外推公式；
`LIMIT 50` 挂在聚合函数上还完全无效（`SUM` 只返回一行，纯模板凑数）。

---

## 根因

**幻觉藏在「别名」里**，并且被下游当成了证据。三层传导：

| 环节 | 行为 | 单看是否撒谎 |
|---|---|---|
| 生成层（Text2SQL） | 无法预测 → 用 `SUM()` 冒充，把「预测」塞进 `AS predicted_next_year_gmv` | 否，只是起了个列名 |
| 回答层（SQL 总结） | 读到列名是 `predicted_*` → 当成预测结果汇报 | 否，只是照读列名 |
| **合起来** | **产出一个凭空数字，并挂上「来源6：结构化查询结果」** | ✅ **这才是问题** |

这比普通幻觉更该防：**普通幻觉是编内容，这个是编「语义标签」，而下游把标签当成了证据。**

那句「预测口径待确认」正是破绽——真有口径的话，SQL 里就该出现 `GROUP BY` 时间
或增长率计算。它自己给出了矛盾信号（"口径待确认"却报出了精确到分的数字），
但这个矛盾没有被任何一层拦住。

**为什么本次改造才暴露**：改造前 SQL 是路由选项，边界/预测类问题大多落 RAG 或不触发 SQL；
改造后 SQL 变成多路里的一路，**由多路规划的 LLM 决定是否开启**，而该判定只写了
正向条件（「数量 / 排名 / 分布 …」），**没有负向排除项**，于是预测类问题也被放进来了。

---

## 影响

对 8110 行的 Demo 库，表现为「多报了一个数」；换到真实业务场景，这类输出最危险的地方在于：

1. **有来源标记** —— 「[来源6：结构化查询结果]」让数字看起来经过查证
2. **有对外话术** —— 直接给出「对外汇报建议写：预测明年 GMV 约 9,192.36 万元」
3. **有口径描述** —— 「`total_amount` 汇总」听起来专业，读者很难发现它根本不是预测

即：**错误结论被包装成了可直接引用的成果**。决策场景下，这比「答不出」的危害高得多。

---

## 修复

三处提示词改动（`src/rag_demo/prompts.py`），**入口 + 兜底 + 最后一道**：

**① 入口防线（最有效）—— `MULTI_QUERY_PROMPT` 第二步加负向排除**

```text
- 不需要（**必须写不需要**）：预测 / 推演 / 假设 / 未来时点类问题，
       如「明年 GMV 多少」「下季度会怎样」「如果能…会如何」。
       库里只有 2024-12-30 的单时点静态画像快照，**没有时间序列**，
       SUM / AVG / COUNT 只能重述历史，算不出未来值。
       这种情况下 SQL 只会给出一个看起来像结论、实际没做过任何预测的数字。
```

**不让 SQL 路开起来，就没有编数字的机会**——问题会退回 RAG 路，走「资料不支持」的拒答路径。

**② 兜底 —— `TEXT2SQL_PROMPT` 加第 9 条**（防判定漏掉时生成器硬凑）

```text
9. 库里只有 2024-12-30 的**单时点静态快照**，没有时间序列表。
   预测 / 推演 / 明年 / 下季度等**未来时点**问题，SQL 无法回答：
   不要用 SUM / AVG 冒充，也不要起 predicted_* / forecast_* 这类
   **暗示结论的输出别名**（别名会被下游当成结论引用）。
   这种情况输出 `SELECT '数据不支持预测：库内无时间序列' AS message LIMIT 1`
```

**③ 最后一道 —— `SQL_SUMMARY_PROMPT` 加第 6、7 条**（回答层）

```text
6. **列别名不等于方法说明**：SQL 里写了 AS predicted_xxx / forecast_xxx，
   不代表它真的做了预测。要回看这条 SQL 有没有外推逻辑（增长率、时间序列、
   预测模型）——没有的话就直说「这条查询只是汇总了历史数据，不是预测」，
   不要照搬别名当成结论汇报
7. 结果里出现「数据不支持预测」这类说明性文本时，照实转述并说明原因，
   不要围绕它编数字
```

**为什么提示词要改三处而不是一处**：① 管住入口，③ 管住万一。② 是中间的软约束，
三层各自独立失效时才轮到下一层——单点修改不足以关闭这条路径。

### ④ 代码层硬拦截 —— `retrieval/query_processor.py`

上面三处全是**软约束**：没有一行代码校验「SQL 是否真的做了预测」，
LLM 漏一次就复现一次。故补一道机制性防线，与既有的「路由复核」并列：

```python
FUTURE_TIME_MARKERS = ("明年", "后年", "下一年", "次年",
                       "下个月", "下个季度", "下季度", "下一季度", "未来", "将来")
PREDICTIVE_ACTION_MARKERS = ("预测", "预估", "预计", "推算", "推演", "展望",
                             "会增长", "会减少", "会下降", "会达到", "会突破", "会变成")
_COUNTERFACTUAL_RE = re.compile(
    r"如果.{0,30}?(多少|金额|GMV|占比|比例|数量|人数|涨|降|增|减|达到|变化)")

def looks_predictive(question: str) -> bool:
    ...

# plan_queries() 返回前复核
if need_sql and looks_predictive(question):
    logger.info("SQL 判定复核：问题属预测类，关闭 SQL 路 -> %s", question)
    need_sql = False
```

**误伤控制的关键在那个 `and`**：拦截条件是 `need_sql AND 命中规则`，不是单看规则。

| 样本 | 规则命中 | LLM 判定 | 最终 | 说明 |
|---|---|---|---|---|
| 明年会员等级会不会调整 | ✅ 命中「明年」 | `need_sql=False` | 不拦 | 业务知识类，本来就不开 SQL |
| 高价值用户有多少人 | ❌ 不命中 | `need_sql=True` | 保留 | 正向统计题，SQL 路不受影响 |

即它只否决「**既要算数 + 又是未来时点**」这个交集 —— 而这恰好就是 SQL 必然答不好的那批。

**为什么放在 `query_processor` 而不是 `pipeline`**：`need_sql` 在本模块是唯一出口
（`plan_queries` 产出 → `multi_query_search` → `pipeline` / `api` 消费），
改这一处即覆盖所有调用方，且与已有的「路由复核」语义一致（都是对 LLM 判定的硬复核）。

**为什么不放在 `sql_tool`**：SQL 生成阶段才拦意味着**已经付过一次 LLM 调用成本**，
不如在入口就掐掉；且那里拿不到「这个问题本就不该走 SQL」的判断依据。

**反事实正则不要求出现「会」字**：中文里「**会**员」「优惠」都含「会」，
早期写法 `如果.{0,30}?(会|能)…` 会让「如果用户是钻石会员有什么权益」命中，
故改为直接匹配量化词。

## 局限性

这一节必须写清楚，因为**本次修复并未在机制上根除该问题**：

### 1. 代码防线也只是关键词匹配

④ 解决了「纯靠提示词」的问题，但**规则本身仍是关键词枚举**：
措辞绕开这些词就无法命中，例如：

- 「三年后能到多少」——没有「明年 / 后年 / 未来」等词表内的时点词
- 「照这个势头下去会怎样」——没有动作词，也构不成 `如果…多少` 的反事实句式
- 「按当前速度何时破亿」——量词是「亿」，不在量化词表内

另外 `MARKERS` 常量需要人工维护：新增一种预测式问法必须有人回来补词，
**没有任何「自动发现新问法」的机制**。

`temperature=0` 只保证同一输入稳定，**不保证 LLM 守规矩** ——
不过现在 LLM 失手时，代码防线能接住**已覆盖的那批**。

### 2. ② 的哨兵返回值依赖下游「看懂」

`SELECT '数据不支持预测：库内无时间序列' AS message LIMIT 1` 会**正常通过**
`validate_sql`（SELECT 开头 + 带 LIMIT + 无禁用词），正常执行并返回一行文本。
也就是说它对系统而言是一条**合法查询**，只是语义上是「拒答声明」。
这行文本能否被正确转述，完全取决于 ③ 是否生效——**②③ 是同一条链上的软约束**。

### 3. 无法覆盖「非预测但有同类结构」的问题

本次只针对**未来时点**加了排除项。但同类模式还可能出现在别处，例如：

- 「如果不发券 GMV 会少多少」——反事实推演
- 「这批用户值多少钱」——价值估算（库里有 `total_amount`，容易被直接 SUM 出来）
- 「照现在的趋势多久能攒够 100 万」——趋势外推

这些都没有被这次的排除项明确覆盖，**属于已知的同类风险敞口**。

### 4. 「预测」的语义边界本身模糊

`MULTI_QUERY_PROMPT` 要求 LLM 判断「是不是预测/未来时点」，这类判断天然有灰区。
例如「明年续费率目标定多少合适」——既像预测又像业务咨询。
灰区样本的表现是**不可预期的**，本次未构造评测样本覆盖。

### 5. 评测集只有 1 条相关负样本

`EDGE-02` 是唯一一条预测类负样本。修复后它是否能稳定拒答，
**单条样本的通过不足以证明该类问题已修复**——可能只是这一条被指令正巧命中。
要真正验证，需要补一组预测/推演类负样本（含上面第 3 点列出的几种变体）。

### 6. 治本方向（本轮已按 ④ 实施，但仍有缺口）

原先设想的规则拦截按 ④ 落地了（位置从 `pipeline` 下沉到 `query_processor`，
理由见修复章节）。但**误伤评估是一次性的**：本次靠 10 条手工样本判断，
没有纳入 `run_eval.py` 的常规回归 —— 后续若有人改动 `MARKERS`，
不会有测试自动告诉他误伤了哪类问题。

**另一个尚未闭合的点**：这层防线只在 `ENABLE_MULTI_QUERY=True` 时存在 ——
`need_sql` 本来就是多路规划那次 LLM 调用的产物，关掉开关就没有 SQL 路、
也就无所谓拦截。这个依赖关系是固有的，不是缺陷，但值得记明。

## 验证

### 第一轮：提示词三处（①②③）

| 问题 | `sql` | 回答 |
|---|---|---|
| 预测一下明年的GMV（原题 `EDGE-02`） | 无 | 「用现有资料，不能可靠预测明年GMV。硬给数字就是编。」 |
| 下个季度用户会增长多少 | 无 | 「现有资料算不出来」+ 列出所需数据 |
| 高价值用户有多少人（正向对照） | **有** `rows=1` | SQL 路未受影响，模型还主动指出了口径差异 |

### 第二轮：代码层 ④

**规则函数本身**（不调 LLM，纯判定）：

| 类别 | 样本数 | 结果 |
|---|---|---|
| 应命中（预测 / 未来时点 / 反事实） | 7 | **7/7** ✅ |
| 不应命中（统计类、业务知识类） | 10 | 8/10，2 例假阳性 |

两例假阳性：「明年会员等级会不会调整」（命中「明年」）、「预计活动什么时候上线」（命中「预计」）。
二者均为业务知识类，LLM 本就判 `need_sql=False`，故实际不触发拦截。

**净效果测试（真跑 `plan_queries`）——这里发现 ④ 当时根本没被触发：**

```
[LOG] 多路规划: … | SQL=不需要      ← 日志里没有「SQL 判定复核」这一行
```

即这几题 **LLM 自己就判了 `need_sql=False`**（说明提示词 ① 已生效），
代码防线**一次都没轮到出场**。也就是说这一轮**并没有验证到 ④**。

**注入式验证**（猴补丁 `_parse_response` 制造 LLM 误判，让防线必须出场）：

```python
qp._parse_response = lambda text: ("rag", True, [])   # 一律判「需要 SQL」
```

| 问题 | 期望 | 结果 |
|---|---|---|
| 预测一下明年的GMV | 拦回 | `need_sql=False` ✅ |
| 如果不发券GMV会少多少 | 拦回 | `need_sql=False` ✅ |
| 下个季度用户会增长多少 | 拦回 | `need_sql=False` ✅ |
| 预计明年有多少新用户 | 拦回 | `need_sql=False` ✅ |
| 高价值用户有多少人 | 放行 | `need_sql=True` ✅ |
| 有多少美妆用户 | 放行 | `need_sql=True` ✅ |
| 哪个城市的人最多 | 放行 | `need_sql=True` ✅ |

**0 失败**：LLM 全判错时，规则仍能把预测类按回去，统计类照常放行。

> **方法论备注**：这是「第一道防线太有效、导致第二道防线无法被自然验证」的典型情况。
> 只跑真实链路就宣布 ④ 生效，等于把「LLM 判对了」误当成「规则拦住了」——
> 两者的输出完全一样，差别只在有没有那条日志。**必须用注入式验证才覆盖得到。**

## 遗留

1. **补预测类负样本**（见局限性 3、5）——当前只有 `EDGE-02` 一条，覆盖不足。
2. ~~评估规则拦截方案~~ → 已按 ④ 实施（提示词 + 代码双层）。
3. **`MARKERS` 缺回归保护**（见局限性 1、6）——规则靠手工维护，
   建议在 `run_eval.py` 里加一组「规则判定」用例：纯函数、不需要 LLM、秒级完成，
   让后续改动 `MARKERS` 时误伤能被自动发现。
4. **同类风险排查**：`SQL_SUMMARY_PROMPT` 目前只点名了 `predicted_* / forecast_*`，
   是否需要扩展成「任何带结论色彩的别名」需要再观察实际生成样例。
5. **`SQL_SCHEMA` 缺「高价值用户」口径**（本次验证时顺带发现）——
   Text2SQL 会把它映射成 `avg_amount >= 1000`（高客单口径），
   与 wiki 里的定义（近 90 天前 20% + 近 30 天活跃）不一致。
   本次模型自己纠正了，但这是运气不是机制。
