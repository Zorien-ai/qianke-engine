# 代码架构评估

**结论：当前结构能跑通 Demo，但有 4 个「埋雷级」问题和若干「产品化前的债」。** 现在不修没关系，但要知道雷在哪。

---

## 一、🔴 埋雷级问题（迟早会炸）

### 1. 数据库连接管理有 bug

`hybrid_retriever.py` 里：

```python
def get_conn():
    global _conn
    if _conn is None or _conn.closed:
        _conn = psycopg2.connect(**DB_CONFIG)
    return _conn
```

**问题**：psycopg2 在**服务端 kill 连接后，客户端 `_conn.closed` 仍为 0**。你之前就踩过——`pg_terminate_backend` 之后，Python Console 拿到死连接，执行 SQL 报 `Software caused connection abort`。

**后果**：服务长时间运行，DB 重启或连接被回收后，`/qa` 会永久卡死，必须重启服务才能恢复。

**正确做法**：每次取连接时 `SELECT 1` 探活，失败则重连。

---

### 2. 全局状态在多 worker / reload 下会崩

现在 `_model`、`_conn`、`_bm25`、`_reranker` 都是**模块级全局**。这在单进程 Demo 下能跑，但：

- **`uvicorn --workers 4`**：每个 worker 各加载一份 bge-m3 + reranker（各 2GB），**8GB 内存直接爆**
- **`--reload`**：改代码后 reloader 会重启主进程，但**子进程残留**，有时出现「文件改了但行为没变」
- **测试**：无法 mock，无法并行跑

**正确做法**：模型实例通过 FastAPI 的 `lifespan` 事件在进程启动时加载一次，通过 `app.state` 传递，而不是模块级全局。

---

### 3. BM25 语料在内存里，数据更新不生效

```python
_bm25_corpus = []  # 8139 条文本常驻内存
_bm25 = None
```

**问题**：
- 每次服务启动**从 DB 全量拉一遍**（慢）
- 数据更新后（如补了新文档），**不重启服务就不生效**
- 多 worker 各一份，内存翻倍

**正确做法**：BM25 用 PostgreSQL 的 `tsvector` + GIN 索引，走 SQL 查询，不在应用层维护内存索引。或者接受 Demo 阶段的内存方案，但**加一个 `/admin/reload` 接口**手动刷新。

---

### 4. `sys.path.insert` 是代码异味

`main.py` 里：

```python
sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))
from retrieval.hybrid_retriever import hybrid_search
```

**问题**：
- 通过 `sys.path` hack 让 `retrieval` 能 import，说明**包结构没配好**
- 换个入口（比如 `uvicorn src.rag_demo.api.main:app`）就可能失效
- 无法被 `pip install -e .` 正确打包

**正确做法**：`pyproject.toml` 里配置正确的包路径，全部用 `from src.rag_demo.retrieval import ...` 全限定导入。

## 二、🟡 产品化前的债（Demo 可接受）

### 5. 配置散落重复

`DB_CONFIG` 在 `hybrid_retriever.py` 和 `ingest_data.py` 里**各写了一份**：

```python
DB_CONFIG = {"host": "localhost", "port": 5432, ...}
```

**改端口要改 3 个文件**。应该抽到 `src/rag_demo/config.py`，或者用 `.env` + `pydantic-settings`。

---

### 6. 没有日志，全靠 print

```python
print(f"✅ {filename}: 导入 {len(chunks)} 个分块")
```

- 无法按级别过滤（DEBUG/INFO/WARN/ERROR）
- 无法输出到文件或采集系统
- 生产环境会刷屏

**正确做法**：`logging` 标准库，按模块命名 logger。

---

### 7. 没有异常处理和重试

`generator.py` 里 LLM 调用裸奔：

```python
resp = client.chat.completions.create(...)
```

- **网络抖动**：直接 500
- **DeepSeek 限流**：直接 500
- **Key 失效**：报错信息不友好

**正确做法**：加 `tenacity` 重试（最多 3 次，指数退避），超时设置 30 秒。

---

### 8. 没有类型提示

```python
def rerank(query, candidates, top_k=5):
```

**正确做法**：

```python
def rerank(query: str, candidates: list[dict], top_k: int = 5) -> list[dict]:
```

不是洁癖——PyCharm 的自动补全、重构、静态检查全都依赖类型标注。

---

## 三、🟢 结构层面（不紧急但值得规划）

### 9. 分层可以更清晰

现在的结构：

```text
retrieval/
├── hybrid_retriever.py    # 向量 + BM25 + RRF，职责太重
└── reranker.py
```

**建议的未来结构**（产品化时重构）：

```text
src/rag_demo/
├── config.py                # 统一配置
├── logger.py                # 统一日志
├── db/
│   ├── connection.py        # 连接池 + 探活
│   └── models.py            # 表 schema
├── retrieval/
│   ├── vector.py            # 只做向量召回
│   ├── bm25.py              # 只做 BM25
│   ├── fusion.py            # 只做 RRF
│   └── reranker.py
├── generation/
│   ├── prompt.py            # Prompt 模板集中
│   └── generator.py
├── tools/                   # 为 Text2SQL / GraphRAG 预留
├── api/
│   ├── main.py
│   └── routes/
└── pipeline/                # 编排层（未来的 Router）
```

**核心变化**：`tools/` 单独出来（你接下来加 SQL 工具就有地方放）、`pipeline/` 独立（未来的意图路由）。

---

### 10. 没有单元测试

只有 `test_search.py`（是集成测试，跑真实模型和 DB）。没有 pytest 单测。

Demo 阶段可以忍，但如果要持续演进，**至少给 `rrf_fusion`、`build_profile_text` 这种纯函数写单测**——它们不依赖 DB 和模型，跑得快。

---

### 11. 敏感配置管理

`DEEPSEEK_API_KEY` 靠环境变量。DB 密码硬编码。

**产品化时**：`.env` + `python-dotenv`，`.env` 加进 `.gitignore`。生产环境用密钥管理服务（Vault / K8s Secret）。

## 四、优先级矩阵

| 问题 | 严重度 | 修复成本 | 什么时候修 |
|---|---|---|---|
| 连接探活 | 🔴 高 | 低（10 行） | **下次改代码时顺手做** |
| 全局状态 | 🔴 高 | 中（改架构） | 加多 worker 之前 |
| BM25 内存 | 🔴 中 | 低（加 reload 接口） | 数据更新频繁时 |
| sys.path hack | 🔴 中 | 低（改 pyproject） | 打包或部署前 |
| 配置散落 | 🟡 中 | 低（抽 config.py） | 下次改代码时 |
| 日志 | 🟡 中 | 低 | 加 API 日志时 |
| 异常重试 | 🟡 中 | 低（10 行） | 上生产前 |
| 类型提示 | 🟡 低 | 中 | 边改边加 |
| 分层重构 | 🟢 低 | 中 | 加 tools/ 时顺便 |
| 单元测试 | 🟢 低 | 中 | 加 SQL 工具时一起 |

---

## 五、我的建议

**现在不修。** 你正在验证业务价值，架构问题不影响你继续加功能。但记住两条底线：

1. **改代码时顺手做「低成本高收益」的**：加连接探活、抽 `config.py`、加类型提示。别专门开一天做重构。
2. **加新功能前先判断会不会碰雷**：
   - 加 `tools/sql_tool.py` 之前，先抽 `db/connection.py`（否则 SQL 工具会再复制一份 `DB_CONFIG`）
   - 加 `pipeline/router.py` 之前，先改 `main.py` 的 `sys.path` hack（否则 pipeline 也要 hack）
   - 上多 worker 之前，必须先把全局状态改成 `app.state`

---

## 一句话总结

**你的 Demo 架构「能跑但脆」——单进程、单用户、不重启的前提下完全够用。** 埋雷主要集中在**连接管理**和**全局状态**这两处，一旦服务要长时间运行或并发访问，就会立刻暴露。产品化前至少要修这两个。
