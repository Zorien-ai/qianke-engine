## 一、已修复

### 1. [严重] `run_eval.py` 在中文 Windows 终端崩溃

**现象**

跑评测时第 1 条就中断，报错出现在**错误处理分支本身**：

```text
File "run_eval.py", line 81, in main
    print(f"  \u2717 失败: {e}")
UnicodeEncodeError: 'gbk' codec can't encode character '\u2717' in position 2
```

**根因**

`print(f"  ✗ 失败: {e}")` 里的 `✗`(U+2717) **不在 GBK 字符集内**，而 Windows 中文终端的默认编码是 GBK。

致命之处在于：这是 **`except` 分支里的 print**——也就是说，只要**任何一条题目失败**，脚本就会在打印错误时二次崩溃，直接终止整个评测，后面 19 条全跑不到。

**修复**

```python
# 修复前
print(f"  ✗ 失败: {e}")
# 修复后
print(f"  [FAIL] {e}")
```

**经验**

- Windows 中文环境下脚本里**避免使用非 GBK 字符**（`✗ ✓ ⚠ 🎉` 等 emoji 和装饰符号）
- 注意 `ingest_data.py` 里也用了 `🎉`，但它走 `logging`——logging 对不可编码字符会做转义处理（输出成 `\U0001f389`），**不会崩**；而 `print` 会直接抛异常。这条差异要记住
- 交付前建议在目标终端实际跑一次，别只在 IDE 里验证（IDE 控制台通常是 UTF-8，掩盖了这个问题）

### 2. [严重] torch 被 `uv run` 自动降级回 CPU 版

**现象**

手动装好 `2.14.1+cu126` 并用 `.venv\Scripts\python.exe` 验证 `cuda.is_available() == True`，但只要跑一次 `uv run`，就退化成 `2.14.1+cpu`，CUDA 变 `False`。

**根因**

`uv run` 每次都会做环境同步，而 `uv.lock` 记录的 torch 来源是 **PyPI**：

```toml
# uv.lock（错误状态）
name = "torch"
version = "2.14.1"
source = { registry = "https://pypi.org/simple" }
```

**PyPI 上的 torch 在 Windows 就是 CPU 版**——其依赖列表里的 CUDA 包全部带 `sys_platform == 'linux'` 标记：

```toml
dependencies = [
    { name = "cuda-bindings", marker = "python_full_version < '3.15' and sys_platform == 'linux'" },
    { name = "nvidia-cudnn-cu13", marker = "sys_platform == 'linux'" },
    ...
]
```

所以只要 `uv run` 触发同步，就会把手动装的 cu126 版本覆盖掉。

**修复过程（三次迭代）**

| 步骤 | 做法 | 结果 |
|---|---|---|
| ① | `pyproject.toml` 加 `[tool.uv.sources]` + `[[tool.uv.index]]` | ❌ 无效，`uv lock` 后 source 仍是 `pypi.org` |
| ② | 把 `torch` 加进 `[project] dependencies` | ✅ 生效，但仍需联网下载 2.4GB |
| ③ | source 改为**项目内本地 wheel 路径** | ✅ 彻底解决，零网络依赖 |

**关键坑（②的必要性）**：uv 的 `tool.uv.sources` **只对「项目直接依赖」生效**。torch 原本只是 `sentence-transformers` 的间接依赖，所以第 ① 步配置完，`uv lock` 跑完 17 秒，source **依然是 PyPI**，等于白配。

**最终配置**

```toml
[project]
dependencies = [
    ...
    "torch==2.14.1",
]

[tool.uv.sources]
torch = { path = "wheels/torch-2.14.1+cu126-cp312-cp312-win_amd64.whl" }

[[tool.uv.index]]
name = "pytorch-cu126"
url = "https://download.pytorch.org/whl/cu126"
explicit = true
```

**连带的必要改动**：`requires-python` 从 `>=3.12` 收紧为 `>=3.12,<3.13`。

原因：`>=3.12` 意味着同时支持 3.13/3.14/3.15，uv 要为每个版本解一套依赖，而本地 wheel 是 `cp312`（只服务 3.12），其他版本 split 无解：

```text
× No solution found ... for split (markers: python_full_version >= '3.14' and sys_platform == 'win32')
╰─▶ torch==2.14.1+cu126 has no wheels with a matching Python version tag (e.g., `cp312`)
```

顺带把 2.4GB wheel 复制进项目 `wheels/` 目录（`.gitignore` 已含 `wheels/`，不会提交）。

**副作用（必须记住）**

- `wheels/` 目录**不能删**，删了 `uv sync` 会失败
- 别人 clone 项目后**需要自备这个 wheel** 才能 sync

### 3. 中文路径导致 uv 参数乱码

**现象**

```powershell
uv pip install "E:\新建文件夹\torch-2.14.1+cu126-cp312-cp312-win_amd64.whl"
# error: The wheel filename "鏂板缓鏂囦欢澶筡torch-2.14.1+cu126-..." has an invalid package name
```

中文路径 `新建文件夹` 被错误编码成 `鏂板缓鏂囦欢澶筡`，导致 uv 解析 wheel 文件名失败。

**绕法**：不把中文写进命令，让文件系统自己去拼路径

```powershell
$whl = (Get-ChildItem -Path 'E:\*\torch-2.14.1+cu126-cp312-cp312-win_amd64.whl' | Select-Object -First 1).FullName
uv pip install $whl
```

`E:\*\<文件名>` 用通配符跳过中文目录名，取到路径后交给变量传递（变量传参不被错误编码）。

### 4. 重复 dist-info 导致 uv 状态错乱

**现象**

```text
torch                    2.14.1
torch                    2.14.1+cu126
```

`uv pip list` 同时列出两个 torch。

**根因**

多次安装失败留下了残壳目录 `torch-2.14.1.dist-info`，里面**只剩一个 `licenses` 子目录**，`METADATA`/`RECORD` 全丢了。uv 读不到元数据，却又把它当"已安装的 torch"。

**修复**：直接删掉残壳

```powershell
Remove-Item -LiteralPath 'F:\workspace\python\rag-demo\.venv\Lib\site-packages\torch-2.14.1.dist-info' -Recurse -Force
```

### 5. Docker Desktop 不自启导致 PostgreSQL 不可用

**现象**

```text
psycopg2.OperationalError: connection to server at "localhost" (::1), port 5432 failed:
Connection refused (0x0000274D/10061)
```

容器状态：`pgvector | Exited (255) 2 hours ago`（异常退出码 255）。

**根因**

`com.docker.service` 的 `StartType` 是 **Manual**，开机/重启后不会自动拉起 Docker Desktop，连带容器全停。

**处理**

```powershell
docker start pgvector
```

**建议**：在 Docker Desktop → Settings → General 勾选 **"Start Docker Desktop when you sign in"**，否则每次重启都要手动拉。

### 6. `wiki_hit` 指标已失效

**现象**

GPU 版评测 **20/20 全部 `wiki_hit=True`**，包括「今天天气怎么样」这种明显不该召回的负样本：

```text
Wiki 预期召回: 14/14 (100%)     ← 假象
```

**根因**

`run_eval.py` 里判断的是「有没有**任意** .md 被召回」：

```python
wiki_sources = [s for s in unique_sources if s.endswith(".md")]
wiki_hit = len(wiki_sources) > 0
```

而 `rerank_by_source(q, cands, top_k_profile=3, top_k_wiki=2)` **强制保留 2 个 wiki 名额**——只要检索池里有 wiki，就必然被选中。

**建议改法**：判断「**期望的那个 .md** 是否命中」

```python
expect_md = {s for s in item["expect_sources"] if s.endswith(".md")}
wiki_hit = bool(expect_md & set(unique_sources))
```

### 7. 负样本在检索层没有拒答能力

**现象**

`EDGE-01`（今天天气）、`EDGE-02`（预测 GMV）都召回了 3~5 个 wiki 块。

**分层表现**

| 层 | 表现 |
|---|---|
| 检索层 | ❌ 无差别召回（受 `top_k_wiki=2` 强制名额影响） |
| 生成层 | ✅ 拒答正确——"现有资料未包含任何天气或气象数据"、"无法给出具体数值预测" |

**结论**：Prompt 里「资料不足就明确说明」的约束**生效了**，但检索层白白消耗了上下文配额。

**方向**：意图路由（见 `bug/10.6/问题 5：意图路由缺失（浪费上下文）.md`）——先判断 query 类型，再决定召回源。

## 三、GPU 加速验证结果

| 指标 | baseline (CPU) | gpu | 变化 |
|---|---|---|---|
| 成功率 | 20/20 | 20/20 | — |
| 首条（含模型加载） | 39.88s | 29.68s | 1.34x |
| **其余 19 条平均** | **16.43s** | **7.34s** | **2.24x** |
| 最快单条（CS-02） | 13.79s | 3.70s | **3.7x** |
| `source_match` | 17/20 | 17/20 | 持平 |

**注意干扰项**：`DA-02` 从 17.01s 变成 **19.59s（反而变慢）**。

原因：单条耗时的大头是 **DeepSeek API 调用**（回答越长越慢），LLM 的波动会盖过 GPU 收益。所以 2.24x 是**被 LLM 稀释后**的数字，纯本地推理（embedding + reranker）的提速实际更高。

**环境配置**

```text
torch 2.14.1+cu126 | CUDA 12.6 | RTX 3060 Laptop (6GB)
模型加载显存占用: 2.12GB（fp16）
```
