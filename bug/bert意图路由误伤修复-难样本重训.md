## 2. 缺口定位：为什么模型把「U2765」当成闲聊

两条误伤的置信度极高（0.9962 / 0.9969），不是「模棱两可判错了」，而是模型**确信**它们是闲聊。回看训练集就能看出原因：

| 形态 | 训练集里的实际情况 | 后果 |
|---|---|---|
| 用户 ID | 几乎只以**长中文句子的成分**出现（「U2765的年龄」「U9911 有没有领过优惠券」） | **裸 ID**（`U2765`）是没见过的输入形态，滑向闲聊 |
| 业务缩写 | GMV / UV / ROI / DAU / SKU 基本没有独立样本 | 「动作 + 缩写」（`看下GMV`）无任何支撑 |

也就是说，不是「数据不够多」，而是**数据不够短**：训练集教会了模型「ID 出现在长句里很正常」，但没教它「ID 单独出现也是业务」。

### 为什么不能只补正样本

只加「ID / 缩写 = 业务」的正样本，模型会学成「含字母数字就是业务」，于是 test 集里的 `asdf` / `yes` / `1` / `testing` 会从「正确拦截」变成「漏判」——**用一个错误换另一个错误**。所以同一批必须补入**同长度、同字符集、但无业务语义**的闲聊负样本，把边界钉住。

（这也解释了最终结果里那 2 条 val 错误为什么发生在 `HelloWorld` 这类 camelCase 上：Latin 一侧的边界只钉住了「小写字母串 / 重复字符 / 网络缩写」，没有覆盖「驼峰命名单词」。见 §8 遗留 2。）

## 3. 难样本设计

### 3.1 两类文件、四种形态

| 文件 | task | 条数 | 形态举例 |
|---|---|---|---|
| `business_id_abbrev.jsonl` | `biz_id_short` | 78 | `U8801`（裸 ID）、`A13`、`查U3027`、`看下U6512的数据`、`U9043的等级`、`用户U1187` |
| | `biz_abbrev` | 47 | `看GMV`、`查UV`、`拉下ROI`、`看下DAU`、`看下SKU` |
| | `biz_term` | 12 | `日活`、`动销`、`转化率`、`退款率`、`履约率` |
| `chitchat_alnum_short.jsonl` | `cc_alnum` | 45 | `zzz`、`6666`、`yyds`、`xswl`、`emmm`、`6`、`呜呜`、`哈哈哈` |

业务侧 137 条 / 闲聊侧 45 条，**故意偏向业务侧**：缺陷在业务侧被误判，而闲聊侧只需「钉住边界」，不需要等量。

### 3.2 三条硬约束（脚本内自检，不靠人盯）

探针（`probes.py` 的 55 条）是分布外评测**唯一**的标尺，污染它的后果比漏判更隐蔽——`split_data.build_probes` 遇到重合会**把探针本身丢掉**，评测集悄悄少一条，指标照样好看。所以生成脚本设了三道闸，且每道都**输出它拦下了什么**：

| # | 检查 | 本轮实际拦下 | 后果（若不拦） |
|---|---|---|---|
| 1 | 归一化后与探针**等值** | `看下GMV`（由「看下」×「GMV」组合出） | 探针进训练集，指标虚高 |
| 2 | 包含「全词未见过」探针的**整串** | `看下GMV明细` | 探针从 `unseen` 静默翻成 `fragment`，测的从泛化变成半记忆 |
| 3 | 与既有数据重合 / **标签冲突**（同形不同标签直接中止） | 15 条重合 | 清洗阶段静默去重（白写）；标签冲突会埋进数据 |

> **第 2 道闸是踩出来的事故**：第一版只做了等值检查，`看下GMV明细` 顺利通过并写进数据，跑完 `split_data` 才发现探针 `看下GMV` 的 `probe_type` 从 `unseen` 变成了 `fragment`。
> 教训：**「不相等」不等于「没污染」**——对「文字游戏」类的数据设计，必须检查包含关系，且判据要锚在「改前是什么状态」（这里是 `UNSEEN_MUST_STAY` 那 8 条），否则守卫会永远不触发。
> 现在这一组动词仍保留「看下」，就是为了让第 1 道闸**有东西可拦**：一条永远不触发的守卫等于没有守卫。

### 3.3 配比与长度的连带影响

补数据不能只看目标指标，还要复查清洗脚本的硬性约束（`analyze_data.py` 会判定并告警）：

| 约束 | 重训前 | 重训后 | 判定 |
|---|---|---|---|
| 类别比（B/C，目标带 1:0.9~1:1.1） | 1371/1341 = 1.022 | 1507/1386 = **1.087** | ✓ 在带内 |
| 最差长度桶少数类占比（目标 ≥25%） | 26.4%（1-3 字桶） | **29.3%** | ✓ 反而改善 |
| 短探针构成 | fragment 21 / unseen 9 | **fragment 21 / unseen 9** | ✓ 未被污染 |
| 探针混入 train/val/test | 0 条 | **0 条** | ✓ |

> 第一版正样本做到 164 条，类别比冲到 1.116（**越界**），只能回头精简 ID 列表、把缩写动词从 5 个压到 4 个，并补 12 条闲聊负样本把比例拉回带内。
> 这说明「补难样本」不是加数据那么简单：**总量受配比约束、形态受探针约束、长度受对称性约束**，三个约束互相牵制。

## 5. 关键发现：新 val 的 2 条错误是「记忆失效」，不是「模型变坏」

重训后 val 不再满分（0.9931），错误是 `护肤步骤有哪些`、`HelloWorld`。直觉上会归因为「新数据把模型教坏了」，但用备份的旧模型逐条比对 + 回查旧划分后，结论相反：

| 样本 | 旧划分里在哪 | 旧模型判定 | 新模型判定 | 真相 |
|---|---|---|---|---|
| `HelloWorld` | **旧 train** | ✓ chitchat（0.9962） | ✗ business（0.0006） | 旧模型的「正确」是**记住了训练样本** |
| `护肤步骤有哪些` | **旧 train** | ✓ chitchat（0.9947） | ✗ business（0.0023） | 同上 |
| `收到` | 旧 **test** | ✗ business（0.0166） | ✗ business（0.0048） | 旧 test 里那条唯一错误；新划分把它挪进了 **train**，模型**仍在训练集内判错** |

三点解读：

1. **旧 val 的满分里有记忆成分**。这两条样本原本就在训练集里，模型判对是「见过」，不是「会做」；重训后它们被分到 val，模型没能泛化过去。这恰好从侧面印证了 `bug/bert模型训练.md` 里「验证集 F1 = 1.0 意味着评估集已经失效」的判断。
2. **指标不可逐条跨划分对比**。数据一变，分层抽样的结果就重排，「谁在 train」会变。因此本类实验的锚必须是**固定的探针集**，而不是 test/val 的总体准确率。
3. `收到` 是另一个性质的问题：它现在在**训练集里**（标签 CHITCHAT）而模型仍判业务（p=0.0048）。这是训练集内的顽固错例，说明 2 字短确认词与语料分布存在纠缠（**假设**：与新增的 `收藏数` / `首单数` 共享「收」字有关；未做消融，不作为结论）。

## 6. 误伤修复的核心证据（逐条 p_chitchat 前后对照）

| 样本 | 期望 | 重训前 p | 重训后 p | 判定变化 | 泛化性说明 |
|---|---|---|---|---|---|
| `U2765` | rag | 0.9962 ✗ | **0.0006** ✓ | 闲聊 → 业务 | 训练集里**从无此 ID**（新增的是 `U8801` 等），是模式泛化 |
| `看下GMV` | rag | 0.9969 ✗ | **0.0002** ✓ | 闲聊 → 业务 | 探针串被自检拦下未入库；训练的是 `看GMV / 查GMV / 拉下GMV` |
| `闰年是怎么回事` | chitchat | 0.7100 ✗ | **0.9773** ✓ | 顺带修好 | 旧 test 里最贴近门槛的样本 |
| `收到` | chitchat | 0.0170 ✗ | 0.0048 ✗ | 仍未修好 | 见 §5.3 |

对照组（**必须无变化**，否则是「按下一个、翘起另一个」）：

| 样本 | 期望 | 重训后 p_chitchat | 判定 |
|---|---|---|---|
| `asdf` | chitchat | 0.9975 | ✓ |
| `yes` | chitchat | 0.9981 | ✓ |
| `1` | chitchat | 0.9955 | ✓ |
| `testing` | chitchat | 0.9983 | ✓ |
| `你好` / `哈哈` | chitchat | 0.9992 / 0.9992 | ✓ |
| `查U2765` / `美妆用户` / `风控` | rag | 0.0003 / 0.0002 / 0.0005 | ✓ |

**风险余量从 −0.0969 变成 +0.6916**：业务侧「最像闲聊」的样本是长探针「那些只买过一次就再没回来的人大概有多少」（0.2084），距门槛还有 0.69 的空间。这比「误伤为 0」本身更重要——它说明修复不是把错误挤到门槛边缘，而是把整条边界推开了。

## 7. 路由层指标（新 345 条评测集）

| 方案 | 准确率 | 闲聊召回 | 误伤业务 | 漏判闲聊 | 单条 p50 |
|---|---|---|---|---|---|
| rule | 0.6348 | 0.0870 | 0 | 126 | 0.022 ms |
| **bert** | **1.0000** | 1.0000 | **0** | **0** | 18.56 ms |
| hybrid | 1.0000 | 1.0000 | 0 | 0 | 18.19 ms |

- 规则在 138 条闲聊里只拦住 12 条（8.7%），BERT 拦回 **126/126（100%）**。
- **门槛不再承重**：0.5 / 0.6 / 0.7 / 0.8 / 0.9 / 0.95 / 0.99 七档**全部 0 误伤 / 0 漏判**。这是模型内在判别力提升的表现，而不是门槛调得好——修好之前，任何门槛都消不掉那 2 条误伤（它们 p≈0.996）。
- 代价换算：规则漏判 126 条 → **3175.2 s** LLM 时间；BERT 漏判 0 条 → **0 s**。
- 延迟无退化：p50 18.56 ms（重训前 18.70 ms），相对 25.2 s 链路占 0.074%。

CPU 侧（`--device cpu`，同一份 345 条）：误伤 / 漏判同样为 **0 / 0**，bert p50 **125.3 ms**（重训前 117.3 ms，同一量级），
hybrid p50 **115.7 ms**。这里出现一个此前没有的现象：**hybrid 比 bert 稳定地快约 9.6 ms**——
因为规则现在能短路 12 条闲聊（重训前只有 9 条），在 CPU 上每条短路省下约 125 ms。
GPU 上这个差值只有 0.37 ms（规则命中 12/345 × 18.6 ms ≈ 0.6 ms），仍属噪声。
结论：`hybrid` 的价值随「规则命中率」与「单次前向成本」上升，**若最终部署在 CPU，hybrid 是更优默认值**。

## 9. 复现

```bash
# 1) 生成难样本（内含三层自检，任一层命中会跳过并点名，标签冲突直接中止）
uv run python src/rag_demo/bert_query_classify/gen_hard_samples.py

# 2) 清洗 + 划分（会重算类别比、长度对称性、探针构成，均需人工确认 ✓）
uv run python src/rag_demo/bert_query_classify/analyze_data.py
uv run python src/rag_demo/bert_query_classify/split_data.py

# 3) 重训（先停 uvicorn / RAG 服务，6GB 卡上共存会 OOM）
uv run python src/rag_demo/bert_query_classify/train.py

# 4) 评测 + 路由层对比（本轮的验收口径）
uv run python src/rag_demo/bert_query_classify/evaluate.py
uv run python src/rag_demo/bert_query_classify/bench_router.py
```

回退方式：`models/bert-intent.bak` 是重训前的权重（被 `.gitignore` 覆盖，不入库），本次前后对照实验用的就是它；确认不需要回退即可删除。数据侧的改动全部在 git 跟踪范围内，`git checkout` 可还原。
