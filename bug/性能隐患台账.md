## P1. 变体生成引入额外 LLM 调用

**现象**

开启 `ENABLE_MULTI_QUERY` 后，每次 RAG 问答会多出 **1 次 LLM 调用**（生成 4 个查询变体）和 **4 次额外 `hybrid_search`**。

**实测数据**

评测集整体（20 条）：

| 版本 | 配置 | 平均耗时 |
|---|---|---|
| `gpu_v8` | 单路检索 | 15.13s |
| `gpu_v9` | 五路检索 | **22.86s**（+51%） |

单条最慢：`OPT-04` 达到 **59.8s**。

逐环节拆解（`tools/profile_pipeline.py`，OPT-01 第 2 轮）：

| 环节 | 耗时 | 占比 |
|---|---|---|
| LLM 生成答案 | 12.65s | 64.3% |
| **变体生成（新增的那 1 次 LLM）** | **6.11s** | **31.0%** |
| 五路检索（串行累加） | 0.75s | 3.8% |
| 精排 + 文档扩展 | 0.16s | 0.8% |
| RRF 融合 | 0.00s | 0.0% |
| **合计** | **19.67s** | |

**⚠️ 关键更正：瓶颈不是「检索串行」**

本条最初标题为「五路 query 检索全串行」，并预估「并发可省 3~5s」——**那是按代码结构猜测的，未经测量，结论错误**。

实测证明：5 次检索串行累加**只有 0.75 秒**（3.8%），**即使全部并发也只能省约 0.6 秒**，不值得做。

真正的开销是**新增的那一次 LLM 调用（6.11s，占 31%）**。

**根因**

`query_processor.py::build_query_variants()` —— 变体生成已从「4 次调用」优化为「1 次调用」出 4 个变体，但 LLM 单次调用本身约 6s。这部分时间是**模型推理 + 网络往返**，不是代码结构问题。

**建议方案（按实测收益排序）**

- **方案 A**：变体生成改用**规则扩展**（复用已有的 `SYNONYMS` 同义词表 + BM25 高权重词），彻底去掉这次 LLM 调用 → **省约 6s**。**但会偏离流程图设计**（图里明确是 LLM 生成变体），需先确认是否接受
- **方案 B**：用更小/更快的模型只做变体生成 → 省 3~5s，保留语义扩展能力
- **方案 C**：只生成 2 个变体而非 4 个 → 省约 3s
- **方案 D**：接受现状——变体生成是「检索质量换响应时间」的**有意取舍**，且当前 17/20 的成绩有它一份贡献
- ~~**方案 E：5 路检索并发**~~ → **已证伪**，实测收益不足 1s

**验收标准**：平均耗时回到 18s 以内，且 20 条评测结果（17/20）不变。

**教训**：**性能问题必须先测量再下结论**。「代码结构上是串行」不等于「性能瓶颈是串行」——本次两个判断都错了，错在没有 `profile_pipeline.py` 这一步。

### 已实施缓解（2026-10-12）

按「让 LLM 判断走哪几路，而不是一律全跑」改造 `query_processor.py`：

- 变体生成改为**一次调用同时完成「判断 + 生成」**，按需只生成被选中的变体（拆成两次调用反而多一次往返）
- **「直接检索」永远执行** —— 兜底，不依赖 LLM 判断成功；LLM 异常或解析失败自动退化为单路
- 新增 `config.MULTI_QUERY_MAX_VARIANTS = 2` 兜住上界，防止模型贪心全选
- 只采纳「判定需要」**且**「确实生成了内容」的策略，避免模型只写策略行不写内容

**实测效果**

| 指标 | 全跑（`gpu_v9`） | 按需（`gpu_v10`） |
|---|---|---|
| 平均路数 | 5.00 | **1.50**（↓70%） |
| 平均耗时 | 22.86s | **20.32s**（↓11%） |
| 自动判定通过 | 17/20 | **17/20**（不变） |
| 来源命中 / 文档命中 | 14 / 11 | **14 / 11**（不变） |

**质量零损失**。重点观察对象 `DA-01`（依赖 `tag_definitions.md`）：按需模式下虽然只走 1 路，**仍命中目标文档** —— 证明多出来的那几路是「锦上添花」而非「必需」，此前五路全跑有相当一部分是白跑。

**剩余开销**：变体生成的 LLM 往返（约 6s）**无法通过按需省掉** —— 判断本身就要调一次模型。彻底解决需方案 A（改规则扩展），但会偏离流程图设计，需产品决策。

**判断质量检查工具**：`tools/check_query_routing.py`（只测判断环节，不跑检索与生成）

**影响面**：全部 16 条 RAG 路径问题。

**代码锚点**：`query_processor.py::multi_query_search`（已埋 `TODO(perf)`）

## P2. Parent Document 召回放大上下文

**现象**

命中的 wiki chunk 会被扩展为**所在文档的全文**（上限 `WIKI_MAX_CHARS = 1200`），导致送进 LLM 的上下文变长。

**实测数据**

| 版本 | 配置 | 平均耗时 |
|---|---|---|
| `gpu_v7` | chunk 原文（约 400 字） | 11.01s |
| `gpu_v8` | 文档全文（最多 1200 字） | 15.13s（+16%） |

**根因**

`src/rag_demo/retrieval/reranker.py` → `_expand_to_full_doc()`：把 chunk 的 `text` 整体替换为源文件全文。

> **注意**：这是**有意为之的正向改进**——它解决了「chunk 粒度错配」问题（详见 `bug/10.11/2026-10-11_phase4验收问题.md` 问题 5），`DA-01` 正是靠它才能列出全部 7 个标签。**不是缺陷，只是有成本。**

**建议方案**

- 调小 `WIKI_MAX_CHARS`（如 1200 → 800）
- 或改为「只扩展被多次命中的文档」，避免为单次命中付全文成本
- 或按文档类型区分长度（`tag_definitions.md` 短、`marketing_playbook.md` 长）

**验收标准**：平均耗时回落 2s 以上，且 `DA-01` 仍能列出完整标签。

**影响面**：所有命中 wiki 的 RAG 问题。

**代码锚点**：`reranker.py::_expand_to_full_doc`（已埋 `TODO(perf)`）

## P3. 两个模型常驻显存（6GB 卡占 73%）

**现象**

`bge-m3`（约 2.2GB fp16）与 `bge-reranker-v2-m3`（约 2.2GB fp16）在进程内**单例常驻**，不释放。

**实测数据**

- RTX 3060 可用显存 6144MiB，桌面程序占用约 910MiB
- 两模型占用约 4.4GB → **约占可用量的 73%**
- 本次 A/B 实验需要加载第三个模型（`BGEM3FlagModel`）时，**必须等主流程退出**才能跑，无法并行

**根因**

`hybrid_retriever.get_model()` 与 `reranker.get_reranker()` 使用模块级单例：

```python
_model = None
def get_model():
    global _model
    if _model is None:
        _model = SentenceTransformer(...)
    return _model
```

> **注意**：单例本身是**正确的设计**——避免每次请求重复加载（加载一次约 20~30s）。问题在于**没有卸载机制**，导致显存被长期锁定。

**建议方案**

- 低峰期主动 `del` + `torch.cuda.empty_cache()`（需配合模型重载逻辑）
- 或改为「按需加载 + 空闲超时卸载」
- 或硬件层面升级显存
- 或对离线批处理脚本（如 A/B 实验）改用 CPU 推理，与在线服务隔离

**验收标准**：能在同一台机器上并行跑通「在线服务 + 离线实验」而不 OOM。

**影响面**：并发请求、离线实验并行、显存紧张的开发机。

**代码锚点**：`hybrid_retriever.py::get_model`、`reranker.py::get_reranker`

## P4. SQL 答案生成重复注入完整 schema

**现象**

为了让「0 行结果能解释原因」，`llm_summarize()` 每次都会把完整的 `SCHEMA_PROMPT`（约 500 字，含所有字段与枚举值）拼进 prompt——**哪怕查询返回了正常结果，根本用不到枚举信息**。

**实测数据**

未单独量化耗时。估算：每次 SQL 题多约 500 字 prompt，约 150~200 token。

**根因**

`generation/generator.py::llm_summarize(question, sql_result, schema=...)` —— 为覆盖 0 行场景而**无条件注入**。

> **注意**：这是修复 `OPT-06`（问「母婴」但数据无此品类，LLM 无法解释原因）时的必要代价。**不是缺陷，是可优化点。**

**建议方案**

- 仅在 `len(rows) == 0` 时注入 schema，正常结果不注入（**最省，改动最小**）
- 或把 schema 精简为「枚举字段清单」而非全表结构

**验收标准**：SQL 题平均耗时下降，且 `OPT-06` 仍能说明「数据中无该类别」。

**影响面**：4 条 SQL 路径问题。

**代码锚点**：`generator.py::llm_summarize`

## P5. BM25 全量语料常驻内存

**现象**

`_load_bm25_corpus()` 会把**全部语料**（画像 8110 条 + 文档分块 36 条）的分词结果一次性载入内存，构建 `BM25Okapi` 索引并常驻。

**实测数据**

**未量化**（未单独测量内存占用）。

**根因**

`hybrid_retriever.py::_load_bm25_corpus()` 使用模块级全局 `_bm25` / `_bm25_corpus`。

**建议方案**

- 先测量实际占用，再决定是否需要处理
- 若语料继续增长到十万级，考虑分片索引或持久化倒排

**验收标准**：语料规模翻倍时内存不失控。

**影响面**：当前规模（8146 条）下无感知，属**预防性记录**。

**代码锚点**：`hybrid_retriever.py::_load_bm25_corpus`

**2026-10-12 变更**

BM25 分词结果已落库（`search_index.bm25_tokens`），启动时直接读回，省掉每次对
8146 条文本重新 jieba 分词的开销（**实测 6.27s → 加载 0.21s**）。

但这**只是省掉了重复计算，本条隐患本身没消除**：语料（id/text/source）与
`BM25Okapi` 所需的 token 列表仍要常驻内存——`rank_bm25` 是库外算法，
打分必须在内存里做，没法下推到数据库（这点与稀疏向量不同，后者可用 `sparsevec` 库内检索）。

顺带记录一个改造引入的坑：分词下推后 `_load_bm25_corpus` 不再调用 jieba，
导致 jieba 首次初始化（约 1.2s）从启动阶段**漂移到了第一个用户请求上**，
已在 `_load_bm25_corpus` 末尾补一次 `_tokenize("预热")` 修正。

## P6. 评测脚本串行执行

**现象**

`tests/run_eval.py` 逐条跑完 20 道题，无并发。

**实测数据**

- `gpu_v9`（五路检索）：20 题约 **8 分钟**

**影响面**：仅开发/评测流程，不影响线上服务。

**代码锚点**：`tests/run_eval.py::main`

## P7. 稀疏索引本地缓存的一致性（已修复 → 机制整体移除）

**现象**

`sparse_retriever._load_sparse_index()` 判断缓存是否可用时**只比对条数**：

```python
if len(cached) == len(corpus):
    _index, _corpus = cached, corpus
    return
```

**风险**：若语料**内容变了但条数没变**（只改 `profile_text` 模板、给每条加字段等），旧缓存会被当成有效复用，**稀疏检索静默使用过期数据**。

**这不是假设**：2026-10-11 给画像补「钻石会员」那次，条数一条没变（仍是 8110），若当时已有缓存便会踩中——所幸缓存是之后（A/B 实验）才生成的，躲过一劫。

**BM25 无此问题**：它每次启动都从 DB 重建，天然与数据同步。

**修复（2026-10-12）**

给缓存加**内容指纹**：

```python
def _corpus_fingerprint(corpus) -> str:
    """对语料 id + text 全量取 SHA-256（8146 条约 800KB，耗时几毫秒）"""
    h = hashlib.sha256()
    for c in corpus:
        h.update(c["id"].encode())
        h.update(b"\x00")
        h.update((c.get("text") or "").encode("utf-8"))
        h.update(b"\x01")
    return h.hexdigest()
```

缓存格式由裸 `list` 升级为 `{fingerprint, weights}`；**旧格式无指纹可校验，直接判无效并重建**。

**验证**（`tools/check_sparse_cache.py`）

| 场景 | 耗时 | 结果 |
|---|---|---|
| 旧格式缓存 | 47.91s | ✅ 判无效并重建，升级为新格式 |
| 指纹一致 | **0.33s** | ✅ 命中（快 145x） |
| 篡改指纹（模拟内容变化） | 24.58s | ✅ 检测到过期并重建 |
| 重建后再加载 | 0.36s | ✅ 命中 |

**结论**：内容变化能被发现，内容未变则稳定复用。

**遗留**：若希望数据更新后**立即**生效（而非等下次加载时才发现），可在 `ingest_data.py` 末尾主动调用 `reload_sparse_index()`。

**代码锚点**：`retrieval/sparse_retriever.py::_corpus_fingerprint` / `_load_sparse_index`

**2026-10-12 再变更：缓存机制整体移除**

稀疏索引不再落本地 pkl，改为存进 `search_index` 表的 `sparsevec` 列（pgvector 0.8.7 原生类型），
检索直接用 `<#>`（负内积）在库内完成。

回头看，「内容指纹」其实是在**给本地缓存打工**——要自己算指纹去猜数据变没变。
既然索引能放进数据库、让一致性由 DB 负责，这一层就没有存在的必要了。
本条隐患随之**消失**：不再有「缓存是否过期」这个问题。

| | 旧（pkl 缓存） | 新（库内索引） |
|---|---|---|
| 索引位置 | `data/cache/sparse_index.pkl` | `search_index.sparse_weights` |
| 打分位置 | Python 双重循环全量遍历 | pgvector `<#>` 库内计算 |
| 内存占用 | 8146 条权重常驻（约 7.9MB） | 0（仅模型） |
| 一致性 | 内容指纹手工校验 | 数据库保证 |
| 多实例 | 各存一份 | 天然共享 |
| 更新方式 | 指纹不一致时自动重建 | **需显式重跑构建脚本** |

**代价（必须记住）**：索引更新从「自动」变成了「显式」——
`ingest_data.py` / `ingest_docs.py` 跑完后**必须**重新执行 `tools/build_search_index.py`，
否则检索会静默使用旧索引。目前只在 ingest 脚本里出日志提示，未做成自动触发。

**新的代码锚点**：`db/schema.py` / `tools/build_search_index.py` / `retrieval/sparse_retriever.py::sparse_search`

## P8. Text2SQL 生成耗时

**现象**

走 SQL 路的题目，`text2sql()` 单次调用约 **21s**，占该题总耗时 34.5%，
使 SQL 题相对纯 RAG 题**耗时接近翻倍**。

**实测数据**（`OPT-05`，用重写后的 `tools/profile_pipeline.py`）

| 环节 | 耗时 | 占比 |
|---|---|---|
| 答案生成（LLM） | 31.42s | 52.0% |
| **Text2SQL（LLM）** | **20.85s** | **34.5%** |
| 多路规划（LLM） | 7.45s | 12.3% |
| 检索（3 路） | 0.45s | 0.8% |
| 精排 + 全文扩展 | 0.16s | 0.3% |
| SQL 执行（DB） | 0.06s | 0.1% |
| **合计** | **60.39s** | |

对照组：同一道题在 `need_sql=False` 那一轮，总耗时仅 **28.77s**。

**LLM 调用占 98.9%，本地计算（检索 + 精排 + SQL 执行）合计只占 1.1%。**

> 与 P1 是同一条教训的第二次验证：**优化本地计算毫无意义**。
> 检索并发化最多省 0.45s，精排换模型最多省 0.16s。

**根因**

输出 token 数。模型倾向生成「一次查全」的巨型 SQL——实测样本 **50+ 行、5 个 CTE、
以 `UNION ALL` 拼接多类指标**（人数 + 城市分布 + 品类分布 + 召回建议）：

```sql
WITH churn_def AS (...), churn_diamond AS (...),
     city_top AS (...), category_top AS (...), advice AS (...)
SELECT ... UNION ALL SELECT ... LIMIT 50
```

而 SQL 执行只要 0.06s——**成本几乎全在生成，不在执行**。

**建议方案（按预期收益排序，均需先验证效果不降）**

- ~~**方案 A：把 SQL 生成并入 `plan_queries`**~~ → **2026-10-14 已用数据证伪，不要再尝试**
  实测 5 轮取中位：现状 9.84s vs 合并后 **20.39s（反而慢 10.56s）**，
  且分布更分裂（2.9 ~ 30.5s）。诊断显示合并产出的 SQL 全部只有 1 行、
  无 CTE/UNION（prompt 约束生效），**耗时与输出长度完全无关**
  （输出最短的那次反而最慢）。推测是 prompt 从 1500 字涨到 2400 字后
  prefill 成本上升，而省下的那次往返本来只有 2~3s，净收益为负。
  详见 `bug/10.14/2026-10-14_性能逐模块计时与方案A实验.md`
- **方案 B**：在 `TEXT2SQL_PROMPT` 里限制复杂度（禁止 CTE / UNION / 嵌套子查询），
  多指标拆成多条简单 SQL **并发执行**——本地执行 0.06s/条，拆 5 条也才 0.3s。
  用「多次廉价查询」换「一次昂贵生成」
- **方案 C**：`Text2SQL` 改流式输出 → **不减少总时间**，只是让 SQL 早点可见
- ~~方案 D：优化 SQL 执行 / 给表加索引~~ → **无意义**，本地执行只占 0.1%
- **方案 E（新增）**：换更小的模型单独跑 Text2SQL → 需评估 SQL 质量

**⚠️ 前置条件（2026-10-14 补充）**：本条之上还有一个更根本的问题——
**当前没有可复现的耗时基线**。实测同一 prompt、同样输出量，服务端耗时能差 11~14 倍
（输出 306 字的调用 30.49s，输出 352 字的调用 2.89s）。
在这个前提下，改任何东西跑一次都分不清是改进还是抽到了快的那次。
**建议先建立基线（固定题目连跑 3 轮取中位数），再谈优化。**

**验收标准**：SQL 题平均耗时下降 8s 以上，且 `OPT-05` / `DA-04` / `MGT-01` 质量不变。

**影响面**：所有 `need_sql=True` 的问题。

**代码锚点**：`tools/sql_tool.py::text2sql`、`prompts.py::TEXT2SQL_PROMPT`

**附带修正**：`tools/profile_pipeline.py` 此前用的是已废弃的 `build_query_variants`，
且**完全没有 SQL 路计时**——本次一并重写，覆盖「多路规划 / 检索 / 精排 /
Text2SQL / SQL 执行 / 答案生成」全链路，并区分「LLM 调用」与「本地计算」两类开销。

## P9. 耗时不稳，无可复现基线（已解决）

> ⚠️ **本条最初的根因判断是错的**，保留原文以记录这次误判过程。

**现象**

同一 prompt、同样输出量，LLM 调用耗时能差 **11~14 倍**。
这导致「改完跑一次评测」的方法**完全失效**——无法区分「真的优化了」和「抽到了快的那次」。

**实测数据**（2026-10-14，逐模块计时）

| 调用 | 输出 | 耗时 | 速度 |
|---|---|---|---|
| `OPT-05` Text2SQL | 501 字 | 17.76s | 28.2 字/s |
| `DA-04` Text2SQL | 469 字 | **6.11s** | 76.8 字/s |
| `MGT-01` Text2SQL | 118 字 | 1.58s | 74.7 字/s |

输出量差 7%，耗时差 2.9 倍；全局速度范围 **5.5 ~ 76.8 字/s**。

方案 A 实验中更极端：合并调用的输出 306 字用时 **30.49s**，
而输出 352 字的那次只要 **2.89s** —— **输出更短反而慢 10 倍**。

**❌ 最初的根因判断（错误）**

「服务端排队与吞吐波动，不是代码问题，客户端无法消除。」

这个判断的直接后果是：把它归为**外部不可控因素**，转而建议「先建基线、
接受波动」。**方向从一开始就错了**——波动是客户端可以消除的。

**✅ 真正的根因：思考模式（reasoning）**

`deepseek-flash` 默认**开启了思考模式**。每次调用，模型先输出一大段推理过程
（`reasoning_content`），**这段内容不返回给用户、也进不了答案，但照样消耗时间和 token**。

| 参数 | 耗时 | `reasoning` | completion_tokens |
|---|---|---|---|
| 默认（思考开） | 20.36s | **3466 字** | 2930（reasoning 占 **2197 / 75%**） |
| 显式开思考复测 | 24.29s / 14.57s | 7049 / 2379 字 | 3503 / 2109 |
| **关闭思考** | **7.46s** | **无** | **863** |

**「输出更短反而更慢」的谜团解开了**：那两个调用的**可见输出**确实一个 306 字、
一个 352 字，但**思考内容的长度完全不同**（前者思考得久）。
manifest 出来的时间差异，几乎全部来自看不见的 reasoning。

`reasoning` 长度本身波动很大（2379 ~ 7049 字，**3 倍**），
所以「同一 prompt 耗时差 11~14 倍」的真实来源是**思考长度波动**，不是服务端排队。

**修复（2026-10-14）**

- `config.py` 新增 `ENABLE_THINKING = False`
- `generator.py` 新增 `chat_completion()` 统一入口，
  所有 LLM 调用（`plan_queries` / `text2sql` / `generate` / `generate_stream` /
  `llm_summarize`）统一走它，思考开关在一处控制
- 关闭参数是 `extra_body={"thinking": {"type": "disabled"}}`

**踩坑记录**（都试过，只有第三个有效）：

| 写法 | 结果 |
|---|---|
| `enable_thinking=False` | ❌ 无效，照旧输出 reasoning |
| `thinking=False` | ❌ **422 报错**——服务端要的是 `ThinkingOptions` 结构体，不是布尔 |
| `thinking={"type":"disabled"}` | ✅ 有效 |
| `chat_template_kwargs={"enable_thinking": False}` | ❌ 无效 |

**实测效果**

单次调用（同一问题，连跑 3 次）：

| | 耗时 | 波动 |
|---|---|---|
| 开思考 | 24.29 / 14.57s | **67%** |
| 关思考 | 7.63 / 7.23 / 7.11s | **7%** |

完整评测（20 题）：

| 指标 | `gpu_v14`（开） | **`gpu_v15`（关）** |
|---|---|---|
| 自动判定通过 | 17/20 | **17/20** |
| 来源命中 / 文档命中 | 17 / 13 | **17 / 13** |
| 分板块 | 5/6, 5/5, 4/4, 2/2, 1/3 | **完全相同** |
| **平均耗时** | **28.57s** | **6.30s（-78%）** |

**质量零损失，耗时降一个数量级，波动从 67% 收到 7%。**

**验收标准**：同一配置连跑 3 轮，中位耗时波动在 ±15% 以内。→ **达成（题内波动中位 9%）**

**配套的度量能力（2026-10-14）**：`run_eval.py` 新增 `--repeat N`，并输出
min / 中位 / max 与**题内波动**。同时修了两个会污染统计的坑：

1. **评测一直开着缓存**：`answer_question(q)` 没传 `use_cache`，默认 `True`。
   此前没暴露只因为「每次 `uv run python` 都是新进程 + 20 题互不重复」；
   一加 `--repeat`，第二轮起就会全部命中缓存（0 秒），数据直接作废。
2. **评测从不预热**：第一道题的第一轮包含 bge-m3 与 reranker 的加载，
   实测 `OPT-01` 第一轮 38.26s vs 第二轮 5.03s（差 7.6 倍），
   看着像「LLM 不稳定」，其实是模型加载。

还改了波动指标的口径：原来报「全局极差」，它把**题目之间的天然差异**
（`OPT-05` 本来就比 `EDGE-03` 慢，那是难度差异不是噪声）也算进去了。
判断「测量可不可信」要看**同一题内**的波动。

**影响面**：所有涉及 LLM 的耗时结论与优化验证。

**关联**：`bug/10.14/2026-10-14_性能逐模块计时与方案A实验.md`

**教训**

本条最值得记的不是「关掉思考快了 78%」，而是**误判的路径**：
看到「同输入同输出、耗时差 10 倍」，就归因给「服务端不可控」，
然后停止追查、转而建议「接受波动、先建基线」。

**只要还在说「这是外部因素、我们改不了」，就该多问一句：真的是吗？**
本次真正的答案只是一个 `extra_body` 参数。

## P10. 各路并行检索 + 分来源精排：精排调用次数随路数增长

**背景（质量导向的链路重构，附带记录其成本）**

2026-10-14 将检索链路重构为（设计约定，由需求方明确）：

    每条改写 query 并行 hybrid_search（向量 top20 + BM25 top20 → RRF → top30）
      → 该路 30 条**分来源精排**：画像池 rerank Top-3 + 文档池 Top-2
        （wiki 入选项扩展为父块全文）→ 每路交出 ≤5 条
      → 各路结果**合并、按 id 去重**，直接作为候选
      → 与 SQL 路结果一起进 LLM

3 路 + SQL 的场合进 LLM 的就是 15 条 + SQL 结果；子问题更多按比例增加。
「top3+top2」是分池上限：某一路没有 wiki 候选时就只交 3 条（实测如此）。

**⚠️ 中途走错过一次，记录以免重蹈**

第一版实现把「合并去重」做成了「各路精排后再 RRF 融合」——那是按名次重新
竞争，弱路的第 5 名仅凭名次就能挤掉强路的第 1 名，与「各路头部全部保留、
只去重」的设计意图相反。已按设计约定改回合并去重。
教训与 P1/P8 同源：**结构相似的两件事（融合 vs 合并去重）语义完全不同，
动手前先把预期行为用具体数字说清楚（「3 路就该 15 条」）。**

**现象（成本）**

精排从「融合后 1 次」变为「每路各 1 次」，Cross-Encoder 前向次数随路数
线性增长（3 路 ≈ 90 条候选分池打分）。无整体终选——三层精排没有意义。

并行范围：**检索并行、精排串行**。检索是 DB + BM25，线程池并发安全；
精排是 GPU 前向，多线程同时 predict 同一 CrossEncoder 会争抢 CUDA。
精排每路 30 条约 0.1s，串行无感知成本。

**实测数据**（2026-10-14）

端到端功能验证：

| 场景 | 路数 | 召回 → 各路精排 → 去重 | 入上下文 | 总耗时 |
|---|---|---|---|---|
| 京沪钻石会员对比（+SQL） | 3 | 90 → 9 → 7 | 7 + SQL 4 行 | 17.6s |
| 深圳钻石会员特征 | 2 | 60 → 9 → 8 | 6 画像 + 2 文档 | 5.9s |

完整评测集对比（`--repeat 3`，20 题，`eval_results_v18` vs `v17`）：

| 指标 | v17（重构前） | v18（重构后） |
|---|---|---|
| 自动判定通过 | 17/20 | **17/20** |
| 分板块 | 5/6, 5/5, 4/4, 2/2, 1/3 | **完全相同** |
| SQL 路触发集合 | DA-04, MGT-01, OPT-05, OPT-06 | **相同** |
| 逐题判定差异 | — | **无** |
| 平均耗时 | 4.57s | 5.28s（+15%，见下） |
| 进上下文条数 | ≤5（终选定额） | 4~11（各路 5 条去重） |

**耗时 +15% 归因**（题内波动中位 16%，该增幅部分在波动范围内）：
精排从 1 次（30 条）变为 3~4 次（每路 30 条分池打分）；候选从 5 条
增至约 8 条，context 变长、生成也略慢。本地计算增量约 0.1s/路。

**来源差异 3 题**（OPT-05 / CS-03 / EDGE-03）：均为子查询或扩写路
多带一篇**相关** wiki 进来（如 CS-03 问 U2765 多带 member_benefits.md），
判定未变。这是「各路头部全部保留」的预期行为，不是噪声回归。

**多路共识可见**：同一条资料被多路选中时 `strategies` 合并
（如 `member_benefits.md` 被直接检索 + 关键词扩写两路命中）。

**代价与局限（仍须记住）**

1. **质量持平而非提升**：17/20 与重构前一致，本次重构的收益是
   **候选数量与结构**（单路定额 5 → 各路 5 条去重，子问题的资料不再被
   弱路名次挤掉），自动通过率没有可观测变化。若后续要证明质量收益，
   需要能区分「答得上」和「答得准」的人工评分，当前自动判定做不到。
2. 每路精排用**该路检索式**而非原问题——保留该路意图下的头部是故意的，
   但全局最优没有保障。
3. 候选随路数线性增长，context 长度随之增长（3 路 = 15 条 ≈ 6000 字），
   token 成本与注意力稀释是隐性代价，未量化。

**建议方案**

- 若耗时敏感：调小 `TOP_K_PROFILE` / `TOP_K_WIKI`，或对命中数 < 阈值的路跳过精排

**代码锚点**：`retrieval/query_processor.py::search_variants`、
`config.py::TOP_K_PROFILE` / `TOP_K_WIKI`
