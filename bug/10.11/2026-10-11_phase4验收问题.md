### 1. [严重] `validate_sql` 拒绝合法的 CTE 查询

**现象**

`OPT-05`（高客单用户和普通用户的偏好差异）走 SQL 路由后返回：

```json
{"route": "sql", "rows": 0, "error": "SQL 校验失败"}
```

**根因**

LLM 生成的是一条**完全正确**的 CTE 查询：

```sql
WITH user_groups AS (
  SELECT
    CASE
      WHEN avg_amount >= 1000 THEN '高客单用户'
      WHEN member_level = '普通' THEN '普通用户'
    END AS user_group,
    top_category
  FROM user_profile_vectors
  WHERE avg_amount >= 1000 OR member_level = '普通'
)
SELECT user_group, top_category, COUNT(*) AS user_count,
       ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER (PARTITION BY user_group), 2) AS category_percent
FROM user_groups
WHERE user_group IS NOT NULL
GROUP BY user_group, top_category
ORDER BY user_group, category_percent DESC
LIMIT 50
```

但 `validate_sql` 有两处误杀：

1. **要求 `SELECT` 开头** —— `WITH`（CTE）是合法的只读查询，却被直接拒绝
2. **表名白名单把 CTE 别名当真实表** —— `FROM user_groups` 中的 `user_groups` 是 CTE 别名，不在白名单里

**修复**

```python
# 1. 允许 SELECT 或 WITH 开头（危险操作仍由关键字黑名单拦截）
if not (low.startswith("select") or low.startswith("with")):
    return False

# 2. 表名校验排除 CTE 别名
cte_names = set(re.findall(r"(?:with|,)\s*([a-z_][a-z0-9_]*)\s+as\s*\(", low))
tables = set(re.findall(r"\b(?:from|join)\s+([a-z_][a-z0-9_]*)", low))
invalid = tables - ALLOWED_TABLES - cte_names
```

**回归测试（13/13 PASS）**

```text
PASS | SELECT user_id FROM user_profile_vectors LIMIT 10                          | True
PASS | DROP TABLE user_profile_vectors                                           | False
PASS | SELECT * FROM user_profile_vectors                                        | False  ← 缺 LIMIT
PASS | SELECT * FROM pg_tables LIMIT 5                                          | False  ← 非白名单
PASS | SELECT * FROM user_profile_vectors; DROP TABLE wiki_vectors              | False  ← 注入
PASS | WITH t AS (SELECT city FROM user_profile_vectors LIMIT 10) SELECT ...    | True   ← 新增：合法 CTE
PASS | WITH t AS (SELECT * FROM pg_tables) SELECT * FROM t LIMIT 5              | False  ← 新增：CTE 内查非白名单表
PASS | WITH t AS (SELECT 1) DELETE FROM user_profile_vectors                    | False  ← 新增：CTE + DELETE
PASS | WITH t AS (SELECT 1) UPDATE user_profile_vectors SET age=1               | False  ← 新增：CTE + UPDATE
```

**经验**：放宽规则时必须补**负向用例**，否则可能打开注入口子。这里 `WITH` 放行后，靠关键字黑名单 + CTE 别名排除双层保证安全。

### 2. [严重] `run_eval.py` 绕过意图路由，评测结果失真

**现象**

Phase 3 完成后，`run_eval.py` 的 `run_one()` 仍然是：

```python
cands = hybrid_search(q, top_k=30)
reranked = rerank_by_source(q, cands, top_k_profile=3, top_k_wiki=2)
result = generate(q, reranked)
```

**完全绕过了 `route()`**。照这样重跑，4 条聚合题依然会走 RAG、依然失败，评测结果**不反映真实系统行为**。

**根因**

`/qa` 的分派逻辑写在 `api/main.py` 里，而评测脚本是独立入口，两条路径各写一份逻辑。

**修复**：抽取统一编排入口 `src/rag_demo/pipeline.py`

```python
def answer_question(question: str, dept: str | None = None) -> dict:
    if route(question) == "sql":
        sql_result = sql_tool.query(question)
        return {...}
    candidates = hybrid_search(question, top_k=30, dept=dept)
    ...
```

- `api/main.py` 的 `/qa` → `return answer_question(req.question, req.dept)`
- `tests/run_eval.py` 的 `run_one()` → `result = answer_question(q)`

**经验**：接口层和评测层**不能各写一份编排逻辑**，否则改了一处、另一处悄悄漂移。

### 3. [严重] 入库数据不完整且存在重复

**现象**

Phase 2 验证时 `COUNT(*)` 返回 **1300**（应为 8110），且 `COUNT(DISTINCT user_id)=950`（**350 条重复**）。

**根因（两个叠加）**

1. **进程被中断**：排查 torch 文件锁时，进程列表中有 `PID 33788 python src/rag_demo/ingest_data.py`（占 1.28GB）。当时执行了 `taskkill /PID 33788 /F` 释放 `c10.dll` 锁 —— 该进程 `TRUNCATE` 已执行，但只插入约 1300 条就被杀死
2. **两个 ingest 进程并存**：当时同时存在 `anaconda\python.exe` 和 `.venv\Scripts\python.exe` 两个解释器在跑同一脚本，各自 `TRUNCATE` + 分批 `INSERT` 交错，产生重复行

**修复**：确认无残留进程后重跑 `ingest_data.py`，现为 `8110 / 8110`（零重复、零缺失）。

**教训**

- `TRUNCATE + 分批 INSERT` 的脚本，**中断会留下不完整数据**且不会有任何报错
- 排查文件锁时**不要盲杀进程**，先看它的命令行在做什么
- 同一脚本**不要用两个解释器同时跑**

### 4. [中] 评测指标与双路由架构失配

**现象**

| 指标 | baseline (10-09) | gpu_v2 (10-11) | 变化 |
|---|---|---|---|
| 来源命中 `source_match` | 17/20 | **13/20** | ⚠️ 看似退步 |
| Wiki 预期召回 `wiki_hit` | 14/14（假值） | 10/14 | 数字变差但**变真实** |

**根因**

`source_match` 的算法是 `set(expect_sources) & set(actual_sources)`，而 `expect_sources` 是按**纯 RAG** 设计的。例如 `OPT-05` 期望 `['user_profile', 'tag_definitions.md']`，但它现在走 SQL，实际来源是 `['sql']` —— **交集必然为空**。

这 4 条被"判负"的题目，答案质量其实是最好的：

| ID | 基线（RAG） | Phase 4（SQL） |
|---|---|---|
| DA-04 | "只有 3 个样本，无法确定分布" | 4 档完整分布，792 人 |
| MGT-01 | "无法确定规模" | **398 人** |
| OPT-05 | "只召回 3 个高客单用户，无法对比" | 7 个品类对比 + 占比 |

**修复**

`run_eval.py` 重构为「按路由分流判定」：

```python
def evaluate_result(r):
    route = r.get("route", "rag")
    expect = set(r.get("expect_sources") or [])
    actual = set(r.get("actual_sources") or [])

    r["source_match"] = sorted(expect & actual)
    r["wiki_hit"] = bool({s for s in expect if s.endswith(".md")} & actual)

    if route == "sql":
        # SQL 题：expect_sources 是按 RAG 设计的，套用必然判负
        r["sql_ok"] = bool(r.get("rows_count")) and not r.get("error")
        r["passed"] = r["sql_ok"]
    else:
        # 负样本（expect 为空）无自动判定依据，留给人工
        r["passed"] = bool(r["source_match"]) if expect else None
```

配套改动：

- `run_one()` 补全输出字段 `sql` / `rows_count` / `error`（旧归档缺这三个字段，重算时只能用 answer 措辞启发式）
- 新增 `--recalc` 模式：对已有结果离线重算指标，**不调用模型、不连数据库**
- `summarize()` 按路由拆分统计

**效果**

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 自动判定通过 | 13/20 | **16/20** |
| SQL 路由 | 4 条全判负 | 4 条中 **3 条成功** |

**人工评分校准（重要发现）**

自动判定与人工评分有 **2 条相反**，正好暴露指标设计的边界：

| ID | 自动 | 人工 | 原因 |
|---|---|---|---|
| CS-04 | False | **1** | 验收标准是「若知识库无权益说明，**应诚实说明现有资料未覆盖**」——属**知识缺口题**，正确行为是拒答，不该用来源命中去卡；`expect_sources` 填了 `tag_definitions.md` 是**设错了** |
| DA-01 | True | **0** | 来源命中 `tag_definitions.md`，但答案绕圈子说「无法确认它是正式标签」，没按验收标准正面列出——**来源命中 ≠ 答案正确** |

**结论**

- `source_match` 只是**必要条件**，衡量的是「检索层有没有把料送到」，衡量不了「生成层有没有用好料」，两者必须分开看
- **知识缺口题的 `expect_sources` 应为空**，改用「是否明确声明未覆盖」来校验

### 5. [中] `rerank_by_source` 强制名额塞入无关文档

**现象**

`top_k_wiki=2` 是**硬性名额**——检索池里的 wiki 全都不相关，也会被强制塞 2 条进上下文，既浪费 token，也可能干扰生成：

| ID | 期望来源 | 实际召回 |
|---|---|---|
| OPT-02 | 仅 `user_profile` | `analysis_report_template.md` + `cs_sop.md`（**全无关**） |
| CS-04 | `tag_definitions.md` | `cs_sop.md` + `segmentation.md`（**答非所问**） |

**第一步：实测分数分布（先测量，再定阈值）**

新增 `tools/probe_rerank.py`，实测 bge-reranker-v2-m3 的分数（sigmoid 后）：

| 查询 | wiki 最高分 | profile 最高分 | 说明 |
|---|---|---|---|
| CS-01（优惠券过期怎么办） | **0.810** | 0.001 | wiki 强相关 ✅ |
| OPT-01（高客单美妆女性） | 0.054 | **0.812** | 需 wiki 的「高客单定义」 |
| CS-04（钻石会员权益） | 0.087 | 0.002 | 知识库实际无此内容 |
| OPT-02（深圳钻石会员特征） | 0.005 | 0.001 | wiki 全无关（噪声） |
| DA-01（哪些标签跟美妆相关） | **0.001** | 0.004 | 需 `tag_definitions.md` 作负面证据 |

**实测结论：分数无法区分「噪声」与「低相关但有用」**——OPT-02 的噪声（0.005）比 DA-01 的有用内容（0.001）**还高**。

根因是**粒度错配**：reranker 判断的是「**单个 chunk** 能否直接回答这个问题」，而 DA-01 需要的是「**chunk 集合**能否提供线索」。「高客单定义」这个 chunk 单独看确实答不了「哪些标签跟美妆相关」，给 0.001 是**合理**的。

**第二步：修复**

名额改为**上限而非强制**，参数提到 config 统一管理：

```python
# config.py
TOP_K_PROFILE = 3
TOP_K_WIKI = 2
WIKI_MIN_SCORE = 0.01  # 低于此分不占名额

# reranker.py
reranked_wikis = [
    c
    for c in rerank(query, wikis, top_k=top_k_wiki)
    if c.get("rerank_score", 0) >= min_wiki_score
]
```

顺带把 `pipeline.py` 里硬编码的 `top_k=30 / top_k_profile=3 / top_k_wiki=2` 全部改为读 config。

**第三步：实测效果与权衡**

| ID | wiki 条数 | 影响 |
|---|---|---|
| OPT-02 | 2 → **0** | ✅ 噪声清掉，答案更聚焦（v2 引用了「报告模板把会员等级列为待填写项」等无关内容；v3 直接说明「资料未提供任何会员等级信息」并完整列出 3 位深圳用户画像） |
| DA-01 | 1 → **0** | ⚠️ `tag_definitions.md`（0.001）**被误杀**，丢失「正式标签里没有美妆相关标签」的负面证据，论证变弱 |
| OPT-01 / CS-01 / CS-02 / CS-04 | 无变化 | ✅ 有用文档（0.054 / 0.810）保住 |

全量评测（`--tag gpu_v3`）：自动判定 16/20 → **15/20**（掉的正是 DA-01），平均耗时 9.01s → **8.40s**。

**结论与局限**

- 这是一次**中性偏好**的权衡：方向正确（不再无脑塞噪声），代价可控（DA-01 本就人工判 0）；受影响的题**通过/失败状态都没变**
- **根因未解**：chunk 粒度的 rerank 分数不足以支撑**文档级**取舍。彻底解决要靠 Parent Document 召回（P2 优先级）或引入更强的相关性信号
- **可回退**：把 `WIKI_MIN_SCORE` 设为 `0` 即可完全恢复原行为

### 6. [中] 会员等级未写入 `profile_text`

**现象**

`OPT-02`（深圳的钻石会员都是什么特征）的答案说：

> 资料中没有出现任何用户的「钻石会员」等级标签……上述三位用户虽均为深圳人，**但资料均未标注其会员等级**

**根因**

`member_level` 字段已建列、已建索引、SQL 能查，但 **`build_profile_text()` 的模板里漏了它**：

```python
# 修复前
f"用户{row['user_id']}（{row['user_name']}）：{row['age']}岁{row['gender']}，"
f"{row['city']}人。累计订单{row['order_count']}笔，"      # ← 这里没有会员等级
```

而 `profile_text` 是 RAG **唯一的可见载体**（BM25 语料 + 向量来源 + LLM 上下文）。**字段只入列、不入文本，检索层就完全看不到它**——这是「结构化字段」与「检索文本」双轨设计里最容易漏的一环。

**修复**

```python
f"{row['city']}人，{row['member_level']}会员。累计订单{row['order_count']}笔，"
```

拼成「钻石会员」这类**连续词**，兼顾 BM25 分词与向量语义。改完重跑 `ingest_data.py`（约 7.5 分钟，TRUNCATE + 全量重灌 8110 条 + 重算向量）。

**效果（对比 `OPT-02`）**

| | 修复前 | 修复后 |
|---|---|---|
| 开场 | 「资料中未提供任何用户的会员等级信息，**也没有「钻石会员」标识**」 | 「资料仅提供了 **3 位深圳钻石会员**的脱敏画像」 |
| 召回对象 | 深圳的**任意**用户（实为运动偏好） | **真正的深圳钻石会员** |
| 特征归纳 | 仅「都偏好运动、都活跃1688」 | 年龄/性别/平台/频次/消费/品类/时间**七项** |

修复前是**拿深圳的普通用户去回答「钻石会员特征」**（错配），修复后命中目标人群。

rerank 分数也印证了效果：`OPT-02` 的 profile 最高分从 **0.001 → 0.312**。

**顺带发现**

重跑日志暴露等级分布失衡：

```text
[('钻石', 4787), ('黄金', 1921), ('白银', 910), ('普通', 492)]
```

**钻石占 59%**——因为等级按 `avg_amount`（平均客单价）推导，而该数据集客单价普遍偏高（有用户平均客单价 29420 元）。阈值区分度偏低，若要真实分布需重新标定 `MEMBER_LEVELS`。

### 7. [低] 评测集字段自相矛盾与表述不清

**现象**

**修复**

```json
// CS-04：改为知识缺口题
{"type": "gap", "expect_wiki": false, "expect_sources": [],
 "acceptance": "知识库无会员权益说明，应诚实说明现有资料未覆盖，不得编造权益内容"}

// DA-01：明确要求正面作答
{"acceptance": "对照 tag_definitions.md 已定义的标签（高客单/流失预警/高价值等）给出明确结论，不得只答「无法确定」"}
```

**经验**：**知识缺口题的 `expect_sources` 必须为空**，否则会自动判定为失败；验收标准要写「可判定的行为」，不能只写期望的内容。

**效果**

**顺带踩坑（重要）**

`ingest_docs.py` 的 `print(f"✅ {filename}: ...")` 在 GBK 控制台抛：

```text
UnicodeEncodeError: 'gbk' codec can't encode character '\u2705' in position 0
```

**崩溃点在循环内**，而 `TRUNCATE wiki_vectors` 已在开头执行 —— 结果**只导入了第 1 个文档就中断**，向量库处于残缺状态。已去掉 emoji（`ingest_data.py` 的 `logger.info("🎉 ...")` 同样处理）。

**教训**

- **emoji 不要写进面向终端的输出**——Windows 控制台默认 GBK，日志重定向到 UTF-8 文件时不会暴露，直接跑就炸
- **`TRUNCATE` 型脚本的进度打印必须用 ASCII**，否则一个 `print` 就能让入库半途而废
- 这类崩溃**不会回滚已提交的分批**，事后 `COUNT(*)` 才发现，属于隐蔽故障

### 9. [中] 会员等级分布失衡

**现象**

```text
[('钻石', 4787), ('黄金', 1921), ('白银', 910), ('普通', 492)]
```

**钻石占 59%**，等级几乎无区分度。

**根因**

`MEMBER_LEVELS` 用**绝对金额**（钻石 2000 / 黄金 1000 / 白银 500），而本数据集客单价整体虚高：

```text
p30=1531   p50=2495   p70=4562   p80=6680   p90=10382   p95=14555
```

**p30 就已经超过「高客单 ≥ 1000」的门槛**——绝对阈值在这种分布下必然失效。

**修复**：改为按分位数标定

```python
MEMBER_LEVELS = [("钻石", 14555.0), ("黄金", 6680.0), ("白银", 2495.0)]  # p95 / p80 / p50
```

**效果**

```text
[('普通', 4053), ('白银', 2434), ('黄金', 1217), ('钻石', 406)]
   50%            30%           15%           5%
```

**遗留**：`tag_definitions.md` 的客单口径（高客单 ≥ 1000）对这份数据同样偏松（约 70% 用户满足），属另一个待处理的数据问题。

### 10. [中] Parent Document 召回（解决问题 5 的根因）

**思路**

问题 5 的根因是**粒度错配**：reranker 判断「单个 chunk 能否作答」，而 `DA-01` 需要的是「chunk 集合能否提供线索」。既然分数无法区分（实测已证），就换一条路——**把命中的 wiki chunk 扩展为所在文档的全文**。

**实现**

```python
# reranker.py
def _expand_to_full_doc(items, max_chars=WIKI_MAX_CHARS):
    """命中的 wiki chunk 扩展为所在文档全文；同一文档多个 chunk 合并为一条"""
    ...读 data/docs/<doc_name>，截断到 max_chars...
```

配置：`WIKI_EXPAND_FULLTEXT = True`、`WIKI_MAX_CHARS = 1200`。

**关键便利**：`candidate["source"]` 本来就是 `doc_name`，所以**无需改动 schema 或入库逻辑**，直接在精排后读源文件即可。

**效果（`DA-01`）**

| | 扩展前 | 扩展后 |
|---|---|---|
| 答案中的标签 | 只提到「无法确认它是正式标签」 | **完整列出 7 个标签**（高价值/高客单/中客单/低客单/流失预警/高潜/母婴偏好） |
| 论证方式 | 无法对照，只能回避 | 对照后明确「标签定义中没有美妆相关标签」 |

**整体效果（`gpu_v6`）**

| 指标 | v5 | v6 |
|---|---|---|
| 自动判定通过 | 16/20 | **17/20** |
| RAG 来源命中 | 13 | **14** |
| 期望文档命中 | 10 | **11** |
| 销售/客服板块 | 4/5 | **5/5** |
| 平均耗时 | 9.79s | 11.42s |

**代价**：wiki 上下文变长，平均耗时 +16%。
