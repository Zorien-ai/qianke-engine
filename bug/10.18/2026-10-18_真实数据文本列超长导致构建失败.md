# 2026-10-18 真实数据文本列超长导致构建失败（gender VARCHAR(4)）

## 现象

真实测试者（系统管理员账号）在新版四步向导 `/v2/#/setup` 上传一份真实电商数据
（`customer_shopping_data.csv`，99,457 行 / 6.1 MB），第 3 步构建失败，界面显示：

```
value too long for type character varying(4)
构建失败。注意：画像/文档是**边写边提交**的，失败时库里可能是部分数据；…
```

随后点「重新开始构建」又出现「网络异常，无法连接服务器」——那是当时正在重启后端
（部署窗口），不是新故障；后端恢复后重试即可。

## 根因

数据是 Kaggle 风格的英文电商表：

```
invoice_no,customer_id,gender,age,category,quantity,price,payment_method,invoice_date
I138884,C241288,Female,28,Clothing,5,1500.4,Alipay,5/8/2022
```

`gender` 的取值是 `Female`（6 字）/ `Male`。而画像表建表语句里
`user_profile_vectors.gender` 是 **VARCHAR(4)**（按演示数据的「男 / 女」定的），
`Female` 超长 → PostgreSQL 抛 `StringDataRightTruncation`。

失败发生在 `write_to_db` 的 INSERT 阶段，也就是 **TRUNCATE 之后**：
表已经被清空，用户看到的是「构建失败 + 库里可能只剩部分数据」，代价最大。

同类隐患：`city VARCHAR(50)`、`top_category VARCHAR(50)`、`member_level VARCHAR(20)`
对真实数据也都偏窄（完整地址、多级类目、长等级名都可能超）。

## 修复（两层防护）

1. **聚合阶段截断**：`ingest_data._clip_text` 按 `TEXT_LIMITS` 清洗
   `gender=16 / city=64 / member_level=32 / top_category=64`，
   超长时 warning 记录字段、原长度与保留前缀（不静默、不因一条脏数据整批失败）。
   `member_level` 原有的 20 字截断一并升到 32。
2. **DDL + 旧库迁移**：
   - `db/schema.py` 建表语句同步为新宽度（新库直接正确）；
   - `ingest_data.ensure_schema` 读 `information_schema.columns`，只在旧库列宽不足时
     执行 `ALTER TABLE … ALTER COLUMN … TYPE VARCHAR(N)`（ALTER TYPE 会重建该列索引，
     没必要每次构建都做）；旧库（含 demo / test / 各企业库）在下次构建时自动扩容。
3. **报错翻译**：`write_to_db` 捕获 `StringDataRightTruncation`，回滚并抛中文
   「某个文本字段超过列长度限制…可直接重试，若仍失败请检查超长文本」
   （原始英文错误附在末尾，保留排查线索）。

## 验证

- 单测：`tests/test_ingest_text_limits.py`（8 项）——`Female` 不截断、超长截断留痕、
  空值处理、DDL 与 `TEXT_LIMITS` 一致性、`member_level` 新上限。
- 端到端（8000 真实接口）：取真实 CSV 前 40 行走「上传 → 构建」，修复前必挂的
  `Female` 数据现在成功（40 画像 / 索引 42 / fresh / 4.7s），
  `information_schema` 确认 `gender` 已从 VARCHAR(4) 扩到 VARCHAR(16)，
  写入值 `['Male','Female']` 完整保留；验证后已清空调试库 `test`。

## 备注

- 测试者原上传批次（`7ded39f8b5fb`，99,457 行）**保留**在 `data/uploads/` 下，
  修复后可直接在向导第 3 步重试（首次构建 10 万行量级需要几分钟，属正常）。
- 「重新开始构建 → 网络异常」只在后端重启窗口出现，属预期；任务过期/网络失败时
  向导会给出明确重试提示，不会静默卡死。
