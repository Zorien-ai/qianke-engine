案例 OPT-05「高客单用户和普通用户的偏好差异」

现象：问题里有「多个对象 + 对比诉求」，单次检索只捞得到其中一边的资料，
生成时只能就一边发挥，对比不成立。

根因：一次 query 只产出一个检索意图。多对象、多子诉求的问题，
需要拆开分别找，再合起来看。

解决方向：多路 query（retrieval/query_processor.py）
让 LLM 先判断需要哪几路，再只生成那几路，而不是一律全跑：

- 直接检索    永远执行——它是兜底，不依赖 LLM 判断成功与否
- 子查询分解  含多个对比对象 / 多个子问题 → 拆开分别检索
- 复杂问题简化 口语化、冗长、带无关修饰 → 提炼核心诉求
- 关键词扩写  含专有名词、标签名 → 精确匹配更有效
- 假设答案检索 问法抽象 → 先生成假想答案再拿去检索

各路口召回的候选用 RRF 融合——按**名次**而非分数加权，
避免不同检索器的分数量纲不可比。变体数上限 2 个额外方式，防模型贪心全选。

判断与生成**合并为一次 LLM 调用**：若拆成「先判断、再生成」，反而多一次往返。

现状：已解决。OPT-05 现在直接走 SQL 对比两群的统计口径；
RAG 侧的多路检索作为通用兜底保留。
