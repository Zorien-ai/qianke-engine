## 1. 结论速览

入口路由是**每题都要过**的一段代码，所以它的两个代价必须同时量出来：判错的代价、以及每次多花的毫秒。

| 方案 | 准确率 | 闲聊召回 | 误伤业务 | 漏判闲聊 | 单条延迟 p50 | p95 |
|---|---|---|---|---|---|---|
| 关键词规则（改造前） | 0.6147 | **0.0667** | 0 | **126** | 0.024 ms | 0.034 ms |
| **BERT（GPU，已采用）** | **0.9878** | **0.9852** | 2 | **2** | **18.7 ms** | 27.7 ms |
| BERT（CPU） | 0.9878 | 0.9852 | 2 | 2 | 117.3 ms | 140.7 ms |
| 混合（规则短路 + BERT） | 0.9878 | 0.9852 | 2 | 2 | 18.3 ms | 27.2 ms |

- **准确率**：规则在 135 条闲聊里只拦住 **9 条（6.67%）**——它的精确率是 1.00，但召回率 0.07，等于这一层基本没在工作。换成 BERT 后准确率 0.6147 → **0.9878**，漏判 126 → **2**。
- **延迟**：BERT 单条 18.7 ms，相对它所要避免的 25.2 s 链路只占 **0.074%**；规则是 0.02 ms，但为了省这 19 ms 要多付 3175 s 的 LLM 时间（327 条上）。
- **代价换算**：规则漏判 126 条 × 25.2 s = **3175 s** 白花；BERT 漏判 2 条 = 50.4 s。相当 327 条样本上省下 **3125 s（约 52 分钟）** LLM 时间，代价是每条业务请求 +19 ms。
- **混合模式没有收益**：规则只命中 9/327（2.8%），短路省下约 0.4 ms，落在噪声里（实测 CPU 上 hybrid 反而"慢 3 ms"）。保留它只是为了回退与对照。

## 2. 改造内容

### 2.1 判定链路

```text
改造前：question → [关键词规则] → chitchat → 固定回复
                              → rag     → 多路规划 LLM → 检索 → 生成

改造后：question → [BERT 二分类] → chitchat → 固定回复
                               → rag     → 多路规划 LLM → 检索 → 生成
                                  ↑ 规则仍在，但只在「模型不可用」或 INTENT_ROUTER=rule 时生效
```

**决策语义完全不变**：命中即 `chitchat`，返回固定回复、不检索、不生成。改动只发生在「谁来判」这一层，下游 `pipeline.answer_question` / `prepare` 的 `route()` 接口未变。

### 2.2 为什么不是「交给 LLM 判」

那一层存在的全部理由是**省掉两次模型推理**。如果闲聊也要付一次 LLM 往返，这个理由就消失了——实测 LLM 多路规划单次 3.8 s，比 BERT 的 18.7 ms 差 200 倍。只有在本地能判、且判得准时，入口拦截才划算。

### 2.3 为什么保留规则（且不是死代码）

1. **模型目录不入库**（`bert_query_classify/models/` 在 `.gitignore` 里，需先跑 `train.py`）。新环境未训练时自动回退规则，服务不中断——只是准确率掉回 0.61。启动日志会有一条 warning。
2. `INTENT_ROUTER` 可切 `"rule"` / `"hybrid"`，规则是回退开关，也是本对比的基线。
3. `hybrid` 模式下规则先短路，命中即返回，省掉那次 BERT 前向。

### 2.4 两个必须遵守的实现约束

1. **必须在服务启动时预加载**（`api/main.py` lifespan，与 `get_model` / `get_reranker` 同批）。
   实测（2026-10-15）：请求期间首次加载模型会拿到**半转换的 fp16 模型**（权重 fp16 / 输入 fp32），首次 forward 抛 `mat1 and mat2 must have the same dtype`，且该进程此后**每次**调用都失败，重启才恢复。触发条件是「加载时还有其他 CUDA 活动」。
   与两个检索模型不同的是：**它加载失败不影响可用性**——router 回退规则，所以 `preload()` 不抛异常。
2. **加载失败要缓存**，不能每次请求重试：重试必然失败，却要为每个请求白付约 1 s 的加载尝试——那比漏判本身更糟。`bert_intent` 把失败原因记一次日志后一直返回 `None`。

## 3. 评测方法

### 3.1 数据集（327 条，均带真实标签）

| 组 | 条数 | 构成 | 作用 |
|---|---|---|---|
| `test` | 272 | 闲聊 135 / 业务 137，与训练同分布 | 主指标 |
| `short_probe` | 30 | 全业务，2~6 字（`U2765`、`看下GMV`） | 专测**误伤**：判错就是拒答真问题 |
| `long_probe` | 25 | 全业务，19~22 字 | 专测误伤（长端） |
| 合计 | 327 | 闲聊 135 / 业务 192 | — |

把「判定为闲聊」视为正类（= 拦截动作）：

| 结果 | 含义 | 代价 |
|---|---|---|
| TP 正确拦截 | 闲聊被拦下 | **省** 25.2 s |
| FN **漏判** | 闲聊进链路 | **浪费** 25.2 s，但答得出来 |
| FP **误伤** | 业务被拦成闲聊 | **拒答真问题**，用户直接受损，且无法用时间衡量 |
| TN 正确放行 | 业务正常走链路 | — |

### 3.2 延迟口径

- **单条逐次调用**（生产形态：一问一次前向），不是批量吞吐。
- **CUDA 同步**：`torch.cuda.synchronize()` 包住计时区间。CUDA 是异步的，不同步测到的是「提交内核」的时间，不是「算完」的时间。
- 预热 10 条后再计时（首次调用含 CUDA 上下文初始化）。
- **以 p50 为主口径**：单遍 327 样本的均值会被 GPU 时钟/后台负载带偏。同一脚本 3 次运行的单条均值分别是 15.8 / 16.2 / 20.0 ms（相对 16 ms 约 12% 波动），p50 更稳。
- `batch32` 只作离线参考（本报告末尾），不代表线上。

### 3.3 代价换算常数（估算值，出处可查）

来自 `bug/10.14/2026-10-14_性能逐模块计时与方案A实验.md` 的逐模块实测：

| 环节 | 耗时 | 说明 |
|---|---|---|
| LLM 多路规划 | 3.8 s | 每题都有（`plan_queries`） |
| 本地检索 + 精排 | 0.5 s | 向量 + BM25 + RRF + CrossEncoder |
| LLM 答案生成 | 20.9 s | 最大头 |
| **合计** | **25.2 s** | 一次「不该走却走了」的完整代价 |

> 这三个数是 LLM 侧的历史实测值，会随 API 波动；本报告只用它做**量级**换算，不是精确值。

## 4. 准确率对比

### 4.1 总览

| 方案 | 准确率 | 精确(闲聊) | 召回(闲聊) | TP 正确拦截 | FN 漏判 | FP 误伤 | TN 正确放行 |
|---|---|---|---|---|---|---|---|
| rule | 0.6147 | 1.0000 | 0.0667 | 9 | 126 | 0 | 192 |
| **bert** | **0.9878** | 0.9852 | 0.9852 | 133 | 2 | 2 | 190 |
| hybrid | 0.9878 | 0.9852 | 0.9852 | 133 | 2 | 2 | 190 |

### 4.2 分组明细

| 组 | n | rule 误伤/漏判 | bert 误伤/漏判 | hybrid 误伤/漏判 |
|---|---|---|---|---|
| test | 272 | 0 / 126 | 0 / 2 | 0 / 2 |
| short_probe | 30 | 0 / 0 | **2 / 0** | **2 / 0** |
| long_probe | 25 | 0 / 0 | 0 / 0 | 0 / 0 |

两侧的错误分布很干净：
- **规则的全部错误集中在 test 组的漏判**（126 条），探针上零错误——因为它几乎从不判闲聊，所以也就从不误伤。
- **BERT 的误伤全部落在 short_probe**（2 条），test / long 组零误伤。

### 4.3 规则为什么这么差

规则只有两个抓手：「短句 + 含寒暄词」与「域外话题名词 + 疑问形态」。而 test 组闲聊里绝大多数既没有寒暄词、也不在域外话题表里：

```text
闰年是怎么回事        口红哪个色号好看      弗洛伊德是谁        怎么养猫
昨天睡得好吗          怎么存钱              你会做梦吗          怎么穿搭
地球为什么是圆的      丝绸之路最早是哪个朝代开辟出来的        焦虑
```

这些在语义上毫无歧义（都是闲聊），但词表里一个词都没有。**规则漏判的 126 条闲聊，BERT 在门槛 0.9 下拦回 124 条（98.41%）**——这正是换模型的价值所在。

同时注意规则的 `precision = 1.00`：它不是"判得不准"，而是"几乎不判"。**只看精确率会把规则误读成完美方案**，这是本表必须同时给召回率的原因。

### 4.4 BERT 的 4 个错误（全部为已知短板，与训练期评估一致）

**误伤（2 条，均为短探针）**

| query | 组 | p_chitchat |
|---|---|---|
| 看下GMV | short_probe | 0.9969 |
| U2765 | short_probe | 0.9962 |

**漏判（2 条）**

| query | 组 | p_chitchat |
|---|---|---|
| 闰年是怎么回事 | test | 0.71 |
| 收到 | test | 0.017 |

这 4 条与 `bug/bert模型训练.md` §5 记录的评估错误**完全重合**（分布外短探针错例 `U2765` / `看下GMV`、测试集唯一错例 `收到`、最低置信样本 `闰年是怎么回事`）。说明：

1. 路由层的错误**不是新问题**，是分类器固有短板在入口的暴露；
2. 换一层「用法」不会改善模型能力——要修得回去补训练数据（见 §7）。

`闰年是怎么回事` 值得单独说：它 p=0.71，是全场最接近门槛的样本，也是训练期置信度最低的样本（0.7098）。模型对它只有 0.71 的闲聊置信度——**这类"通用知识问题"在训练集里覆盖不足**。

## 5. 门槛怎么定：0.9 而不是 0.5

### 5.1 扫描结果

| 阈值 | 准确率 | 误伤 | 漏判 | 正确拦截 | 误伤率(业务) | 漏判率(闲聊) |
|---|---|---|---|---|---|---|
| 0.5 | 0.9908 | 2 | 1 | 134 | 0.0104 | 0.0074 |
| 0.6 | 0.9908 | 2 | 1 | 134 | 0.0104 | 0.0074 |
| 0.7 | 0.9908 | 2 | 1 | 134 | 0.0104 | 0.0074 |
| 0.8 | 0.9878 | 2 | 2 | 133 | 0.0104 | 0.0148 |
| **0.9（采用）** | 0.9878 | 2 | 2 | 133 | 0.0104 | 0.0148 |
| 0.95 | 0.9878 | 2 | 2 | 133 | 0.0104 | 0.0148 |
| 0.99 | 0.9847 | 2 | 3 | 132 | 0.0104 | 0.0222 |

### 5.2 三个读数

1. **误伤不随门槛变化**：0.5 → 0.99 之间始终是 2 条。那两条（0.9969 / 0.9962）是**高置信误判**，抬门槛根本解决不了——它们比绝大多数真闲聊的置信度还高。想靠调阈值消灭误伤是徒劳的。
2. **漏判随门槛上升**：0.71 → 0.9 之间多丢 1 条，0.99 时丢 3 条。
3. 因此在本数据集上，**0.5~0.7 严格占优**（误伤同、漏判少 1）。唯一被 0.7 捞回的是 `闰年是怎么回事`（p=0.7076），余量仅 **0.0076**。

### 5.3 结论：仍然选 0.9，理由是「代价不可逆」

两个方向的代价不对称，而且**兜底通道只对一侧有效**：

- 漏判（闲聊→业务）：多走一次检索 + 生成，浪费 25.2 s，**但答案是对的**；且 `query_processor` 的路由复核（复用已有的多路规划 LLM 调用）有机会把它改道成闲聊——**存在免费兜底**。
- 误伤（业务→闲聊）：直接拒答真问题，用户受损；而 BERT 这一层**没有任何兜底**——`query_processor` 的复核只在「已判 RAG」的分支里才执行，捞不回已经被拦掉的请求。

在「一侧可免费兜底、另一侧不可逆」的前提下，把门槛设在保守方向是合理的。**风险边界已经贴边**：业务侧最高 p_chitchat = 0.9969，门槛余量为 **-0.0969（已为负）**——即已经有业务样本越线。这也说明当前的主要风险不是「门槛太低」，而是那 2 条短探针本身就是模型的盲区。

（若后续补了短样本训练数据、误伤降到 0，再回来把门槛下调到 0.7~0.8 是合理的下一步。）

## 6. 延迟对比

### 6.1 单条延迟（生产形态）

| 方案 | p50 | 均值 | p95 | 最大值 | 相对 25.2 s 链路 |
|---|---|---|---|---|---|
| rule（同一台机器，纯 CPU 计算） | 0.0239 ms | 0.0250 ms | 0.0337 ms | 0.26 ms | 0.0001% |
| **bert（GPU fp16）** | **18.70 ms** | 20.04 ms | 27.75 ms | 42.41 ms | **0.074%** |
| bert（CPU fp32） | 117.32 ms | 116.68 ms | 140.66 ms | 157.82 ms | 0.466% |
| hybrid（GPU） | 18.34 ms | 18.98 ms | 27.18 ms | 48.90 ms | 0.073% |

> 采样次数：rule 3270 次（GPU 机）/ 1635 次（CPU 机）；bert 与 hybrid 各 981 次（GPU，3 遍）/ 327 次（CPU，1 遍）。

### 6.2 四个读数

1. **跨运行方差大于方案间差异**。同一脚本 3 次运行的单条均值 15.8 / 16.2 / 20.0 ms，p50 18.7 ms。所以：
   - 「rule 0.024 ms vs bert 18.7 ms 差 800 倍」这个倍数关系本身没错，但绝对值的精度只有量级可信；
   - **hybrid 与 bert 的 0.3 ms 差异无意义**——落在噪声里（GPU 时钟、后台进程都会带来 2~4 ms 抖动）。
2. **把两个数量级放在同一把尺子上**：对 25.2 s 的链路，19 ms 是 0.074%，CPU 上的 117 ms 是 0.466%。也就是说，即便退到 CPU 部署，这个判定器的开销也只有链路的千分之五——**它不是性能问题，是「别白跑 25 秒」的问题**。
3. **CPU 比 GPU 慢 6.3 倍**（117.3 vs 18.7 ms），batch32 下单条差 **40 倍**（32.42 ms vs 0.81 ms）。原因是单条推理的瓶颈在 kernel launch 与 padding，不在算力——line by line 的 327 次前向无法摊薄启动成本。**推论**：如果服务最终跑在 CPU 上，应当把路由改成批量/缓存形态（见 §7），否则 117 ms × 每题会变成可感知的固定开销。
4. **显存代价可以忽略**：fp16 实测模型净增 **202.1 MB**（推理后峰值分配 210.5 MB、缓存池 214.0 MB）。与 bge-m3 + bge-reranker 约占的 4.4 GB 相比是个零头，6 GB 卡放得下——但前提是**加载时机**正确（见 §2.4，与检索模型同一批加载，避免半转换 fp16）。

### 6.3 收益端：拦住闲聊省下多少

| 项 | 值 |
|---|---|
| 规则漏判 | 126 条 → 浪费 **3175.2 s** |
| BERT 漏判 | 2 条 → 浪费 **50.4 s** |
| 327 条样本合计省下 | **3124.8 s（≈52 分钟）** |
| BERT 自身总开销（327 条 × p50） | 6.1 s |
| 性价比 | 花 6 s 换回 3125 s，**约 512 倍** |

> 注意这个换算只在「有大量闲聊流量」时成立。若线上闲聊占比很低（例如 1%），收益端会按比例缩水，而 19 ms/题的成本是**每题都付**的——这也是为什么必须把两个数放在一起看。

## 7. 风险与遗留

| # | 问题 | 影响 | 建议 |
|---|---|---|---|
| 1 | **2 条短探针误伤**（`U2765`、`看下GMV`，p≈0.996） | 拒答真问题，且抬门槛无效 | 补「字母/数字 ID + 极短业务词」难样本重训（与训练文档 §9 同一件事） |
| 2 | **误伤无兜底通道**（架构性） | 一旦判错就是拒答 | 可考虑：BERT 判闲聊且命中业务关键词表时放行（规则反向复用），或对低置信区间走原 LLM 复核 |
| 3 | CPU 部署 117 ms/题 | 每题固定开销涨 6 倍 | 若必须 CPU：加 LRU 缓存（重复 query 直接命中）、或退到 hybrid/规则 |
| 4 | **模型目录不入库** | 新环境自动回退规则，准确率掉到 0.61，且只有一条 warning | 运维需知：`INTENT_ROUTER=bert` 但日志出现「意图分类模型不可用」时，实际生效的是规则 |
| 5 | 门槛 0.9 在本数据集上略逊于 0.7 | 多丢 1 条闲聊（浪费 25.2 s） | 已在 §5.3 论证保留；补数据后重评 |
| 6 | 数据集 327 条，规模有限 | 置信区间宽（误伤 2/192，真实误伤率的 95% 上界不低） | 与训练文档同一问题：先补难样本，再扩大评测集 |
| 7 | `query_processor` 的路由复核仍然存在 | 它只能捞漏判、捞不回误伤 | 文档已明确；不要误以为「下游有兜底」就等于误伤无害 |

## 8. 复现

```bash
# 1) 对比实验（GPU；CPU 加 --device cpu）
uv run python src/rag_demo/bert_query_classify/bench_router.py

# 2) 只跑 CPU 一套（输出到独立文件，避免覆盖 GPU 结果）
uv run python src/rag_demo/bert_query_classify/bench_router.py \
    --device cpu --bert-passes 1 --out src/rag_demo/bert_query_classify/outputs/router_compare_cpu.json

# 3) 切换路由方案（改 config.INTENT_ROUTER 或临时覆盖：
#    "bert" 默认 / "hybrid" 规则短路 / "rule" 回退对照）
```

脚本产出：`outputs/router_compare.json`、`outputs/router_compare_cpu.json`，含三方案的逐组混淆、门槛扫描、错误归因（含每条错误样本的 `p_chitchat`）、业务侧风险余量。
