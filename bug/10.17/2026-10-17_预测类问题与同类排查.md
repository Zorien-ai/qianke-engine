# 预测类问题：能力边界，以及「demo 规则当系统规则」的同类排查（2026-10-17）

起点是一句反问：**如果数据能预测未来，你答不答？**

这篇不给「能/不能」的结论，只把三件事说清：现在预测题实际走到哪一步、
要走通还缺什么、以及仓库里还有多少同类问题（把「当前数据的现状」写成了「系统的规则」）。

---

## 一、先分清两件事

「SQL 路答不了预测题」有两个完全不同的原因，现在代码里被混成了一件：

| 缺陷 | 具体表现 | 换成有时间序列的数据后 |
|---|---|---|
| **数据缺能力** | 库里没有事实级时间序列，只有聚合后的画像快照 | 可能解决 |
| **方法冒充结论** | 用 `SUM/AVG` 算出历史均值，起名 `predicted_gmv` 当结论汇报 | **永远不解决** |

第二条跟数据有没有时间序列**无关**。哪怕有十年日粒度流水，`AVG` 也只是重述历史；
它缺的不是数据，是外推方法。

现在的实现把这两条都塞进了同一个动作里：

```94:105:src/rag_demo/retrieval/query_processor.py
def looks_predictive(question: str) -> bool:
    """
    问题是否属于「预测 / 未来时点 / 反事实推演」——SQL 路无法回答的那一类
    ...
```

```240:246:src/rag_demo/retrieval/query_processor.py
    sql_blocked = False
    if need_sql and looks_predictive(question):
        logger.info("SQL 判定复核：问题属预测类，关闭 SQL 路 -> %s", question)
        need_sql = False
        sql_blocked = True
```

注意第 243 行：这个判断**不查任何数据**。换成一个有完整时间序列的库，
它照样关掉 SQL 路。上一轮把 `MULTI_QUERY_PROMPT` 里的时间能力动态化了，
但这条硬复核没动——现在它是「用 demo 的数据属性，永久关掉一条能力」。

## 二、实测：预测题现在走到哪一步

2026-10-17 实跑（临时脚本已删）：

| 问题 | `looks_predictive` | LLM 判 need_sql | 硬复核 sql_blocked |
|---|---|---|---|
| 预测明年 GMV 会是多少 | True | **False** | **False** |
| 如果发 100 万张券，GMV 会增长多少 | True | **False** | **False** |
| 明年会员等级会不会调整 | True | **False** | **False** |

**关键发现：硬复核一次都没触发。** 因为 `MULTI_QUERY_PROMPT` 里已经写明
「预测 / 推演 / 假设 / 未来时点类问题**必须写不需要**」，模型自己就把 SQL 路关掉了。

这条比预想的重要：**要让预测题走到 SQL 路，改 `looks_predictive` 不够，
提示词第 164 行那条「必须写不需要」也得一起改**，否则能力接了也用不上。
两层拦截，改一层等于没改。

## 三、更隐蔽的问题：关掉 SQL 不等于拒答

同一轮实测里，「预测明年 GMV」的完整答案（节选）：

> 明年 GMV 具体数字没法从现有资料里推出来……**从现有用户样本看，明年 GMV 的增长支撑
> 主要靠少数高客单用户**，样本本身不足以做大盘预测。
> - 资料里只有 3 个用户画像，累计消费分别是 19504 元、7537 元、4339 元

没有编数字，这一步是对的。但它**用 3 条画像推出了「明年增长的支撑结构」**，
还带着 `[资料1][资料2][资料3]` 的来源标记。对不细看的用户来说，
这段话和「结论」没有区别——它以「推断」的形式输出了预测的结论形态。

所以「拒答预测题」不是关掉 SQL 就完事：
**RAG 路同样能用样本讲趋势**。这条不写进提示词约束，光靠 SQL 侧拦截是个假防线。

## 四、如果数据真能预测：答，但要三个条件

我的立场：**「数据能预测未来」这句话本身不成立**。能成立的表述是
「用某个方法从数据里外推出一个带误差范围的估计」。说得清方法才叫回答。

| 条件 | 具体要求 | 缺了会怎样 |
|---|---|---|
| **数据前提** | 有按日/按月的**事实级**流水（订单行），不是聚合后的画像 | 现在的 `days_since_last_buy` 是相对天数，把时间压成了一个点，天然不可外推 |
| **方法可辩护** | 明确的方法：移动平均 / 同比环比 / 线性趋势 / 分位数区间。方法本身要能写出来 | 说不清方法的「预测」等于把历史数字往后挪一格 |
| **输出有边界** | 必须给**区间**不给点值；标注训练窗口与样本量；少于 3 个周期不外推 | 点值会被当成承诺，区间才会被当成估计 |

三档策略（按缺什么给不同回复，不要一律「无法回答」）：

| 情况 | 回复 |
|---|---|
| 数据、方法都有 | 答，附区间 + 方法 + 窗口 + 样本量 |
| 有数据没方法（有流水但没定口径） | 说明能算哪些描述性趋势（同比/环比），但仍不做外推 |
| 数据和方法都缺 | 明确说「不能预测」，并**说清缺的是哪一层** |

## 五、改造方案（分三步，别一次全做）

### 第 1 步：把「能力」变成可探测的

`schema_facts.get_time_capability()` 已经在做「有没有时间序列」的判定，
扩展成 `forecastable()` 即可：有时间列 + 有事实行 + 覆盖周期数 ≥ 3。

### 第 2 步：提示词按能力分叉

`MULTI_QUERY_PROMPT` 里「必须写不需要」改成条件式：

- 无时间序列 → 保持现在的写法（必须写不需要）
- 有时间序列 → 允许判「需要」，但限定为「描述性趋势」，禁止外推

**这一步和第 3 步必须一起改**，否则第 1 步的能力永远走不到。

### 第 3 步：独立的 forecast 通道

不要塞进 `sql_tool`。理由：SQL 的职责是「取数」，预测的职责是「建模 + 给区间」，
两者的安全边界（只读 SELECT vs 方法白名单）完全不同。

- 工具层：方法白名单（移动平均 / 同比 / 线性趋势），每个方法强制返回区间
- 校验层：禁止 `SELECT ... AS predicted_*` 这类「聚合冒充预测」的写法（已有规则可复用）
- 生成层：结果必须带四件套——方法名、训练窗口、样本量、区间

### 验收

| 验收项 | 判定 |
|---|---|
| demo 库（无时间序列） | 行为不变：3 道预测题仍 `need_sql=False`，答案不含预测数字 |
| 构造一份带 12 个月流水的测试库 | 预测题走 forecast 通道，答案含区间与方法，不含点值 |
| 只有 1~2 个周期的库 | 明确拒答并说明「样本周期不足」，不硬算 |
| 有流水但问的是「明年会不会被收购」这类外部事件 | 拒答，且不借样本编趋势（对应第三节） |

## 六、同类问题排查

判断标准一句话：**这条规则的依据是「系统不变量」，还是「当前这份数据的现状」？**
后者一旦写进代码/提示词，换数据就会错，而且错得不像 bug、像结论。

### A. 确认的同类（还没修）

| # | 位置 | 固化了什么 | 换数据后的表现 |
|---|---|---|---|
| 1 | `query_processor.py:243` + `prompts.py:164` | 「本库无时间序列」→ 预测题永久关 SQL | 有时间序列的库也用不上（本文主题） |

### C. 协议的孤儿（同类，性质不同）

`TEXT2SQL_PROMPT` 规则 9 约定：无法预测时输出
`SELECT '数据不支持预测：库内无时间序列' AS message LIMIT 1`，
再由 `SQL_SUMMARY_PROMPT` 第 7 条「照实转述」。

但全仓搜索这个字符串，**只有提示词里出现**，代码里没有任何解析。
也就是说这是一条**只靠 LLM 自觉遵守的字符串协议**：模型改写措辞、换语言、
或者把它和其他结果混在一起，下游没有任何兜底。

要么在代码里解析这个字段并接管输出，要么承认它只是提示词里的软约定，
不要写成像是有契约一样。现在这种「半契约」状态最危险。

## 七、今后怎么防

一个提问就够了：**去掉这份 demo 数据，这条规则还成立吗？**

- 成立（如「只读、必须带 LIMIT」「枚举值要加引号」）→ 写在代码/提示词里没问题
- 不成立（如「快照日是 2024-12-30」「平台只有这 6 个」「高客单是 1000 元」）
  → 必须来自运行时采集，或者做成带启用条件的开关

已经按这个原则改掉的有：`SQL_SCHEMA` 的条数/枚举/分位、`MULTI_QUERY_PROMPT` 的时间能力。
没改的列在第六节 A 里。
