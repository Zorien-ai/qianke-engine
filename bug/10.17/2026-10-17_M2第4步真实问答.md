# M2 第 4 步：查询接真实 pipeline（2026-10-17）

## 一、这一步做了什么

一句话：**向导第 4 步不再返回内置样例答案**。真人上传自己的数据、等构建跑完，问到的必须是他那批数据的答案。

| 改动 | 说明 |
|---|---|
| `mvp/app.py` 的 `/query` | 走与首页 `/qa` **同一条** pipeline（意图路由 → 多路检索 → 精排 → 生成），按请求把当前数据集切到用户构建的那个库；响应带 `route` / `cached` / `elapsed_ms` / `dataset` |
| **整段问答持锁** | 原先是「试探一下就放」。M1 时答案是内存里的假文本，放锁没有代价；现在一次问答要真读库几秒，留的窗口足以让构建挤进来共用同一条 psycopg2 连接（非线程安全），报错还会在用户点击的瞬间随机炸 |
| 构建成功后**清空问答缓存** | 缓存键是 (数据集, 问题, 检索参数)，**不含数据版本**。不清就会出现「明明换了数据，提问却秒回上一版的答案」，而且看不出是旧的 |
| `mvp/mock_data.py` | 删掉假答案与假示例文件清单，只留字段字典 / 构建步骤 / 示例问句（假数据留着就是第二处真源，早晚有人改错一处） |
| 前端 | 来源卡片按真实的 `source` / `text` 渲染；显示耗时与「查的是哪批数据」；三种「答不出来」（检索侧 / 大模型侧 / 闲聊）分别提示；页脚不再自称「原型」 |

**不做按角色裁剪**（`permissions.render`）：向导是一条独立业务线，操作者是这批数据的主人——他手里本来就有 CSV 和 `.md` 原件，来源片段对他是自查凭据而不是越权信息。等向导接入登录态时再统一收口。

## 二、走 3 遍完整流程（每遍换数据）

刻意选了三种**输入组合**，它们对应三条不同的构建语义：

| 遍 | 输入 | 覆盖的语义 | 实测 |
|---|---|---|---|
| 1 | 淘宝 + 1688 两个 CSV（含一个多出来的列）+ 三篇文档，**不传 dataset** | 两表合并 / 未识别列警告 / 默认数据集 user | 700 行 → 616 个用户、索引 633 条，48s |
| 2 | **只传两个文档** | 画像三步跳过、且不碰上一批画像 | 6.0s，三步 `skipped`，画像条数不变 |
| 3 | **只传一个 CSV**（1200 行，文件名不是已登记平台） | 文档步骤跳过、不碰上一批文档、未登记来源 | 1122 个用户、索引 1136 条，74s |

第 3 遍那条特别值：文件名不在已登记平台清单里，画像 `platforms` 被记为「**未标注来源**」——不拿文件名冒充平台。

## 三、走流程时抓到 3 个问题

### ① 检索线程池丢数据集（会答错数据，最严重）

**现象**：向导切到 `user` 库提问，回来的来源里出现了只存在于 `test` 库的文档。

**根因**：检索是 `ThreadPoolExecutor` 并行跑的，而 `concurrent.futures` 的线程**不继承 contextvar**。本项目靠 contextvar 传「当前数据集」（见 `db/connection.py`），于是所有检索线程都拿到默认值 → **安静地打到 demo 上**。

**为什么一直没暴露**：`/qa` 本来就查 demo，看不出任何异常；只有「切到别的库」的调用方（向导）才会撞上，而且**不报错**——答案看着很正常，只是不是他那批数据的。`connection.py` 里其实早就警示过「自己 new 的 Thread 不继承 contextvar」，但只覆盖了构建线程，线程池这条漏了。

**怎么证的**：
- 一份 8 行诊断脚本对比三种写法：端点线程里 `use_dataset` 生效 ✓ / 线程池里直接看 = demo ✗ / 调用方取拷贝再传 = user ✓
- 端到端：造一份**本轮独有**的文档（文件名 + 内容里的 999 元礼遇），修前答不出、修后来源与答案都对上

**修法**：提交时带一份 `contextvars.copy_context()`。必须**逐任务** copy——同一个 Context 不能被两个线程同时进入。

### ② 只传文档时构建被 400 拦住（一道无解的关卡）

**现象**（实测）：只上传两篇文档 → 构建返回 `400 「用户ID」还没选对应的列…请回到上一步选择`。而第 2 步的下拉框里**一个列都没有**（没有 CSV），用户照做也做不到。

**与设计意图矛盾**：`app.py` 里紧跟着的注释写着「只传文档、没有交易数据：仍允许构建（文档问答本来就不需要画像）」——被上面那道必填检查先拦掉了。

**修法**：必填字段检查只在**有 CSV** 时做。顺带修掉同一场景下的一条**假警告**（「关键字段未识别到，建议手动指定：用户ID」）——没有列可选时这句话无解，假警告比没有警告更伤人。

### ③ 完成提示拿交易行数冒充画像条数

第 1 遍的完成提示是「构建完成：画像 **700 行**、索引 633 条」——700 是清洗后的**交易行数**，真实画像是 **616 个用户**。没传 CSV 时更糟：「画像 **0 行**」，读起来像「画像被清空了」，实际是「本次没重建」。

**修法**：构建结果同时带 `rows` 与 `profiles`（`profiles: None` 表示「没重建」，与「重建出 0 个用户」是两件事），提示分两种说法：

- `构建完成：画像 616 个用户（来自 700 行交易），索引 633 条…`
- `构建完成：本次只更新了文档（未重建画像，上一批画像保持不变），索引 1,136 条…`

## 四、验证

| 范围 | 项数 | 结果 |
|---|---|---|
| 第 4 步接真实问答（换数据：京东 + 拼多多 2000 行 + 一份独有指纹文档） | 38 | 全绿 |
| 3 遍完整流程（三种输入组合） | 43 | 全绿 |

两个临时脚本已删。**`demo` 全程零改动**：画像 8110 / 文档 36 / 索引 8146，每轮留底都一致。

第 4 步那份还覆盖了：缓存命中、**重建之后缓存必须失效**、构建期间查询被拒、**问答进行中构建被拒 409**、查 demo 被白名单拒 400。

**测法上的两个坑**（都不是代码问题，记下来省下次的时间）：

1. 指纹文档选成了「demo 库里也有的」——那个断言等于没写，是这次真 bug 能藏住的原因
2. 并发那段先等 4 秒再点构建，而一次问答实测只要 3~5 秒，问答早结束了 → 构建被正常受理（假通过）
