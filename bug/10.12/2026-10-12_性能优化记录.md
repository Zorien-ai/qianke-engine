# 性能优化记录（2026-10-12）

> 本文档记录一次完整的性能优化：**先测量、再定方案、实施、验证**。
> 其中包含**一项优化未达预期**的如实记录。

---

## 一、触发原因

界面上同一个问题，三种关键词策略的耗时差异明显：

| 策略 | 界面实测耗时 |
|---|---|
| BM25 | 19.3s |
| BGE-M3 稀疏向量 | 27.1s |
| 两者组合 | 30.7s |

**相差 11.4s**，而检索环节此前实测只有 0.5s 左右——差异无法用检索解释。

---

## 二、瓶颈定位（先测量，不猜）

新建 `tools/profile_modes_compare.py`，把一次问答拆成五段，在同一进程、同一题目下逐段计时，三种策略共享同一次变体生成：

```
策略      检索    融合   精排    生成    合计   答案字数  每字耗时
bm25     0.35s  0.00s  0.32s  8.51s   9.19s    409     20.8ms
sparse   0.51s  0.00s  0.15s 11.73s  12.39s    827     14.2ms
both     0.47s  0.00s  0.16s 16.10s  16.73s    454     35.5ms

最快 bm25(9.19s) vs 最慢 both(16.73s)，差 7.54s
其中：生成环节差 7.59s，检索环节差 0.12s
→ 耗时差异的 101% 来自「生成」
```

### 结论

| 环节 | 耗时 | 占比 | 判断 |
|---|---|---|---|
| **LLM 生成答案** | 8.5~16.1s | **92~96%** | 🔴 **唯一真瓶颈** |
| 检索（多路） | 0.35~0.51s | 3~5% | 🟢 可忽略 |
| 精排 | 0.15~0.32s | 2~3% | 🟢 可忽略 |
| RRF 融合 | 0.00s | 0% | 🟢 可忽略 |
| 变体生成（独立一环） | ~3.7s | — | 🟡 次要 |

**两个关键事实**：

1. **界面上的策略耗时差异与检索无关**——三种策略检索只差 0.12s，生成却差 7.59s。**召回素材越多 → 模型写得越长 → 生成越慢**。
2. **每字耗时在 14~35ms 之间波动**（sparse 827 字只用 11.7s，both 454 字却用 16.1s），说明 **LLM API 输出速度本身不稳定**，答案长度是第一驱动因素但非唯一因素。

## 三、优化方案（按收益排序）

| # | 方案 | 预期效果 | 代价 | 实际实施 |
|---|---|---|---|---|
| **1** | **问答结果缓存** | 重复问题 16s → 毫秒级 | 需处理失效 | ✅ 已实施 |
| **2** | **流式输出（SSE）** | 首字延迟 ↓ | 前后端都要改 | ✅ 已实施（**收益低于预期，见下**） |
| 3 | 限制 `max_tokens` | 生成 ↓30~50% | **可能降低答案质量** | ❌ 未做（质量优先） |
| 4 | 变体生成改规则扩展 | 省 ~3.7s | **偏离流程图设计** | ❌ 未做（需产品决策） |
| 5 | 多路检索并发 | 省 0.2s | — | ❌ 不做（收益过低） |

**优化目标**（当时设定）：

| 目标 | 当前 | 目标值 | 验证方式 |
|---|---|---|---|
| 首字延迟（主目标） | ≈12s | < 6s | `tools/check_stream_cache.py` 记录首个 delta 到达时间 |
| 重复问题响应 | 9~17s | < 0.1s | 同脚本连问两次 |
| 总耗时 | 9~17s | 不劣化 | `run_eval.py`，平均耗时不高于 20.32s |

**约束原则**：任何优化**不得让 17/20 掉下来**，质量优先于速度。

## 四、实施内容

### 4.1 问答结果缓存

**新增** `src/rag_demo/cache.py`：

- **LRU + TTL**（容量 256、有效期 1 小时），线程安全
- **缓存键包含 question + dept + 检索模式** —— 必须带模式，否则切换 BM25 / 稀疏向量后会拿到另一套策略的结果，看起来像「策略没生效」
- 失效：TTL 到期、LRU 淘汰、`/admin/clear-cache` 手动清空

**接入** `pipeline.py`：`answer_question()` 包一层缓存，实际流程抽到 `_answer_uncached()`；
返回值新增 `cached` 字段标明是否命中。

**新增接口**：`GET /cache/stats`（命中率）、`POST /admin/clear-cache`。

### 4.2 流式输出（SSE）

- `generator.py` 新增 `generate_stream()`：`stream=True`，逐段 yield 文本
- `pipeline.py` 新增 `prepare()`：把「路由 + 检索 + 精排」与「生成」拆开，让流式接口先拿到上下文
- `api/main.py` 新增 `POST /qa/stream`，事件类型：`stage` / `meta` / `delta` / `done` / `error`
- 前端 `app.js` 改为 `fetch` + `ReadableStream` 手动解析 SSE，**逐字渲染**，并在徽章上标出「首字 X.Xs · 总计 Y.Ys」

## 五、验证结果

`tools/check_stream_cache.py`（两次独立运行）：

```
【第 1 次 · 冷生成】首字 25.46s / 总计 26.73s / 482 字
【第 2 次 · 缓存命中】总计 0.010s     → 2729x

【第 1 次 · 冷生成】首字 17.79s / 总计 18.61s / 375 字
【第 2 次 · 缓存命中】总计 0.006s     → 2997x
```

| 目标 | 目标值 | 实测 | 结果 |
|---|---|---|---|
| 重复问题响应 | < 0.1s | **0.006~0.010s** | ✅ **超额达成（快 3 个数量级）** |
| 首字延迟 | < 6s | **17.8~25.5s** | ❌ **未达成** |
| 质量 | ≥ 17/20 | 未回归（缓存不影响生成逻辑） | ✅ |

### ⚠️ 流式收益低于预期——如实记录

**首字延迟仍高达 17.8~25.5s**，原因拆解：

1. **前置阶段无法流式**：必须先完成「路由 → 变体生成（~3.7s）→ 多路检索 → 精排」才有上下文，这段约 **5~8s** 是硬性等待
2. **模型首 token 本身就要 ~10s**：从 `首字占比 95~96%` 可反推——总耗时 18.6s 里，17.8s 都花在等第一个字。这说明**当前模型在输出首个 content token 前有很长的「思考」阶段**（疑似 reasoning 模型），**这部分 SSE 拿不到任何东西**

**因此流式的实际价值是**：把「生成中」的状态反馈给用户（阶段提示 + 逐字出现），**而不是把首字延迟压到秒级**。原来设定的 `< 6s` 目标**过于乐观，当时没考虑到模型自身的思考耗时**。

**教训**：**流式只能覆盖「输出阶段」，覆盖不了「思考阶段」和「前置检索阶段」**。评估流式收益时，必须先确认模型首 token 延迟——如果模型本身要思考 10s，SSE 再完美也救不了。

## 六、未解决问题 / 后续方向

| 方向 | 预期收益 | 说明 |
|---|---|---|
| **换用非 reasoning 模型做生成** | 首 token 可能从 ~10s 降到 ~1s | **当前首字延迟的主因**，需评估质量损失 |
| 变体生成改规则扩展 | 省 ~3.7s | 偏离流程图设计，需产品决策 |
| 限制 `max_tokens` | 生成 ↓30~50% | 有降低答案质量的风险，未做 |
| 前置阶段进度反馈 | 体感改善 | 已在做（"检索中…" → "生成中…"），可再细化到「检索到 N 条」 |
| 多路 query 检索并发 | 省 0.2s | 收益过低，不做 |

**仍然成立的结论**：**检索、精排、融合加起来不到 1s，无论怎么优化都不值得投入**——优化必须盯住 LLM 生成。

## 七、过程中的问题记录

### 7.1 服务跑了旧代码，验证结果失真

**现象**：验证脚本报 `HTTP Error 404: Not Found`（请求 `/admin/clear-cache`）。

**根因**：`Stop-Process` 没有真正终止旧进程（PID 29604），**后续几次「重启」都因端口被占而静默失败**。查 `openapi.json` 发现注册的路由里没有新接口，才确认服务跑的是旧代码：

```
已注册路由：/qa, /search, /stats, /health, /admin/reload
                                          ↑ 缺 /qa/stream、/cache/stats
```

**修复**：强制清理所有残留 python 进程 → 确认端口释放 → 重新启动，路由补齐：

```
routes: /qa, /search, /stats, /qa/stream, /cache/stats, /admin/clear-cache, /health, /admin/reload
```

**教训**：**改完后端代码要重启服务，而"重启成功"不能只看 `Start-Process` 返回了 PID**——必须验证新接口是否注册（查 `/openapi.json`）。否则会拿着旧服务的结果做判断。

### 7.2 脚本被错误的解释器执行

同一个 404 排查中，traceback 显示 `F:\heima\anaconda\Lib\urllib\request.py`，说明脚本被 **Anaconda 的解释器**执行，而非项目 `.venv`。当前已确认 `.venv\Scripts\python.exe` 正常（`sys.executable` 指向正确）。

**教训**：发现「依赖明明装了却 import 不到」时，先打印 `sys.executable` 确认解释器。

## 九、一句话总结

**瓶颈是 LLM 生成（92~96%），缓存拿下了重复提问（快 3 个数量级），但流式受限于模型自身的思考延迟（首 token ~10s），首字延迟未能压到秒级——这一项没达到预期目标。**
