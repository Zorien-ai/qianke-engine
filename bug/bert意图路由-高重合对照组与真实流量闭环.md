## 2. 第 ③ 项：高重合对照组

### 2.1 为什么必须补

`evaluate.py` 的【4】按「整句 4-gram Jaccard 相似度 ≥0.6」把探针分组，本意是回答**「模型的成绩里多少来自词面记忆、多少来自语义泛化」**。但补之前 55 条探针**没有一条**落在高重合组（最高 0.40 / 0.25）——只有一个组，比较无从谈起，脚本里那句告警指的就是这件事。

### 2.2 怎么造：只改词面，不改语义

从**训练集**的业务句出发做最小改写：

| 训练原句 | 探针 | 相似度 | 改写 |
|---|---|---|---|
| 各会员等级的人数分布以及对应的平均消费 | 各会员等级的人数分布以及对应的平均消费**呢** | 0.933 | 追加语气词 |
| 上个月新增的钻石会员里有多少人已完成首单 | **请问，**上个月新增的钻石会员里有多少人已完成首单 | 0.800 | 前置礼貌语 |
| 麻烦帮我查最近九十天各渠道新客首单转化情况 | 麻烦帮我查最近九十天各渠道新客首单转化情况**呢** | 0.947 | 追加语气词 |

三条硬约束（脚本内自检，与 `gen_hard_samples.py` 同一套思路）：

1. **相似度 ≥0.7**（判据是 0.6，留出余量避免贴边界被算进低重合组）；
   相似度用**字符 4-gram Jaccard**，与 `evaluate.py::_grams` **同一定义**——两处口径不一致，造出来的样本会在评测里落错组。
2. **与清洗集原文不重合**（否则是泄漏：测的就成了记忆，不是"内容相似"）。
3. **语义不变**。对照组的变量只能有一个：词面重合度。改写一旦动了业务语义，两组的差异就分不清是「记忆」还是「问题变难了」。

### 2.3 一个几何事实：短端造不出高重合对照组

句长 L 的句子追加 1 个字符后，4-gram 集合从 L-3 个变到 L-2 个，Jaccard = **(L-3)/(L-2)**：

| 句长 L | 追加 1 字后相似度 | 能否 ≥0.6 |
|---|---|---|
| 4 | 0.500 | ✗ |
| 5 | 0.667 | 边界 |
| 6 | 0.750 | ✓ |
| 20 | 0.941 | ✓ |

**所以高重合组必然由中长句构成**，`U2765` / `看下GMV` 这类短端**在原理上**无法构造"内容见过"的对照——短端只能靠 `unseen` / `fragment` 探针测，别再指望用重合度分组解释它。这条限制已写进本模块与 `evaluate.py` 的注释。

### 2.4 结果

```
【3】分布外探针
  [short] 30 条  准确率：30/30 = 100.0%  [95% CI 88.6%, 100.0%]
  [long]  25 条  准确率：25/25 = 100.0%  [95% CI 86.7%, 100.0%]
  [high]  17 条  准确率：17/17 = 100.0%  [95% CI 81.6%, 100.0%]

【4】重合度整体画像
  [high] n=17  平均 p→t=1.000  平均 t→p=1.000  词面全覆盖(17/17)  最高整句相似=0.947

  按内容重合度分组（max 4-gram 相似度 ≥0.6 视为「内容也见过」）：
    [high] 高重合(>=0.6)     17/17 = 100.0%  [95% CI 81.6%, 100.0%]
    读法：高重合组 17/17=100.0%，低重合组 55/55=100.0%（差 +0.0%）。
      低重合组不低于高重合组 -> **没有证据**表明成绩来自词面记忆；
      低重合组的分数本身就是泛化能力的下界。
      ⚠ 两组样本量都小（17 / 55），差值未做显著性检验
```

对照组确实是"内容见过"的：`p→t = 1.000`、`t→p = 1.000`、词面全覆盖 17/17、最高整句相似 0.947。而它和"字面没见过"的低重合组得分**完全相同**——这是本轮唯一能得出的、有对照支撑的结论。

**不能过度解读**：两组样本量都小（17 / 55），差值未做显著性检验。它只能回答「**有没有**记忆迹象」，不能给出"记忆贡献 0%"这种精确数字。脚本会把这句警示一起打出来，避免读的人只看 100% vs 100%。

### 2.5 工程约束：必须在划分之后生成，且每次划分都重跑

这批探针是从 **train 句**改写来的。换一次划分，它们的"归属"就可能变——旧探针落进新训练集的那一刻，它就从**对照组**变成了**泄漏**，而指标只会更好看、不会报错。

所以生成逻辑挂在 `split_data.py` 的末尾（步骤 2.10），**每次划分自动重跑**，并重新执行"与清洗集不重合"的自检（`build_and_write()` 里自检失败直接 `SystemExit`）。

## 3. 真实流量闭环

### 3.1 为什么必须用分布，而不是个例

「我构造了个例，模型答错了」是**个例驱动**；「真实流量里有多大比例落在模型不稳的区间」是**分布驱动**。区别很实际：

- 个例可以被一条样本修好（上次修 `U2765` 就是这样），但**不可复制**——下一个错误还得等下一次撞上；
- 分布问题得改数据构成或调门槛，**而且必须知道各段占比才知道该改哪段**。

所以本轮的重点不是再修几个个例，而是**把"能看见真实分布"这件事建成基础设施**。

### 3.2 埋点记什么

`logs/intent_routes.jsonl`（运行期数据，已在 `.gitignore`），每行一个 JSON：

| 字段 | 说明 |
|---|---|
| `ts` / `source` / `query` / `route` | 时间 / 来源（`api`=真实线上，`replay`/`backfill-log`=回放与旧日志）/ 原始问题 / 最终判定 |
| `mode` / `via` | 判定器（bert/hybrid/rule）与来源（bert / rule / rule_fallback） |
| **`p_chitchat` / `threshold`** | 概率与当时生效的门槛——**决定"要不要补、门槛要不要调"的唯一依据** |
| `latency_ms` | 本次路由决策耗时（含模型前向） |
| `event` | `route`（入口判定）/ `recheck`（下游复核改道） |

三条纪律（写在模块文档里，代码里强制）：

1. **绝不拖垮请求**：写入 best-effort，出错只记一次 warning 后**自我关闭**（`_disabled`），不抛给调用方；
2. **不拖慢请求**：单行 append + 简单锁，不做聚合、不做远程上报；
3. **不污染分布**：来源必须可分。`api/main.py` 启动时把 source 置为 `api`，离线脚本（bench / smoke / 回放）的记录不会被当成线上流量。

### 3.3 真实流量没有标签：两类的"标签成本"天然不对称

用户不会标注自己问的是闲聊还是业务。但两类错误的标签可得性**完全不同**：

| 错误方向 | 有没有免费标签 | 原因 |
|---|---|---|
| **漏判**（业务被判闲聊，多走一次检索） | ✅ **有** | 下游 `query_processor` 的 LLM 复核会把误判改道，覆盖率 = 100% 的 RAG 分支，**零额外成本** |
| **误伤**（闲聊被判业务，拒答真问题） | ❌ 没有 | 被判 chitchat 的请求**不会**再进 LLM 复核（复核只在 RAG 分支里执行），只能**抽样 + LLM 标注** |

这条不对称不是实现缺陷，是**架构决定**的（同一个事实也解释了为什么门槛要保守：误伤没有兜底通道）。埋点里 `recheck` 事件就是那条免费标签。

### 3.4 分析脚本的两种输入、两种口径

`analyze_routes.py`：

- **输入 1（正式）**：结构化回流 `logs/intent_routes.jsonl`；
- **输入 2（应急/回溯）**：`--backfill "logs/rag_demo.log*"`，把改造前的**文本日志**解析成真实 query 清单，再用**当前模型**离线补算 `p_chitchat`（标记 `p_chitchat_source="offline_model"`）。
  必须说清：它回答的是「**当时用户问了什么**」，不是「当时模型怎么判」——改造前那层是关键词规则，压根没有概率。
- **两种口径**：按请求 / 按去重 query。真实流量重复率很高（本批 44 请求只有 8 个不同问题，`各会员等级的用户人数分别是多少` 一条占了 18 次），只看请求数会被高频问题主导。
- **可选 `--label`**：按 `P(闲聊)` 档位**分层抽样**去重 query，调 LLM 打代理标签（结果缓存到 `outputs/route_labels.jsonl`，支持断点续跑、不重复花钱）。
  ⚠ 这是**代理标注**，与 `recheck` 同源（同模型家族）→ 有同向偏差，能发现"明显错判"，**不能当人工金标准**。

### 3.5 决策门槛（写死在脚本里）

| 条件 | 动作 |
|---|---|
| 请求 < 200 或 去重 < 50 | **不产出补充决策**（只出分布画像）——继续用构造个例驱动补数据会引入采样偏差 |
| 误伤 > 0 | P1：**优先补**，并按长度/字符形态归类误伤样本 |
| 漏判率 > 5% | P1：**先调门槛**（漏判有下游兜底，代价低，比补数据见效快） |
| 模糊带 `p∈[0.5,0.9)` 占比 > 5% | P1：补「模型自己也不确定」的那批样本 |

门槛写进脚本而不是写在文档里，是为了**避免对着数字拍脑袋**：改决策规则就得改代码，改代码就有 diff 可审。

### 3.6 本轮真实数据（44 请求 / 8 去重）

```
来源 {'backfill-log': 36, 'replay': 8}    判定器 {'rule(改造前)': 36, 'bert': 8}
按请求：{'rag': 42, 'chitchat': 2}  被拦成闲聊 4.5%
按去重：{'rag': 7,  'chitchat': 1}  被拦成闲聊 12.5%
```

| P(闲聊) 档位 | 请求数 | 占比 | 判为闲聊 | 去重数 |
|---|---|---|---|---|
| 0.00-0.10 | 42 | 95.5% | 0 | 7 |
| 0.10-0.99 | 0 | 0.0% | 0 | 0 |
| 0.99-1.00 | 2 | 4.5% | 2 | 1 |

- **模糊带 `p∈[0.5,0.9)` 占比 0/44 = 0.0%**，长度画像为空；
- 漏判（免费标签）**0 条**；
- 路由决策耗时 n=8：**p50 27.7ms / p95 43.4ms / max 43.4ms**；
- LLM 代理标注 8 条：**准确率 1.0000**，误伤 0 / 漏判 0。

**这批数据的分布形状很"干净"但也说明不了能力**：8 条问题全来自同一批人工回归（7 条业务 + 1 条「你好」），既没有真实流量的多样性，也没有闲聊/业务的自然配比。所以脚本给出的决策是：

```
样本充足：否   门槛 {'min_requests': 200, 'min_distinct': 50, ...}
[blocked] 样本不足，不产出补充决策
    真实请求 44 条 / 去重 8 条，门槛是 ≥200 / ≥50。
    继续用构造个例驱动补数据会引入采样偏差——等真实流量积累。
```

**这正是"用分布驱动"应有的诚实答案**：不是"模型表现好所以不用补"，而是"**数据量不足以判断**，因此不补"。8/8 的准确率（CI 极宽）和 0% 模糊带都只是"还没看到问题"，不是"没有问题"。

### 3.7 真实 HTTP 流量为什么没跑起来（阻塞点与复现路径）

用户要求的「接到 RAG 入口层跑真实流量」，**接入已完成**（`router.route()` 是入口唯一判定点，埋点在其中），但**真实 HTTP 流量没能跑起来**：

| 检查 | 结果 | 证据 |
|---|---|---|
| Docker daemon | ✗ 未运行 | `failed to connect to the docker API at npipe://.../dockerDesktopLinuxEngine` |
| `docker compose up -d` | ✗ 失败 | 同上（daemon 未起，compose 无法拉起 pgvector） |
| PostgreSQL 5432 | ✗ 不可达 | TCP `connect_ex` 返回 10035；本机无 postgres Windows 服务 |
| 真实启动流程 | ✗ 停在 DB | 直接执行 `lifespan(app)`：`INFO 预加载模型和 BM25 语料...` → `OperationalError: connection to server at localhost (127.0.0.1), port 5432 failed: Connection refused` |

`api/main.py` 的 lifespan 里 `_load_bm25_corpus()` 未做容错——这是**正确的设计**（DB 挂了就该拒绝启动，而不是带病运行产出"知识库缺失"的假答案，`docker-compose.yml` 的注释里记着 2026-10-14 因此误判过一次），所以这里不动它。

**DB 起来后一条命令即可跑真实流量**：

```bash
# 1) 启动数据库（Docker Desktop 需先运行）
docker compose up -d && docker compose ps        # healthy 才算好

# 2) 起服务（lifespan 会预加载模型并启用埋点，source 自动标为 api）
uv run uvicorn rag_demo.api.main:app --port 8000

# 3) 打真实请求（前端 / curl 都可以），埋点自动落 logs/intent_routes.jsonl

# 4) 分析真实分布（只统计 api 来源）
uv run python src/rag_demo/bert_query_classify/analyze_routes.py --source api --label
```

届时 `analyze_routes.py` 会直接给出「要不要补、补什么」的结论——**不需要任何额外开发**，这正是本轮要交付的东西。

### 3.8 顺带修掉的真问题：首次判定 607ms

回放暴露了一个只有真实调用才会显形的问题：`BERT_LOAD` 只加载权重时，CUDA 的 kernel 选择/autotune 被推迟到**第一次请求**，那次判定 **607.9 ms**（p50 25.7ms）。

入口路由在**每个请求**的关键路径上，把这 0.6s 留给真实用户没有理由。已在 `preload()` 里补一次真实前向预热：

| 指标 | 预热前 | 预热后 |
|---|---|---|
| mean | 108.60 ms | ~28 ms |
| p50 | 25.66 ms | 27.69 ms |
| **p95 / max** | **607.91 ms** | **43.38 ms** |

（p50 基本没变，被修掉的是那条长尾——这也说明只看均值会低估问题、只看 p50 会漏掉它。）

## 4. 两项已知边界（记录在案，不再动）

按约定，上一轮的两项遗留**不再花成本**，在此封存：

| # | 边界 | 表现 | 方向与代价 | 为什么不动 |
|---|---|---|---|---|
| 1 | **camelCase 类字母闲聊**（如 `HelloWorld`）被判成业务 | 闲聊漏判 | 多走一次检索 + 生成（约 25.2s 白花，**但答得出来**），不拒答 | 属"可兜底"方向；且它与本轮修好的 ID 泛化能力是**同一根神经**（字母+数字越像 ID 越判业务），贸然加负样本可能把误伤换回来。**严禁**把 `HelloWorld` 本身加进训练集（它在 val 里，那是泄漏） |
| 2 | **`收到`**（2 字确认词）在**训练集内**仍判错 | 闲聊漏判 | 同上，不拒答 | 新增 `收藏数` / `首单数` 里的"收"字与它纠缠（**假设，未做消融**）。要动它得先做消融实验，成本高于收益 |

**封存的依据**：这两项都是**漏判方向**（可被下游 LLM 复核捞回、不拒答），代价是时间不是正确性；而 §3 的闭环已经能回答更重要的问题——**它们到底占真实流量的多大比例**。如果某天分布分析显示这类形态占比显著，再回来动它，那时是数据说话。
